# recipe-management（レシピ管理）全体設計

> UI の詳細（画面毎の部品配置・画面遷移）は書かない → `ui-design.md`
> API の詳細（パス・要求・応答・エラー）は書かない → `api-design.md`
> テーブル定義と ER 図は書かない → `db-design.md`

## 全体構成

本設計は `requirements.md` の REQ-001〜REQ-014 を満たす。

- フロントエンド: `src/features/recipe-management/frontend` の Vue（SPA）。Vite `base` は `/portal_recipe_management/`。nginx では dist をドキュメントルートの `features/recipe-management/` に置き、公開 URL `/portal_recipe_management/` へ対応付ける。
- バックエンド: `src/features/recipe-management/backend` の別プロセスの FastAPI（venv、uvicorn）。開発時のポートは 8008、フロントの開発ポートは 5182（既存機能と重複しない値）。
- API 基点: フロントの `VITE_API_RECIPE_MANAGEMENT_URL`。
- DB: 業務テーブル（レシピ・工程・工程の材料・材料・分量名称）はスキーマ `recipe_management` に置く。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` を直接読む（複製しない）。
- 材料・分量名称は、全利用者共通のもの（所有者なし）と、利用者独自のもの（所有者あり）を、同じテーブルに持つ。共通のものは DDL で初期データとして登録する。
- レシピは、利用者ごとに持つ。レシピの削除は論理削除（削除フラグ）。工程と工程の材料は、レシピの編集時に、作り直す（物理削除して再登録）。
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない。
- 本機能の識別子: `recipe-management`（機能マスタの識別子。利用可否判定に用いる）。
- 移行プログラム: バックエンドの `scripts/` に、コマンドラインのスクリプトとして置く。移行元 DB と移行先 DB へ同時に接続する。API サーバとは独立に動く。

```
ブラウザ ── SPA(Vue) ──(Cookie)──▶ FastAPI ──▶ PostgreSQL（移行先: public / recipe_management）
                                                        ▲
移行プログラム(scripts/) ── 読み取り ──▶ 移行元 DB       │ 書き込み
                       └─────────────────────────────────┘
```

関連ドキュメント: `requirements.md` / `ui-design.md` / `db-design.md` / `api-design.md`

## フロントエンド設計

### 画面

画面の一覧のみ。部品配置と遷移の詳細は `ui-design.md`。ログイン画面とメニュー画面は持たない。ヘッダ / ナビの殻を使う（`rules/15-ui-style.md`）。パスは Vue Router のルート（公開パスの基点は Vite `base`）。

| 画面 | パス | 役割 |
|------|------|------|
| レシピ一覧 | `/` | 本人のレシピを、かなの順に表示する。詳細・登録への入口。 |
| レシピ登録 | `/recipes/new` | メニュー名・かな・工程・材料と分量の入力。材料・分量名称の追加のダイアログを含む。 |
| レシピ詳細 | `/recipes/:id` | メニュー名・かな・材料一覧・工程ごとの説明と材料の表示。編集・削除への入口。 |
| レシピ編集 | `/recipes/:id/edit` | 登録と同じ入力を、現在の内容を初期値として編集する。 |

未ログインはシステム設定のログイン画面 URL へ誘導する。戻る先はシステム設定のメニュー画面 URL とする。`createWebHistory(import.meta.env.BASE_URL)` を用いる。`/recipes/new` は `/recipes/:id` より先に定義する。

材料・分量名称は、独立した画面を持たず、レシピの登録・編集画面の選択肢と、そこから開くダイアログ（追加）として扱う（REQ-008・REQ-009）。

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 一覧・入力中の内容・材料と分量名称の選択肢は画面内の状態とする。永続化しない。
- システム設定（ログイン画面 URL、メニュー画面 URL、共通アイコン）は API から取得して保持する。

### レシピの入力（フロントの責務）

- 入力は、メニュー名・かなと、1 件以上の工程（説明と、材料の行 0 件以上）で構成する。工程は追加・削除でき、最後の 1 件は削除できない。材料の行は追加・削除できる。
- 材料の行は、材料の選択、分量名称の選択（接頭語を選び、その接頭語と組になる接尾語を選ぶ）、数量の入力からなる。分量名称が数量なしのときは、数量を入力できない（空にする）。
- 材料が未選択の行は、送信のときに取り除く。
- 材料・分量名称のダイアログから追加したら、選択肢を取得し直し、その行に、追加したものを選ぶ。
- 詳細の「材料一覧」は、取得した工程の材料を、フロントで、工程の順に並べて組み立てる（サーバは、工程と材料を並び順で返すだけ）。
- 入力の検証は、送信前に行い、サーバ側の検証と同じ規則にする。失敗時は、内部理由が分からない一文だけを示す。

### 業務ロジック

#### 共通

- すべての操作は、ログイン必須かつ、ログイン中ユーザに本機能が割り当てられていること。
- レシピは、常にログイン中ユーザ自身の `user_id` で絞り込む。他ユーザの行は存在しないものとして扱う。
- 材料・分量名称は、共通（所有者なし）と、ログイン中ユーザの独自だけを対象にする。レシピに指定された材料・分量名称が、この範囲に無いときは、存在しないものとして扱う。
- 文字列の必須項目は、前後の空白を除いた結果が空のときは入力不正とする。

#### レシピの一覧・詳細

- 一覧は、本人の削除されていないレシピを、かなの昇順、同じなら登録の古い順（識別子の昇順）で返す。
- 詳細は、本人の削除されていないレシピについて、メニュー名・かなと、工程を工程番号の昇順で返す。各工程に、その工程の材料を、並びの順に含める。各材料には、材料（識別子・名前・かな・共通か）、分量名称（識別子・接頭語・接尾語・数量の要否）、数量を含める。工程の説明の本文を、ログには出さない。

#### レシピの登録・編集

- 登録・編集の入力の検証（メニュー名・かなの必須、工程が 1 件以上、工程の説明の必須、材料の行の分量名称、数量ありのときの数量の必須）を、サーバ側でも行う。数量なしの分量名称の数量は、保存しない（空にする）。
- 登録と編集は、それぞれ 1 つのトランザクションで行う。
- 登録: メニュー名が、本人の削除されていないレシピと重複するときは失敗にする（重複の判定は、DB の一意制約で行い、同時の登録でも、二重に作らない）。成功したら、工程を 1 から連番で作り、各工程の材料を並びの順に作る。
- 編集: 対象のレシピを行ロックで取得し（本人の、削除されていないもの。無ければ対象なし）、メニュー名・かなを更新し、既存の工程と工程の材料を削除して、入力の内容で作り直す。レシピの識別子は変わらない。メニュー名の重複は、自身を除いて判定する（DB の一意制約）。更新日時を更新する。
- 材料の行の並びは、入力の順に採番して保持し、詳細では、その順に返す。

#### レシピの削除

- 本人の削除されていないレシピを、論理削除する（削除フラグを立て、更新日時を更新する）。工程と材料は残す。削除済みのレシピは、一覧・詳細・編集・削除の対象にならない。同じメニュー名での再登録を許すため、メニュー名の一意制約は、削除されていないレシピだけを対象にする。

#### 材料・分量名称

- 材料: 共通と本人の独自を、かなの昇順、同じなら識別子の昇順で返す（共通か独自かを含める）。追加は、名前・かなの必須を確認し、同じ名前の材料が、共通、または本人の独自としてあれば、失敗にする。
- 分量名称: 共通と本人の独自を、接頭語の昇順、接尾語の昇順、識別子の昇順で返す（共通か独自かを含める）。追加は、接頭語・接尾語の前後の空白を除き、両方が空なら入力不正とする。同じ接頭語と接尾語の組が、共通、または本人の独自としてあれば、失敗にする。
- 共通の材料・分量名称、および独自のものの変更・削除の操作は持たない。

#### ログ

- 操作が試みられたとき、次を契機としてログへ出す。
  - 入力された内容（メニュー名・かな・工程数・材料の行の数・材料名・分量名称、対象の識別子など。工程の説明の本文は出さない）
  - それを元にした判断結果（成功、一覧の件数）
  - 正常系ではない場合の理由（重複、対象なし、入力不正、未ログイン、権限なし）
- 1 行はタイムスタンプ、区分、メッセージの順。区分は INF / WRN / ERR / DBG。出力先は `log/`。ファイルサイズでローテーションし、上限は `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。
- セッション ID、パスワード、Cookie は出さない。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。DB の失敗は、原因の先頭の 1 行をログにだけ残す（パスワードは含まれない）。

### 移行プログラム

移行元（既存のレシピ管理サービスの DB。スキーマ `recipe`）から、移行先（本機能の DB）へ、両方に同時に接続して直接移行する。実行場所は、本機能のバックエンドの venv が使え、両方の DB に到達できる環境。

- 配置: `backend/scripts/migrate_from_recipe.py`、手順書 `backend/scripts/README.md`。
- 接続:
  - 移行元: 引数（`--host` `--port` `--dbname` `--user` `--password`）または環境変数（`RECIPE_DB_HOST` / `RECIPE_DB_PORT` / `RECIPE_DB_NAME` / `RECIPE_DB_USER` / `RECIPE_DB_PASSWORD`）。パスワードは画面・ログに出さない。読み取り専用のセッションで接続する。
  - 移行先: `backend/.env`（または `RECIPE_MANAGEMENT_ENV_FILE` で指定した設定ファイル）。
  - どちらかの接続に失敗したときは、どちらかがわかるメッセージを表示して終了する。
- 引数: `--username`（必須。移行先の利用者名）、`--dry-run`（書き込まない）。
- 処理の流れ:
  1. 両方の DB に接続し、`--username` の利用者を、移行先の `public.users` から探す（論理削除済みは不可）。無ければ、何も移行せずに、その旨を表示して終了する。
  2. 材料を、移行元の識別子の昇順に、対応付ける。移行先の共通の材料に、名前が同じものがあれば、それに対応付ける。無ければ、指定した利用者の独自の材料に、名前が同じものがあれば、それに対応付ける。それも無ければ、指定した利用者の独自として追加する。
  3. 分量名称を、同様に、接頭語と接尾語の組で対応付ける（共通 → 指定した利用者の独自 → 追加）。数量の要否が、対応付けた既存のものと違うときは、既存のものを変更せず、違いを一覧表示する。
  4. レシピを、移行元の識別子の昇順に、1 件ずつ移行する（下記）。削除済みのレシピは、対象外として記録する。
  5. 結果を報告する。
- レシピ 1 件の移行:
  - 移行済みの判定: 指定した利用者の、削除されていないレシピに、同じメニュー名があるとき、移行済みとしてスキップする。
  - 移行先に、レシピ、全工程（工程番号は移行元の値）、全工程の材料（並びは移行元の識別子の順。材料・分量名称は対応付けた識別子）を、**1 つのトランザクション**で作成する。数量は移行元の値を用いる。
  - 移行元に存在しない材料・分量名称を指す行は、その行だけを取り除き、取り除いた行を一覧表示する。
  - 最後に、移行先の工程数と材料の行の数を、移行元（取り除いた行を除く）と照合し、一致したときだけ確定する。一致しない、または途中で失敗したときは、ロールバックして、そのレシピを失敗として記録する。次のレシピへ進む。
  - 識別子は移行先で新しく採番する。
- ドライラン: 移行元と移行先の読み取りだけを行い、対象の件数、スキップ、対象外を報告して終了する。
- 進捗: レシピ 1 件ごとに「n / 全体件数、メニュー名」を標準エラー出力へ出す。
- 結果の報告: 種別（レシピ・工程・材料の行・材料・分量名称）ごとに、移行・スキップ・対象外・失敗の件数と内訳を標準エラー出力へ出す。失敗が 1 件でもあれば、終了コードを 0 以外にする。
- 移行元へは書き込まない。移行プログラムの操作記録（開始・終了・失敗の理由）は、本機能のログ方針に従い `log/` にも出す（パスワードは出さない）。

## 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API は、ログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログイン、割当なしは権限なしとして扱う。フロントは、未ログインならログイン画面へ誘導する。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい（当該ユーザへの本機能の割当は判定する）。本番では空にする。
- 他機能の API を認証・利用可否判定に使わない。
- 移行プログラムは、画面のログインを介さない。移行先の利用者は、ユーザ名の指定で決める。

## 外部連携

- 移行元のレシピ管理サービスの DB（`sample/recipe` の実運用 DB）。移行プログラムからだけ、読み取りで接続する。本機能の API サーバは、移行元へ接続しない。
- 上記以外の他システム・外部 API との連携はなし。
