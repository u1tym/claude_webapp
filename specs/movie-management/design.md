# movie-management（動画管理・視聴）全体設計

> UI の詳細（画面毎の部品配置・画面遷移）は書かない → `ui-design.md`
> API の詳細（パス・要求・応答・エラー）は書かない → `api-design.md`
> テーブル定義と ER 図は書かない → `db-design.md`

## 全体構成

本設計は `requirements.md` の REQ-001〜REQ-023 を満たす。

- フロントエンド: `src/features/movie-management/frontend` の Vue（SPA）。Vite `base` は `/portal_movie_management/`。nginx では dist をドキュメントルートの `features/movie-management/` に置き、公開 URL `/portal_movie_management/` へ対応付ける。
- バックエンド: `src/features/movie-management/backend` の別プロセスの FastAPI（venv、uvicorn）。開発時のポートは 8007、フロントの開発ポートは 5181（既存機能と重複しない値）。
- API 基点: フロントの `VITE_API_MOVIE_MANAGEMENT_URL`。
- DB: 業務テーブル（動画・チャンク・サムネイル・作品・ジャンル・プレイリスト・再生状態など）はスキーマ `movie_management` に置く。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` を直接読む（複製しない）。
- 動画ファイル本体はデータベースに保管する。動画ファイルを約 4 MB のチャンクに分割し、1 チャンクを 1 行として保管する（サンプルと同じ方式。移行元と保管方式が同じため、移行はチャンクの単純なコピーになる）。
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない。
- 本機能の識別子: `movie-management`（機能マスタの識別子。利用可否判定に用いる）。
- 移行プログラム: バックエンドの `scripts/` に、コマンドラインのスクリプトとして置く。移行元 DB と移行先 DB へ同時に接続する。API サーバとは独立に動く。

```
ブラウザ ── SPA(Vue) ──(Cookie)──▶ FastAPI ──▶ PostgreSQL（移行先: public / movie_management）
                                                        ▲
移行プログラム(scripts/) ── 読み取り ──▶ 移行元 DB       │ 書き込み
                       └─────────────────────────────────┘
```

関連ドキュメント: `requirements.md` / `ui-design.md` / `db-design.md` / `api-design.md`

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 一覧・検索条件・ページ位置・編集中の内容は画面内の状態とする。永続化しない。
- システム設定（ログイン画面 URL、メニュー画面 URL、共通アイコン）は API から取得して保持する。

### 動画のアップロードと再生（フロントの責務）

- アップロード: ブラウザが、選んだ動画ファイルを約 4 MB ごとに分割し、順番に 1 つずつ送信する。全チャンクの送信後に完了を通知する。進捗は「送信済みチャンク数 / 全チャンク数」で示す。送信前に、再生時間の取得、H.265 の判定、サムネイル画像の生成（未指定のとき）を行う。
- 再生: HTML の動画要素に、バックエンドの動画配信の URL を直接指定する。ブラウザが必要な範囲だけを要求し、位置の移動もブラウザが行う。動画要素は Cookie を自動で送る。
- 再生位置の保存: 一時停止、位置の移動の完了、画面を離れるとき、および再生中の一定間隔（10 秒ごと）に、再生位置を送信する。送信の失敗では再生を止めない。
- 再生終了時: 次の動画（プレイリスト再生では次の項目）があれば、続けて再生する。

### バリデーション

- タイトル・名称は、空文字・空白のみを送信しない。文字数の上限は要件どおり。
- 動画ファイルは、H.265 と判定できるとき登録・差し替えを行わず、警告と変換方法を示す。
- 失敗時は、内部理由が分からない一文のメッセージだけを示す。

### 業務ロジック

#### 共通

- すべての操作は、ログイン必須かつ、ログイン中ユーザに本機能が割り当てられていること。
- 動画・作品・独自ジャンル・プレイリスト・再生状態は、常にログイン中ユーザ自身の `user_id` で絞り込む。他ユーザの行は存在しないものとして扱う。
- 一覧はページ分けする。標準 20 件、上限 100 件。

#### 動画の登録とアップロード

- 動画の登録は 3 段階とする。(1) 動画情報（メタ情報）を「登録中」で作成し、識別子を払い出す。(2) チャンクを 1 つずつ受信し保管する。(3) 完了の通知を受けて、チャンク数の一致を確認し、再生時間を確定して「再生可能」にする。
- チャンクの受信時に、対象動画が本人のもので「登録中」であること、時刻範囲とデータが妥当であること、同じ番号のチャンクが無いことを確認する。動画のチャンク数とファイルサイズの合計は、チャンクの保管と同時に更新する。
- 完了の通知でチャンク数が一致しないとき、またはチャンクが 1 つも無いときは、「再生可能」にしない。
- 再生時間は 1 ミリ秒以上 14,400,000 ミリ秒以下とする。
- 作品の新規作成を伴う登録では、作品を先に作成してから動画情報を作成する（フロントが順に呼び出す）。
- 話数の重複は、同一作品内で判定する。

#### 動画ファイルの差し替え

- 差し替えの開始時に、その動画の既存チャンクを削除し、動画を「登録中」に戻して、チャンク数・ファイルサイズを 0、再生時間・ファイル形式を新しいファイルのものにし、本人の再生位置と視聴完了をリセットする。以降は、登録時のチャンク受信と完了の流れに合流する。
- 差し替えを開始した後に失敗したときは、動画は「登録中」のまま残る（再度の差し替えまたは削除ができる）。

#### 動画の削除

- 物理削除とする。動画ファイル、サムネイル、ジャンルとの関連、再生状態は、動画に連鎖して削除する（削除の連鎖はテーブルの参照制約で行う）。プレイリストの項目は動画に連鎖して削除され、続きから視聴の参照は解除される。

#### 動画の配信（範囲配信）

- 動画の配信は、指定されたバイト範囲だけを返す（範囲指定がなければ全体を返す）。ブラウザの再生・位置の移動は、この配信で実現する。
- チャンクごとのバイト長を先頭から積み上げて、各チャンクの動画内のバイト位置を求める（データ本体は読まない）。要求された範囲にかかるチャンクだけを、1 つずつ取得して、必要な部分を切り出して返す。同時にメモリに載せるのは 1 チャンクとする。
- 範囲が動画の大きさを超えるときは、満たせないものとして扱う。
- 「再生可能」の動画だけを配信する。
- 認証は Cookie（`認証 / 認可` 節）。
- 再生時間から位置に対応するチャンクを特定する処理（再生開始・シーク）は、チャンクの時刻範囲から求める。

#### 再生

- 再生の開始時に、本人の動画が「再生可能」であることを確認し、再開位置を決める（前回位置から再開、または先頭。前回位置が動画の長さ以上のとき、つまり超えるとき、および末尾のときは先頭）。再生回数を 1 増やし、最終再生日時を更新し、続きから視聴の情報（最後に単独で再生した動画と位置）を更新する。
- 再生位置の保存は、動画ごと・利用者ごとに 1 件を更新する（無ければ作成する）。位置が動画の長さを超えるときは受け付けない。プレイリスト再生の途中では、プレイリストの続きから視聴の情報（プレイリスト、項目、位置）も更新する。
- 「次の動画」は、動画が作品に属するときは同一作品内の作品内順序（同じ順序の動画は、話数、識別子の順）で、属さないときは本人の作品に属さない動画の登録日時順で決める。いずれも「再生可能」の動画だけが対象。
- 続きから視聴は、単独再生とプレイリスト再生を別々に保持する。動画・プレイリスト・項目が削除された、または再生できない状態のときは、示さない。
- 視聴履歴は、再生状態を最終再生日時の降順で返す。

#### 動画一覧

- 既定は「再生可能」のみ。状態、ジャンル、作品、キーワード（タイトル・話タイトル、大文字小文字を区別しない部分一致）で絞り込む。登録日時・タイトル・最終再生日時で並べ替える。最終再生日時で並べるとき、再生していない動画は末尾。
- 一覧の応答に動画ファイルのデータは含めない。サムネイルは別の取得で表示する。

#### 作品・ジャンル・プレイリスト

- 作品: 登録、一覧（登録日時の降順、タイトル検索）、詳細（所属動画を作品内順序・話数の順）。
- ジャンル: 全利用者共通のジャンル（所有者なし）と、本人の独自ジャンルを、表示順で返す。独自ジャンルの名称は、同一ユーザの中で重複させない。共通ジャンルは変更できない（追加・変更・削除の操作を持たない）。
- プレイリスト: 作成、一覧（更新日時の降順、含まれる動画の件数）、詳細（項目を並び順）、名前・説明の変更、削除、項目の並びの置換。項目の置換は、指定された動画がすべて本人のものであることを確認し、既存の項目を入れ替える。項目の置換・名前の変更のとき、プレイリストの更新日時を更新する。
- プレイリストの再生: 先頭から、または続きから（そのプレイリストで最後に再生した項目と位置。位置が動画の長さ以上のときは、その項目を先頭から）。次・前の項目は、並び順で隣接するものを返す。返した項目を続きから視聴の情報にする。

#### ログ

- 操作が試みられたとき、次を契機としてログへ出す。
  - 入力された内容（タイトル、名称、検索キーワード、対象の識別子など。説明文の値そのものは出さない）
  - それを元にした判断結果（成功、一覧・検索の件数）
  - 正常系ではない場合の理由（重複、対象なし、入力不正、処理不可、未ログイン、権限なし）
- 高頻度の処理（チャンクごとの受信・配信、再生位置の定期保存）は、1 件ごとにはログへ出さず、動画単位・再生単位でまとめて出す（アップロードの開始と完了、配信の要求は範囲の初回のみ、など）。
- 1 行はタイムスタンプ、区分、メッセージの順。区分は INF / WRN / ERR / DBG。出力先は `log/`。ファイルサイズでローテーションし、上限は `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。
- セッション ID、パスワード、Cookie の値は出さない。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。

### 移行プログラム

移行元（既存の動画視聴サービスの DB）から、移行先（本機能の DB）へ、両方に同時に接続して直接移行する。実行場所は、本機能のバックエンドの venv が使え、両方の DB に到達できる環境。

- 配置: `backend/scripts/migrate_from_movie.py`、手順書 `backend/scripts/README.md`。
- 接続:
  - 移行元: 引数（`--host` `--port` `--dbname` `--user` `--password`）または環境変数（`MOVIE_DB_HOST` / `MOVIE_DB_PORT` / `MOVIE_DB_NAME` / `MOVIE_DB_USER` / `MOVIE_DB_PASSWORD`）。パスワードは画面・ログに出さない。読み取り専用のセッションで接続する。
  - 移行先: `backend/.env`（本機能の設定）。
  - どちらかの接続に失敗したときは、どちらかがわかるメッセージを表示して終了する。
- 引数: `--dry-run`（書き込まない）、`--username`（対象ユーザの絞り込み。複数指定可）。
- 処理の流れ:
  1. 両方の DB に接続する。
  2. 移行元の全アカウント（識別子とユーザ名）を読み、ユーザ名が一致し、論理削除されていない移行先ユーザに対応付ける。対応付けできないアカウントは、対象外として、ユーザ名と件数（動画・作品など）を記録する。
  3. 共通ジャンルを名称で対応付ける（移行先に無ければ追加）。利用者独自のジャンルは、移行先の同じ利用者の同名のものと対応付け、無ければ追加する。
  4. 作品を、同じ利用者・同じタイトルのものと対応付け、無ければ追加する（移行元の日時を保つ）。
  5. 動画を 1 件ずつ移行する（下記）。
  6. 再生状態を、移行した（または移行済みの）動画について移行する。移行先に、同じ利用者・同じ動画の再生状態が既にあるときはスキップする（移行先で視聴が進んでいる可能性があるため、上書きしない）。
  7. プレイリストを、同じ利用者・同じ名前のものが移行先に無いときだけ移行する（あるときはスキップ）。項目は、移行元の並びのまま。動画が移行されていない項目は取り除き、取り除いた項目を記録する。
  8. 続きから視聴の情報を、移行先に同じ利用者の情報が無いときだけ移行する。指す動画・プレイリスト・項目が移行されていないときは、その部分を空にする。
  9. 結果を報告する。
- 動画 1 件の移行:
  - 対象は、移行元で「再生可能」の動画のみ。それ以外は対象外として記録する。
  - 移行済みの判定: 移行先に、同じ利用者で、タイトル・ファイルサイズ・再生時間が一致する動画があるとき、移行済みとしてスキップし、その動画の識別子の対応（移行元→移行先）を記録する。
  - 移行先に、動画情報（「登録中」）、全チャンク、サムネイル、ジャンルとの関連を、**1 つのトランザクション**で作成する。チャンクは、移行元から、番号順に 1 件ずつ読み取り（サーバ側カーソル）、1 件ずつ書き込む。全チャンクを同時にメモリへ載せない。
  - 最後に、移行先のチャンク数とバイト長の合計を、移行元と照合し、一致したときだけ「再生可能」にして確定する。一致しない、または途中で失敗したときは、ロールバックして、その動画は失敗として記録する。次の動画へ進む。
  - 識別子は移行先で新しく採番する。登録日時・更新日時・話数・作品内順序・再生時間・ファイル形式・チャンクの分割は、移行元の値を用いる。
- ドライラン: 移行元と移行先の読み取りだけを行い（チャンクのデータは読まない）、対象の件数、スキップ、対象外を報告して終了する。
- 進捗: 動画 1 件ごとに「n / 全体件数、タイトル」を標準エラー出力へ出す。
- 結果の報告: 種別（動画・サムネイル・作品・ジャンル・再生状態・プレイリスト・項目・続きから視聴）ごとに、移行・スキップ・対象外・失敗の件数と内訳を標準エラー出力へ出す。失敗が 1 件でもあれば、終了コードを 0 以外にする。
- 移行元へは書き込まない。移行プログラムの操作記録（開始・終了・失敗の理由）は、本機能のログ方針に従い `log/` にも出す（パスワードは出さない）。

## 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API は、ログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログイン、割当なしは権限なしとして扱う。フロントは、未ログインならログイン画面へ誘導する。
- 動画の配信とサムネイルの取得も、同じ Cookie 認証で守る（URL だけでは取得できない）。動画要素・画像要素は Cookie を自動で送るため、追加のトークンは設けない。この前提のため、フロントの公開先と API の公開先は、Cookie が送られる関係（同一サイト）にする（開発時は `localhost` のポート違い、本番は nginx で同一オリジン）。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい（当該ユーザへの本機能の割当は判定する）。本番では空にする。
- 他機能の API を認証・利用可否判定に使わない。
- 移行プログラムは、画面のログインを介さない。移行先のユーザは、ユーザ名の一致で対応付ける。

## 外部連携

- 移行元の動画視聴サービスの DB（`sample/movie` の実運用 DB）。移行プログラムからだけ、読み取りで接続する。本機能の API サーバは、移行元へ接続しない。
- 上記以外の他システム・外部 API との連携はなし。

## デプロイ上の考慮（nginx）

- 公開 URL とディスク配置は `rules/17-nginx-deploy.md` に従う（`/portal_movie_management/`、`features/movie-management/`）。
- チャンクのアップロード（1 リクエストが約 4 MB）を通せるよう、API を nginx 経由で公開する場合は、リクエスト本文の上限を 8 MB 以上にする。
- 動画の配信は、応答をバッファリングせずに流す設定にする。配置例は `frontend/nginx.example.conf` に書く。
