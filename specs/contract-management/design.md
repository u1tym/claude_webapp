# contract-management（契約管理） 全体設計

> UI の詳細（画面毎の部品配置・画面遷移）は書かない → `ui-design.md`
> API の詳細（パス・要求・応答・エラー）は書かない → `api-design.md`
> テーブル定義と ER 図は書かない → `db-design.md`

## 概要

本設計は `requirements.md` の REQ-001〜REQ-014 を満たす。ログイン中の、本機能が割り当てられた利用者が、自分専用の契約（契約を伴わないアカウントを含む）を登録・編集・削除・一覧・検索・詳細表示でき、区分の管理、ユーザ名とパスワードのアカウント一覧、解約順の整理と解約手順の PDF 出力ができるようにする。外部システム（生成AI など）は、API キーで、パスワードの値を除いて、契約の参照・登録・更新ができる。ログインとメニューは `portal` が担う。本機能は `public` のユーザ・セッション・システム設定・機能マスタ・メニュー割当・API キーを参照し、複製しない。

## 全体構成

- フロントエンド: `src/features/contract-management/frontend` の Vue（SPA）。Vite `base` は `/portal_contract_management/`。nginx では dist をドキュメントルートの `features/contract-management/` に置き、公開 URL `/portal_contract_management/` へ対応付ける。開発時のフロントのポートは 5186。
- バックエンド: `src/features/contract-management/backend` の別プロセスの FastAPI（venv、uvicorn）。開発時のポートは 8012。
- API 基点: フロントの `VITE_API_CONTRACT_MANAGEMENT_URL`。
- DB: 業務テーブル（契約、区分、解約順など）はスキーマ `contract_management` に置く。DDL は `backend/sql/` が持つ。ユーザ、セッション、システム設定、機能マスタ、メニュー割当、API キーはスキーマ `public` を直接読む（複製しない）。
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない。
- 本機能の識別子: `contract-management`（機能マスタの識別子。利用可否判定に用いる）。

```
ブラウザ ── SPA(Vue) ──(Cookie)──▶ contract-management(FastAPI) ──▶ contract_management.*（業務データ）
                                                                  └▶ public.*（ユーザ・セッション・機能マスタ・割当）
外部システム（生成AI など）──(API キー)──▶ 同じ FastAPI（許可する操作だけ） ──▶ public.api_keys（判定・最終利用日時）
password-management の DB ──（取り込みスクリプト）──▶ contract_management.contracts
```

関連ドキュメント: `requirements.md` / `ui-design.md` / `db-design.md` / `api-design.md`

### 状態管理・バリデーション

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 一覧・絞り込み条件・選択中の契約・マスク表示の状態・解約順の編集中の並びは画面内の状態とする。永続化しない。
- パスワードの値は、一覧・アカウント一覧の応答に含まれない。表示・コピーを操作したときに、その 1 件を取得して画面内にだけ保持し、画面を離れるときに破棄する。
- 入力検査（名称の空白、維持費の整数、契約日の精度との整合、契約終了日はステータスが解約のときだけ、2段階認証の送付先の対応、数値項目など）は、送信前にも行う。失敗時は、内部理由が分からない一文のメッセージだけを示す。
- 契約を伴わないに切り替えるときは、消える項目があることを、保存の前に示す。

### PDF 出力

解約順ページが、出力対象（解約の対象とその順序）を取得し、印刷用のレイアウト（画面には出さない領域）に、出力日、解約順の番号、名称、解約方法を並べて、ブラウザの印刷機能（`window.print()`）を呼ぶ。PDF への保存は、ブラウザの印刷先「PDF に保存」で行う。この方式は、`note-management` の PDF 出力と同じで、日本語の字形はブラウザに任せる。パスワード、ユーザ名、登録メールアドレスは、取得も、印刷用のレイアウトへの出力もしない。

### 業務ロジック

#### 共通

- すべての操作は、ログイン必須かつ、ログイン中ユーザ（API キーのときは持ち主）に識別子 `contract-management` の機能が割り当てられていること。論理削除済みのユーザまたは本機能は許可しない（REQ-001）。
- すべての参照・操作は、常に、ログイン中ユーザ自身の `user_id` で絞り込む。他ユーザの行は存在しないものとして扱う。依存契約・支払方法・解約順の対象に、他ユーザの契約を指定した場合は、入力不正とする（REQ-012）。
- 契約・区分は、削除（契約は論理削除）されたものを、一覧・アカウント一覧・解約順・依存契約・支払方法の選択肢の対象から除く。

#### 契約

- 契約には、契約を伴う・伴わないの別がある。伴わない契約は、維持費、更新日、契約日（と精度）、契約終了日、無料期間の終了日、解約方法、依存契約、支払方法、契約者名義、会員番号・契約番号、自動更新の有無、解約の受付期限、解約手数料・違約金、最低契約期間、問い合わせ先を持たない。送られた場合は入力不正とする。伴うから伴わないへの切替では、これらの値を消す（保存の前に、画面が示す）。切替時は、解約順の対象からも外す。
- 入力の検査（REQ-001）は、サービス層で行う。名称・ユーザ名・登録メールアドレスなどの文字列は、前後の空白を除いて格納する。名称は空白のみ不可。パスワードは、空文字のみ不可（空白のみ・複数行は可）。
- 維持費は、金額（0 以上の整数）と、年間か月額かの別をまとめて持つ。契約日は、精度（年月日、年月、年、不明）に応じた日付を、年月日の日付 1 つとして持ち、精度に応じて、使わない月・日を 1 で埋める。契約終了日は、契約を伴うかつステータスが解約のときだけ受け付ける。ステータスが解約でなくなったとき、契約終了日は消す。
- 2段階認証の送付先は、メール・TEL の方式ごとに持ち、ログイン方法にその方式を選んでいるときだけ受け付ける。ログイン方法から方式を外したとき、その送付先は消す。
- 依存契約は、複数を持つ関係とし、更新時に、依存の関係が循環しないことを、依存先をたどって検査する（REQ-002）。自分自身は選べない。支払方法は、契約 1 つへの参照で、自分自身は選べない。循環の検査の対象外とする。
- 契約の削除は論理削除。削除した契約への参照（依存契約、支払方法）は、参照している側の表示から外れる。解約順の対象からも外す。
- ステータスが解約になった契約、契約を伴わないに切り替えた契約は、解約順の対象から外す。
- 区分は、契約に必ず 1 つ付く。指定がないときは「その他」とする。
- 支払方法には、削除されていない、同じ利用者の他の契約のうち、金融機関の区分の契約だけを指定できる。それ以外は入力不正とする。契約の区分を、金融機関の区分から、金融機関でない区分に変えるときは、その契約が、他の契約の支払方法になっていないことを検査する（なっていれば入力不正）。支払方法の選択肢の取得（画面用）は、金融機関の区分の契約に限る。

#### パスワードの扱い（REQ-005、REQ-007、REQ-013、REQ-014）

- パスワードは、DB に平文で保存する。一覧、アカウント一覧、詳細、解約順、API キーの応答には、パスワードの値を含めない。含めるのは、設定されているかどうか（真偽）だけである。
- パスワードの値は、専用の取得の API で、1 件ずつ返す。この API は、Cookie（または `DEBUG_USER`）による認証だけを許し、API キーでは拒否する。
- 登録・更新でパスワードの値を受け付けるのは、Cookie（または `DEBUG_USER`）による認証のときだけとする。API キーで、パスワードの値を含む要求が来たときは、保存せず入力不正として拒否する。更新で、パスワードの項目が送られなかったときは、保存済みの値を変えない。
- 「パスワード未設定」は、ログイン方法にユーザ名とパスワードを選んでいて、パスワードの値がない契約を指す。一覧の絞り込みに使う。

#### 一覧・アカウント一覧

- キーワードは、名称・ホームページ・登録メールアドレス・ユーザ名・メモのいずれかに、大文字小文字を区別しない部分一致（`ILIKE`）で判定する。パスワードは対象にしない。空・空白のみは全件と同じ。アカウント一覧は、名称・ユーザ名・ホームページ・メモを対象にする。
- 区分、ステータス、契約の有無、パスワード未設定の絞り込みは、すべて満たすものを返す。
- 一覧の並び順は、名称の昇順（同名は ID 昇順）とする。
- アカウント一覧は、ユーザ名またはパスワードを持つ契約を対象にする（契約の有無、ステータスは問わない）。

#### 区分

- 区分は、利用者ごとに持つ。「その他」は、利用者が本機能を最初に使うときに、自動で用意する（区分の一覧の取得などの前に、なければ作る）。名称の変更と削除はできない。
- 区分の名称は、同じ利用者の中で重複できない。空白のみは不可。
- 区分は、金融機関かどうかの指定（真偽。既定は、金融機関ではない）を持つ。「その他」は金融機関にできない。金融機関の指定を外せるのは、その区分の契約を支払方法にしている契約（削除されていないもの）が無いときだけとする。
- 区分の削除は、その区分を使っている、削除されていない契約が 1 件もないときだけ可能とする。

#### 解約順

- 対象にできるのは、契約を伴う契約で、ステータスが有効または休止中のもの。対象の追加・除外・並べ替えは、画面の編集結果を、対象の契約の並び（先頭が最初に解約する契約）として保存する形にする。
- 取得時に、対象としての条件を満たさなくなった契約（ステータスが解約、削除、契約を伴わない）を、対象から外して返す。
- 警告は、取得時に算出する。ある契約 A が契約 B に依存していて、B が A より解約順で先にあるとき、その並びを警告として返す。警告があっても保存はできる。

#### 取り込み（REQ-010）

- `backend/scripts/import_password_management.py` が、`password_management.entries` の削除されていない行を、利用者ごとに、契約を伴わない契約として、`contract_management.contracts` に取り込む。名称←タイトル、ユーザ名←ユーザ名、パスワード←パスワード、ホームページ←サイトURL、メモ←メモ、区分は「その他」（なければ作る）、ステータスは有効、ログイン方法はユーザ名とパスワード。
- 取り込み元の行の ID を、取り込み先の契約に控え、同じ行を重複して取り込まない（何度実行してもよい）。取り込み元は変更しない。
- 取り込んだ件数、取り込めなかった件数と理由を、標準出力に出す。パスワード・ユーザ名の値は出さない。
- このスクリプトは、他機能の Python を import せず、DB の `password_management.entries` を直接読む。1 回限りの移行のための例外であり、通常の API からは `password_management` のデータを読まない。

#### ログ

- 操作が試みられたとき、次を契機として出力する（REQ-011）。
  - 入力された内容（名称、絞り込み条件、ID、区分名など。パスワード、ユーザ名、登録メールアドレス、2段階認証の送付先、API キー全体とそのハッシュ、セッション ID の値は出さない）
  - それを元にした判断結果（登録・更新・削除の成功、一覧の件数、解約順の保存、PDF 出力に使う取得）
  - 正常系ではない場合の理由（入力不正、対象なし、依存の循環、区分が使用中、未ログイン、権限なし、API キーで許可しない操作）
- API キーによる要求は、API キーの識別用の先頭部分と持ち主のユーザ名を出す。
- ログの 1 行はタイムスタンプ、区分、メッセージの順。区分は INF / WRN / ERR / DBG。
- 出力先は作業ディレクトリの `log/`。ファイルサイズでローテーションする。上限サイズは `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。いずれも `.env` から読む。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。

## 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。加えて、外部システム向けに API キー認証を受け付ける（`rules/14-security.md`）。

- すべての操作はログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログインとして扱う。割当なしは権限なしとして扱う。フロントは未ログインならログイン画面へ誘導する。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい。本番では空にする。その場合も、当該ユーザに本機能が割り当てられていることを判定する。
- API キーは、`Authorization` ヘッダ（Bearer）で受け取る。ヘッダがあるときは、API キーだけで判定し、失敗しても Cookie・`DEBUG_USER` には戻らない。`public.api_keys` を、キーの SHA-256 ハッシュで検索する。該当なし・失効済み・有効期限切れ・持ち主が論理削除済みは未ログイン、持ち主に本機能が割り当てられていない（または本機能が論理削除済み）は権限なしとする。許可したときは、持ち主として処理し、最終利用日時を更新する。セッションの期限は延ばさない。
- **API キーで許可する操作は、次に限る**（REQ-013）。契約の一覧・詳細の参照、契約の登録、契約の更新（いずれもパスワードの値を除く）、区分の一覧の参照、解約順の参照。それ以外の操作（契約の削除、パスワードの値の取得、区分の追加・変更・削除、解約順の保存、アカウント一覧、システム設定の取得以外の画面用の操作）は、API キーでは拒否する。許可する操作の対応は `api-design.md` に書く。
- 他機能の API を認証・利用可否判定に使わない。他機能の Python を import しない。

## 外部連携

- 外部システム（生成AI など）: API キーによる参照・登録・更新を受け付ける。MCP サーバ（別プロジェクト `mcp`）へのツールの追加は、本機能の API の承認後に別途行う（スコープ外）。
- `password-management`: 取り込みスクリプトが DB を直接読む。ほかの連携はなし。

## 未決事項

- PDF 出力の方式。ブラウザの印刷機能（PDF に保存）を使う設計とした（`note-management` と同じ）。ファイルを直接ダウンロードさせたい場合は、バックエンドで PDF を生成する方式に変える。
- API キーの対象機能に、本機能を加えること。`api-key-management` の要件・設計は、対象機能を 5 機能に限っている（その他は後で広げる）。本機能の API キー認証は、`public.api_keys` を直接読むので、`api-key-management` のコードの変更は要らない。ただし、その SPEC の記述を改訂するかは、別途決める。
- `password-management` の取り込みスクリプトが、DB を直接読むこと（1 回限りの移行の例外）。
