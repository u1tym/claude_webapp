# 機能: mail-notice（メール通知）

## 目的

スケジュール機能で「通知要」とされた予定・TODO について、開始の直前に所有者へメールで知らせる。画面は持たず、Python の処理として動かす。

## ユーザーストーリー

- 利用者として、通知要の予定や TODO の開始が近づいたらメールで知りたい。なぜなら、カレンダーを開いていなくても気づけるから。
- 運用者として、同じ予定・TODO を何度もメールしたくない。なぜなら、重複通知は迷惑だから。
- 運用者として、現在日から大きく遡った古い予定・TODO は判定から外したい。なぜなら、毎回見る対象を絞りたいから。

## 用語

| 用語 | 意味 |
|------|------|
| スケジュール | スケジュール機能が保持する一件。種別は「予定」または「TODO」。 |
| 予定 | 実施状態を持たないスケジュール。 |
| TODO | 実施済み／未実施を持つスケジュール。 |
| 日単位 | 年月日までで開始を持つ粒度。時刻は持たない。 |
| 時間単位 | 年月日時分までで開始を持つ粒度。秒は持たない。 |
| 通知要 | スケジュールに付いた指定のうち、通知が要であるもの。 |
| 開始日時 | 通知判定に使う日時。時間単位は開始日と開始時刻。日単位は開始日に、設定された時刻（未設定なら 9:00）を付けたものとみなす。 |
| 判定時刻 | 通知対象かどうかを判定するときの、日本標準時の現在時刻。 |
| 余裕分数 | 開始の何分前から通知対象にするか。設定値。未設定なら 3 分。 |
| 日単位みなし時刻 | 日単位の開始に付ける時刻。設定値。未設定なら 9:00。 |
| しきい時刻 | 判定時刻に余裕分数を足した時刻。開始日時がこれより前なら通知対象になり得る。 |
| 遡及日数 | 開始日が現在日から何日以上前ならチェック対象外とするか。設定値。未設定なら 30 日。 |
| 所有者 | そのスケジュールを持つユーザ。 |
| 通知済み | 当該スケジュールについて、本機能がメール送信に成功したこと。 |
| 本機能 | このメール通知機能そのもの。画面は持たない。 |
| ログ | 処理の入力、判断結果、正常系ではない場合の理由を、タイムスタンプと区分付きで残す記録。 |

## 要件

要件は EARS の意味を保ち、日本語の文で書く。画面部品、テーブル定義、API パス、HTTP ステータスなど設計は書かない。

### REQ-001

システムは画面を持たず、Python で通知対象の判定とメール送信を行うこと。利用者のログインやメニューからの起動は不要とすること。

#### 受け入れ条件

- [ ] 本機能に Web 画面は無い。
- [ ] Python の処理として、判定と送信を実行できる。
- [ ] 判定と送信に、利用者のログインは不要である。
- [ ] ポータルのメニューに本機能は載らない。

### REQ-002

システムは、スケジュールの参照にスケジュール機能が保持するデータを使い、宛先の参照に共通のユーザが持つメールアドレスを使うこと。本機能はそれらを複製しないこと。スケジュール機能が保持する項目は変更しないこと。

#### 受け入れ条件

- [ ] 予定・TODO の内容は、スケジュール機能が保持しているものを参照する。
- [ ] 宛先は、所有者のメールアドレスを参照する。
- [ ] 本機能は、ユーザやスケジュールを複製して持たない。
- [ ] スケジュール側に、通知済みを表す項目は追加しない。

### REQ-003

システムは、通知の実施記録を本機能側で保持すること。あるスケジュールを一度通知済みにしたあと、システムは当該スケジュールを再度通知対象にしないこと。

#### 受け入れ条件

- [ ] メール送信に成功したスケジュールは、通知済みとして残る。
- [ ] 通知済みのスケジュールは、開始日時がしきい時刻より前でも、再度メールしない。
- [ ] 開始日時や通知要不要をあとから変えても、通知済みなら再度メールしない。
- [ ] 通知済みの記録は、スケジュール機能の項目としては持たない。

### REQ-004

判定を行うとき、システムは次をすべて満たす TODO を通知対象とすること。論理削除されていない。通知要である。未実施である。開始日時がしきい時刻より前である。まだ通知済みでない。開始日が現在日から遡及日数以上前でない。

#### 受け入れ条件

- [ ] 論理削除された TODO は対象にしない。
- [ ] 通知不要の TODO は対象にしない。
- [ ] 実施済みの TODO は対象にしない。
- [ ] 開始日時がしきい時刻と同じ、またはそれより後の TODO は対象にしない。
- [ ] 未実施かつ上記を満たす TODO は対象にする。
- [ ] 通知済みの TODO は対象にしない。
- [ ] 開始日が現在日から遡及日数以上前の TODO は対象にしない。

### REQ-005

判定を行うとき、システムは次をすべて満たす予定を通知対象とすること。論理削除されていない。通知要である。開始日時がしきい時刻より前である。まだ通知済みでない。開始日が現在日から遡及日数以上前でない。実施状態は条件にしない。

#### 受け入れ条件

- [ ] 論理削除された予定は対象にしない。
- [ ] 通知不要の予定は対象にしない。
- [ ] 開始日時がしきい時刻と同じ、またはそれより後の予定は対象にしない。
- [ ] 上記を満たす予定は対象にする。実施状態の有無は見ない。
- [ ] 通知済みの予定は対象にしない。
- [ ] 開始日が現在日から遡及日数以上前の予定は対象にしない。

### REQ-006

時間単位のスケジュールについて、システムは開始日時を開始日と開始時刻（分まで）として扱うこと。日単位のスケジュールについて、システムは開始日時を開始日と日単位みなし時刻として扱うこと。しきい時刻は、判定時刻に余裕分数を足した時刻とすること。余裕分数と日単位みなし時刻は設定値から読み、未設定のときはそれぞれ 3 分と 9:00 とすること。コードに埋め込まないこと。判定は日本標準時で行うこと。

#### 受け入れ条件

- [ ] 時間単位は、開始日と開始時刻を組み合わせた日時で判定する。
- [ ] 日単位は、開始日に日単位みなし時刻を付けた日時で判定する。
- [ ] 日単位みなし時刻の設定が無いときは 9:00 とする。
- [ ] しきい時刻は、判定時刻に余裕分数を足した時刻である。
- [ ] 余裕分数の設定が無いときは 3 分とする。
- [ ] 余裕分数と日単位みなし時刻を設定で変えると、判定に使う値も変わる。
- [ ] 判定に使う日時の基準は日本標準時である。

### REQ-007

システムは、通知対象の各スケジュールについて、所有者のメールアドレスへメールを 1 通送ること。送信元と SMTP の接続先・認証は設定値から読むこと。コードに埋め込まないこと。

#### 受け入れ条件

- [ ] 通知対象 1 件につきメールは 1 通である。
- [ ] 宛先は所有者のメールアドレスである。
- [ ] メールには、少なくともタイトルと開始日時が含まれる。
- [ ] 日単位の開始日時は、開始日に日単位みなし時刻を付けて書く。未設定なら 9:00 とする。
- [ ] 送信元、SMTP の接続先、ポート、認証ユーザ、認証パスワードは設定から読む。
- [ ] 認証パスワードはログに出さない。

### REQ-008

所有者のメールアドレスが空のとき、または所有者が論理削除済みのとき、システムは当該スケジュールのメールを送らないこと。送らなかったものは通知済みにしないこと。

#### 受け入れ条件

- [ ] メールアドレスが空の所有者には送らない。
- [ ] 論理削除済みの所有者には送らない。
- [ ] 送らなかったスケジュールは、通知済みにならない。
- [ ] あとからメールアドレスが入ったときは、条件を満たせば対象になる。

### REQ-009

メール送信に失敗したとき、システムは当該スケジュールを通知済みにしないこと。他の通知対象の処理は続けること。

#### 受け入れ条件

- [ ] 送信失敗のスケジュールは、通知済みにならない。
- [ ] 次の判定で、条件を満たせば再度対象になる。
- [ ] ある件の失敗が、他の件の送信を止めない。

### REQ-010

システムは、判定と送信を繰り返し行えること。初回実行時に、しきい時刻より前でまだ通知済みでなく、開始日が現在日から遡及日数以上前でないものは対象とすること。

#### 受け入れ条件

- [ ] 判定と送信を、繰り返し実行できる。
- [ ] 開始が既に過ぎていても、未通知かつ開始日が遡及日数の範囲内なら対象になる。
- [ ] 一度成功したあとは、繰り返しても同じスケジュールを再送しない。

### REQ-011

判定または送信が試みられたとき、システムは当該試行の記録を log フォルダへ出力すること。

#### 受け入れ条件

- [ ] 判定の開始、対象の件数、各件の送信成否が log フォルダ配下のファイルに残る。
- [ ] 記録にはタイムスタンプが含まれる。
- [ ] 記録には区分（INF、WRN、ERR、DBG のいずれか）が含まれる。
- [ ] 記録には、入力のうち判断に使う値が含まれる。SMTP のパスワードは含まれない。
- [ ] 記録には判断結果（成功または失敗）が含まれる。
- [ ] 失敗のとき、内部理由が記録に含まれる。
- [ ] メールアドレスが空、所有者が論理削除済みなど、送らない判断も記録に残る。
- [ ] ファイルはサイズが大きくなったら新しいファイルへ切り替わる。

### REQ-012

判定を行うとき、システムは開始日が現在日から遡及日数以上前のスケジュールをチェック対象にしないこと。遡及日数は設定値から読み、未設定のときは 30 日とすること。コードに埋め込まないこと。対象外としたものは通知済みにしないこと。

#### 受け入れ条件

- [ ] 開始日が、現在日から遡及日数を引いた日と同じ、またはそれより前のスケジュールはチェックしない。
- [ ] 開始日が、現在日から遡及日数を引いた日より後のスケジュールは、他の条件を満たせば対象になる。
- [ ] 遡及日数の設定が無いときは 30 日とする。
- [ ] 遡及日数を設定で変えると、チェックする開始日の下限も変わる。
- [ ] チェック対象外としたスケジュールは、通知済みにならない。

## 非機能要件

- 本機能は認証しない。画面は無く、利用者の操作も無い。
- 本機能は `portal` および `schedule` の Python を import しない。ユーザとスケジュールは共通データおよびスケジュール機能のデータを直接参照する。機能スキーマへ複製しない。
- 通知済みの記録だけを本機能で保持する。スケジュール機能の保持項目は変えない。
- パスワード（SMTP 認証を含む）はログに出さない。
- 操作の記録は、入力された内容、それを元にした判断結果、正常系ではない場合の理由を契機として出力する。
- ログはファイルサイズでローテーションする。上限サイズと世代数は、機能の `.env` で指定する。コードに埋め込まない。
- SMTP の接続先、ポート、認証ユーザ、認証パスワード、送信元は `.env` で指定する。コードに埋め込まない。
- 余裕分数と日単位みなし時刻は `.env` で指定する。未設定のときはそれぞれ 3 分と 9:00 とする。コードに埋め込まない。
- 遡及日数は `.env` で指定する。未設定のときは 30 日とする。コードに埋め込まない。
- 日時の基準は日本標準時とする。

## 対象外

- Web 画面、フロントエンド
- ポータルへの機能登録、メニュー表示、ログイン
- スケジュールの登録・更新・削除・実施状態の変更（`schedule` が担う）
- ユーザのメールアドレスの登録・変更（`user-management` が担う）
- 通知要不要の指定そのもの（`schedule` が担う）
- 一度送ったメールの取り消し、再送の指示
- 複数宛先、CC、BCC、添付
- メール本文や件名を画面から編集すること
- 終了日時を基準にした通知
- プッシュ通知、SMS
