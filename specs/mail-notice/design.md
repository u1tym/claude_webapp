# 設計: mail-notice（メール通知）

## 概要

本設計は `requirements.md` の REQ-001〜REQ-012 を満たす。スケジュール機能で通知要とされた予定・TODO を、起動のたびに判定し、開始が近づいたものについて所有者へメールを送る。開始日が現在日から遡及日数以上前のものは見ない。一巡したらプロセスを終了する。繰り返しは、本アプリを再度起動して行う。画面は持たない。利用者のログインは不要で、ポータルのメニューにも載せない。宛先は `public` のユーザが持つメールアドレスを参照する。予定・TODO は `schedule` のデータを参照する。いずれも複製しない。通知済みの記録だけを本機能のスキーマに持つ。`schedule` の保持項目は変えない。SMTP と判定用の数値は `.env` から読む。操作の試行は、入力・判断結果・失敗時の内部理由を `log` フォルダへ残す。

画面毎の部品配置と画面遷移は `ui-design.md`、API のパス・要求・応答は `api-design.md`、テーブル定義と ER 図は `db-design.md` に書く。

## 構成

- フロントエンド: なし。`frontend` は置かない
- バックエンド: `src/features/mail-notice/backend` の venv で、コンソールアプリケーションとして起動する。HTTP サーバは使わない。起動したら判定と送信を 1 回行い、終了する
- API 基点: なし。HTTP API は持たない
- DB: 通知済みの記録はスキーマ `mail_notice`。ユーザはスキーマ `public`、スケジュールはスキーマ `schedule` を直接読む。機能スキーマへ複製しない。DDL は本機能の `backend` が持つ。詳細は `db-design.md`
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない
- 本機能の識別子: `mail-notice`。機能マスタへは登録しない

## バックエンド設計

### 起動

- 作業ディレクトリ: `src/features/mail-notice/backend`
- 仮想環境: `venv/`
- 起動: `python -m app`
- FastAPI と uvicorn は使わない。待ち受けポートは持たない
- 起動したら、通知対象を順に確認して条件に合うものへメールを送り、一巡したら終了する。プロセス内で待ち続けない
- 繰り返し判定したいときは、本アプリを再度起動する（タスクスケジューラなど）。間隔は運用で決める。余裕分数の既定が 3 分なので、それより短い間隔での起動を想定する

### モジュール構成

| ファイル | 役割 |
|----------|------|
| `app/main.py` | エントリポイント。ログの初期化と、判定・送信を 1 回実行して終了する |
| `app/__main__.py` | `python -m app` から `main` を起動する |
| `app/config.py` | `.env` から接続情報、SMTP、余裕分数、日単位みなし時刻、遡及日数、ログのローテーション設定を読む |
| `app/logger.py` | ファイルログの初期化と出力。サイズによるローテーション |
| `app/db.py` | PostgreSQL への接続 |
| `app/services/notice_service.py` | 判定時刻・しきい時刻の算出、通知対象の選定、1 件ずつの送信と通知済み記録。失敗しても次の件を続ける |
| `app/services/mail_service.py` | 設定の SMTP でメールを 1 通送る |
| `app/repos.py` | スケジュールとユーザの参照、通知済みの有無確認と追加 |
| `sql/` | スキーマ `mail_notice` の DDL |
| `log/` | ログファイルの出力先。リポジトリに含めない |

エンドポイントの契約は `api-design.md`。テーブルは `db-design.md`。

`portal` および `schedule` の Python を import しない。HTTP のルータは持たない。CORS は用いない。機能マスタとメニュー割当は参照しない。

### 業務ロジック

- 認証しない。ログイン中ユーザの特定も、機能の割当判定も行わない。
- 1 回の判定では、日本標準時の現在を判定時刻とする。しきい時刻は判定時刻に余裕分数を足した時刻とする。
- 余裕分数は `.env` の `NOTICE_LEAD_MINUTES`。未設定または空なら 3。正の整数でないときは 3 とし、その判断をログに残す。
- 日単位みなし時刻は `.env` の `NOTICE_DAY_TIME`。未設定または空なら `09:00`。`HH:MM`（分まで）として解釈できないときは `09:00` とし、その判断をログに残す。
- 遡及日数は `.env` の `NOTICE_LOOKBACK_DAYS`。未設定または空なら 30。正の整数でないときは 30 とし、その判断をログに残す。
- 開始日時は次のとおりとする。時間単位は開始日と開始時刻（分まで）。日単位は開始日に日単位みなし時刻を付けた日時。タイムゾーン付きの型は使わず、日本標準時として扱う。
- チェックする開始日の下限は、判定日（日本標準時の現在日）から遡及日数を引いた日とする。開始日が下限と同じ、またはそれより前の行は取得しない。通知済みにもしない。
- 通知対象は、スケジュール機能が保持する未削除かつ通知要の行のうち、開始日が下限より後で、開始日時がしきい時刻より前で、本機能に通知済みとして残っていないもの。TODO はさらに未実施であること。予定は実施状態を見ない。
- 所有者は当該スケジュールのユーザ ID に対応する `public` のユーザとする。論理削除済み、またはメールアドレスが空なら送らず、通知済みにもしない。
- 対象 1 件につきメールは 1 通。宛先は所有者のメールアドレス。件名に種別（予定または TODO）とタイトルを含める。本文にタイトルと開始日時を含める。日単位の開始日時は、開始日に日単位みなし時刻を付けて書く。
- SMTP は `.env` の `SMTP_HOST`、`SMTP_PORT`、`SMTP_USERNAME`、`SMTP_PASSWORD`、`SMTP_FROM` を使う。コードに埋め込まない。接続して認証し、送信元を `SMTP_FROM` として送る。
- 送信に成功したときだけ、当該スケジュールを通知済みとして本機能側に残す。`schedule` の行は更新しない。
- 送信に失敗したときは通知済みにしない。次の判定で条件を満たせば再度対象になる。ある件の失敗は他の件を止めない。
- 同じスケジュールを二重に送らないよう、通知済みの追加は既にあるときは送らない。同時に二つ起動しても、既に記録がある件は送らない。
- しきい時刻より前で未通知でも、開始日が下限より後のものだけを対象とする。開始が過ぎていても、下限より後なら対象とする。
- 判定または送信が試みられたとき、次を契機としてログへ出す。SMTP のパスワードは出さない。
  - 入力された内容（判定時刻、余裕分数、日単位みなし時刻、遡及日数、開始日の下限、しきい時刻、スケジュールの識別、種別、粒度、開始日時、所有者の識別、宛先の有無。パスワードは出さない）
  - それを元にした判断結果（対象にする／しない、送信成功、送らない、送信失敗）
  - 正常系ではない場合の理由（メールアドレス空、所有者論理削除済み、SMTP 失敗、設定値不正で既定を使った）
- ログの 1 行はタイムスタンプ、区分、メッセージの順とする。区分は INF（判定開始・対象件数・送信成功）、WRN（送らない判断、設定値不正で既定を使用）、ERR（想定外および SMTP 失敗）、DBG（調査用）とする。
- ログの出力先は作業ディレクトリの `log/`。ファイルサイズでローテーションする。上限サイズは `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。いずれも `.env` から読む。開発用の初期値は 10485760（10MB）と 5 世代。
