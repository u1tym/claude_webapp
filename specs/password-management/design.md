# 設計: password-management（パスワード管理）

## 概要

本設計は `requirements.md` の REQ-001〜REQ-008 を満たす。ログイン中の、本機能が割り当てられた利用者が、自分専用のパスワードエントリ（タイトル・ユーザ名・パスワード・サイトURL・メモ）を登録・編集・削除・一覧・検索・詳細表示できるようにする。ログインとメニューは `portal` が担う。本機能は `public` のユーザ・セッション・システム設定・機能マスタ・メニュー割当を参照し、複製しない。業務テーブル（パスワードエントリ）はスキーマ `password_management` に置く。操作の試行は、入力・判断結果・失敗時の内部理由を `log` フォルダへ残す。パスワードの値自体はログに残さない。

画面毎の部品配置と画面遷移は `ui-design.md`、API のパス・要求・応答は `api-design.md`、テーブル定義と ER 図は `db-design.md` に書く。

## 構成

- フロントエンド: `src/features/password-management/frontend` で Vue を起動。Vite `base` は `/portal_password_management/`。nginx では dist をドキュメントルートの `features/password-management/` に置き、公開 URL `/portal_password_management/` へ対応付ける
- バックエンド: `src/features/password-management/backend` の venv で uvicorn を起動
- API 基点: フロントの `VITE_API_PASSWORD_MANAGEMENT_URL`
- DB: 業務テーブル（パスワードエントリ）はスキーマ `password_management` に置く。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` を直接読む
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない
- 本機能の識別子: `password-management`（機能マスタの識別子。利用可否判定に用いる）

関連ドキュメント:

- UI設計: `ui-design.md`
- DB設計: `db-design.md`
- API設計: `api-design.md`

公開パスの基点は Vite `base`（`/portal_password_management/`）。Vue Router のルートは `/`。未ログインはシステム設定のログイン画面 URL へ誘導する。戻る先はシステム設定のメニュー画面 URL とする。

### コンポーネント

構成上の単位（ページ、共有部品）の名前と役割のみ。配置の詳細は `ui-design.md`。

| 名前 | 役割 |
|------|------|
| ルータ | 画面の切り替え（本機能は単一画面）。 |
| 殻 | ヘッダとナビ。他機能の部品は import しない。ナビは「パスワード管理」のみ。 |
| パスワード管理ページ | 検索欄、一覧、新規登録、詳細表示（マスク・表示切替・コピー）、編集フォーム、削除確認を持つ。 |

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 一覧・検索結果・選択中のエントリ・マスク表示の状態は画面内の状態とする。永続化しない。
- システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）は API から取得して画面内の状態とする。
- 開いた直後に一覧を取得する。検索キーワードの変更のたびに再取得する。

### バリデーション

- タイトル・ユーザ名は、空文字・空白のみを送信しない。
- パスワードは、空文字を送信しない（空白のみ・複数行は許容）。
- 失敗時は、内部理由が分からない一文のメッセージだけを示す。

### API クライアント

- 基点 URL: `import.meta.env.VITE_API_PASSWORD_MANAGEMENT_URL`
- API ホストをコードに直書きしない
- 呼び出し時は Cookie を含める（credentials）
- エンドポイントの契約は `api-design.md`

`portal` の Python を import しない。ログイン・ログアウトの API は持たない。利用可否は `public` の機能マスタとメニュー割当を本機能が読んで判定する。

### 業務ロジック

- すべての操作はログイン必須かつ、ログイン中ユーザに識別子 `password-management` の機能が割り当てられていること。論理削除済みのユーザまたは本機能は許可しない。
- 一覧・検索・単件取得・更新・削除は、常にログイン中ユーザ自身の `user_id` で絞り込む。他ユーザの行は対象にしない（存在しないものとして扱う）。
- タイトルの一意性は、同一 `user_id` の未削除（`is_deleted = false`）の行の中でだけ判定する。登録時・更新時ともに重複があれば失敗する。更新時は編集対象自身を除いて判定する。
- 削除は論理削除（`is_deleted = true`）とする。物理削除はしない。削除後、同じタイトルで新規登録できる（一意性判定が未削除の行だけを見るため）。
- 検索キーワードは、タイトル・ユーザ名・サイトURL・メモのいずれかに、大文字小文字を区別しない部分一致（`ILIKE`）で判定する。空・空白のみのキーワードは全件表示と同じ扱いにする。
- 一覧の並び順は登録順（ID昇順）とする。
- 操作が試みられたとき、次を契機としてログへ出す。パスワードとセッション ID は出さない。
  - 入力された内容（タイトル、検索キーワードなど。ユーザ名・パスワード・サイトURL・メモの値そのものはログに出さない）
  - それを元にした判断結果（登録・更新・削除の成功、一覧・検索の件数）
  - 正常系ではない場合の理由（タイトル重複、対象なし、入力不正、未ログイン、権限なし）
- ログの1行はタイムスタンプ、区分、メッセージの順とする。区分は INF（要求受付・成功）、WRN（想定内の失敗）、ERR（想定外）、DBG（調査用）とする。
- ログの出力先は作業ディレクトリの `log/`。ファイルサイズでローテーションする。上限サイズは `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。いずれも `.env` から読む。
- セッションの有効期間は `SESSION_TIMEOUT_MINUTES` 分。期限切れは未ログインとする。セッションの作成と破棄は本機能では行わない。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。
- システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）は `public` から読む。未ログインでもログイン画面 URL は取得できるようにする（未ログイン時の誘導に使う）。

### データアクセス

テーブル定義は `db-design.md`。ここにはアクセス関数の役割だけを書く。

| 対象 | 役割 |
|------|------|
| ユーザ | ID による取得（認証・認可）。業務データとしては更新しない |
| セッション | 参照。作成と破棄はしない。期限切れの扱いは未ログイン |
| システム設定 | キーによる取得 |
| 機能マスタ | 識別子による取得（本機能の利用可否）。更新しない |
| メニュー割当 | 指定ユーザに指定機能があるかの確認 |
| パスワードエントリ | 本人の未削除行の挿入・更新・論理削除・一覧・検索・単件取得・タイトル重複確認 |

### 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API はログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログインとして扱う。割当なしは権限なしとして扱う。フロントは未ログインならログイン画面へ誘導する。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい。本番では空にする。その場合も、当該ユーザに本機能が割り当てられていることを判定する。
- 他機能の API を認証・利用可否判定に使わない。
