# 設計: server-start（PC起動）

## 概要

本設計は `requirements.md` の REQ-001〜REQ-007 を満たす。ログイン中の、本機能が割り当てられた利用者が、決められた 1 台の起動対象について起動済みかどうかを確認し、起動を指示できるようにする。起動の成功は、本機能が保持する起動処理が正常に終わったこととし、その時点の ping は見ない。ログインとメニューは `portal` が担う。本機能は `public` のユーザ・セッション・システム設定・機能マスタ・メニュー割当を参照し、複製しない。業務テーブルは持たない。ping 先、MAC、待ち時間は `.env` から読む。操作の試行は、入力・判断結果・失敗時の内部理由を `log` フォルダへ残す。

画面毎の部品配置と画面遷移は `ui-design.md`、API のパス・要求・応答は `api-design.md`、テーブル定義と ER 図は `db-design.md` に書く。

## 構成

- フロントエンド: `src/features/server-start/frontend` で Vue を起動。Vite `base` は `/portal_server_start/`。nginx では dist をドキュメントルートの `features/server-start/` に置き、公開 URL `/portal_server_start/` へ対応付ける
- バックエンド: `src/features/server-start/backend` の venv で uvicorn を起動
- API 基点: フロントの `VITE_API_SERVER_START_URL`
- DB: 業務テーブルは持たない。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` を直接読む。機能スキーマは作らない
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない
- 本機能の識別子: `server-start`（機能マスタの識別子。利用可否判定に用いる）

関連ドキュメント:

- UI設計: `ui-design.md`
- DB設計: `db-design.md`
- API設計: `api-design.md`

公開パスの基点は Vite `base`（`/portal_server_start/`）。Vue Router のルートは `/`。未ログインはシステム設定のログイン画面 URL へ誘導する。戻る先はシステム設定のメニュー画面 URL とする。

### コンポーネント

構成上の単位（ページ、共有部品）の名前と役割のみ。配置の詳細は `ui-design.md`。

| 名前 | 役割 |
|------|------|

| PC起動ページ | 起動対象の状態表示、状態の再確認、起動の指示、起動済み時の警告と続行確認、成功／失敗の表示。 |

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 起動済み／未起動、起動処理の実行中、警告の表示中は画面内の状態とする。永続化しない。
- システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）は API から取得して画面内の状態とする。
- 開いた直後に状態を取得する。利用者が状態の確認を求めたときも再取得する。

### バリデーション

- 起動処理の実行中は、重ねて起動を指示しない。
- 起動対象が起動済みのとき、警告に対して利用者が続行しないあいだは、起動指示を送らない。
- 失敗時は、内部理由が分からない一文のメッセージだけを示す。

### API クライアント

- 基点 URL: `import.meta.env.VITE_API_SERVER_START_URL`
- API ホストをコードに直書きしない
- 呼び出し時は Cookie を含める（credentials）
- エンドポイントの契約は `api-design.md`

## バックエンド設計

### 起動

- 作業ディレクトリ: `src/features/server-start/backend`
- 仮想環境: `venv/`
- 起動: `uvicorn app.main:app --reload --port 8003`

### モジュール構成

| ファイル | 役割 |
|----------|------|
| `app/main.py` | FastAPI 生成、CORS 設定、ルータ登録、ログの初期化 |
| `app/config.py` | `.env` から接続情報、CORS、セッション有効期間、`DEBUG_USER`、ログのローテーション、ping 先、待ち時間、MAC を読む |
| `app/logger.py` | ファイルログの初期化と出力。サイズによるローテーション |
| `app/db.py` | PostgreSQL への接続 |
| `app/security.py` | セッション Cookie の参照 |
| `app/deps.py` | 要求からログイン中ユーザを特定し、本機能の割当を判定する。未ログイン・期限切れは未ログイン。割当なしは権限なし |
| `app/routers/power.py` | 起動対象の状態参照と起動指示 |
| `app/routers/settings.py` | システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）の取得。`public` を直接読む |
| `app/services/status_service.py` | ping による起動済み／未起動の判定 |
| `app/services/start_service.py` | 起動処理の実行。同時に 1 つだけ。本機能配下の Wake-on-LAN 処理を使う |
| `app/services/access_service.py` | 指定ユーザに指定機能が割り当てられているかの判定（本機能内） |
| `scripts/wol.py` | Magic Packet の送信。`sample/wol.py` 相当。MAC は引数で受け取る |
| `log/` | ログファイルの出力先。リポジトリに含めない |

エンドポイントの契約は `api-design.md`。テーブルは `db-design.md`。

`portal` の Python を import しない。ログイン・ログアウトの API は持たない。利用可否は `public` の機能マスタとメニュー割当を本機能が読んで判定する。

### 業務ロジック

- 状態参照と起動指示はログイン必須かつ、ログイン中ユーザに識別子 `server-start` の機能が割り当てられていること。論理削除済みのユーザまたは本機能は許可しない。
- ping 先は `.env` の `PING_HOST`。値は `192.168.2.178`。コードに埋め込まない。
- ping の待ち時間は `.env` の `PING_TIMEOUT_SECONDS`。値は `2`。コードに埋め込まない。
- MAC は `.env` の `WOL_MAC`。値は `D8:43:AE:82:D0:F1`。コードに埋め込まない。
- 状態判定は、OS の ping を 1 回実行する。待ち時間内に応答があれば起動済み、なければ未起動。ping コマンド自体が失敗したときも未起動とし、内部理由をログに残す。
- 起動処理は、同一 venv の Python で `scripts/wol.py` を実行し、設定の MAC へ Magic Packet を送る。終了コード 0 を正常終了とする。この判定に ping は使わない。
- 起動指示を受けたとき、バックエンドは起動済みかどうかを起動処理の可否には使わない。続行の確認はフロントが行う。起動済みでも未起動でも、指示があれば起動処理を実行する。
- 起動指示には、フロントが続行確認を経たかどうか（起動済みだったか）を含める。バックエンドは起動処理の成否と合わせてログに残す。利用者が続行しないときは起動指示を送らない（サーバログにキャンセルは残らない）。
- 起動処理の実行中は、新たな起動処理を開始しない。対象は利用者を問わない（起動対象が 1 台のため）。実行中の指示は失敗とし、内部理由をログに残す。フロントは実行中を画面状態で示し、重ねて送らない。
- 操作が試みられたとき、次を契機としてログへ出す。パスワードとセッション ID は出さない。
  - 入力された内容（ユーザ名、ping 先、待ち時間、MAC、続行確認を経たかどうか）
  - それを元にした判断結果（起動済み／未起動、起動処理の開始、成功、失敗、実行中のため拒否）
  - 正常系ではない場合の理由（ping 失敗、起動処理の終了コード、実行中、未ログイン、権限なし）
- ログの 1 行はタイムスタンプ、区分、メッセージの順とする。区分は INF（要求受付・成功）、WRN（想定内の失敗）、ERR（想定外）、DBG（調査用）とする。
- ログの出力先は作業ディレクトリの `log/`。ファイルサイズでローテーションする。上限サイズは `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。いずれも `.env` から読む。開発用の初期値は 10485760（10MB）と 5 世代。
- セッションの有効期間は `SESSION_TIMEOUT_MINUTES` 分。期限切れは未ログインとする。セッションの作成と破棄は本機能では行わない。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。
- システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）は `public` から読む。未ログインでもログイン画面 URL は取得できるようにする（未ログイン時の誘導に使う）。

### データアクセス

テーブル定義は `db-design.md`。ここにはアクセス関数の役割だけを書く。業務テーブルは無い。

| 対象 | 役割 |
|------|------|
| ユーザ | ID / ユーザ名による取得（認証・認可）。業務データとしては更新しない |
| セッション | 参照。作成と破棄はしない。期限切れの扱いは未ログイン |
| システム設定 | キーによる取得 |
| 機能マスタ | 識別子による取得（本機能の利用可否）。更新しない |
| メニュー割当 | 指定ユーザに指定機能があるかの確認 |

### 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API はログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログインとして扱う。割当なしは権限なしとして扱う。フロントは未ログインならログイン画面へ誘導する。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい。本番では空にする。その場合も、当該ユーザに本機能が割り当てられていることを判定する。
- 他機能の API を認証・利用可否判定に使わない。
