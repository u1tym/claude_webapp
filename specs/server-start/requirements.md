# 機能: server-start（PC起動）

## 目的

ログイン中の利用者が、決められた 1 台の起動対象について、起動済みかどうかを確認し、起動を指示できるようにする。起動の成功は、本機能が保持する起動処理が正常に終わったこととする。

## ユーザーストーリー

- 利用者として、対象の PC が起動済みかどうかを見たい。なぜなら、起動する必要があるか判断したいから。
- 利用者として、対象の PC の起動を指示したい。なぜなら、手元から起動したいから。
- 利用者として、すでに起動済みのときに起動を指示したら警告してほしい。なぜなら、誤って重ねて起動したくないから。
- 運用者として、起動の指示と判断結果を記録として残したい。なぜなら、誰が起動を試みたかを後から追えるようにしたいから。

## 用語

| 用語 | 意味 |
|------|------|
| 本機能 | この PC 起動機能そのもの。メニューへ載せる機能の一つである。識別子は `server-start`。 |
| 起動対象 | 本機能が扱う 1 台の機器。IP は `192.168.2.178`。画面から対象を増やしたり切り替えたりはしない。 |
| 起動済み | 起動対象へ ping したとき、待ち時間内に応答があった状態。 |
| 未起動 | 起動対象へ ping したとき、待ち時間内に応答がなかった状態。 |
| ping の待ち時間 | ping 1 回あたり待つ上限。2 秒とする。 |
| 起動処理 | 本機能が保持し、起動対象へ起動を指示する処理。MAC `D8:43:AE:82:D0:F1` へ Wake-on-LAN する。現行の `sample/do.bash` 相当を本機能配下へ移したもの。 |
| 起動の成功 | 起動処理が正常に終わったこと。この時点で ping が通っていなくても成功とする。 |
| 続行の確認 | 起動済みであるときに起動を指示した場合、警告のあと、利用者が実行してよいかを決めること。 |
| ログ | 操作の入力、判断結果、正常系ではない場合の理由を、タイムスタンプと区分付きで残す記録。画面へ出す文言とは別である。 |

## 要件

要件は EARS の意味を保ち、日本語の文で書く。画面部品、テーブル定義、API パス、HTTP ステータスなど設計は書かない。

### REQ-001

本機能を利用するとき、システムはログインを必須とし、ログイン中ユーザに本機能が割り当てられているときだけ利用を許可すること。

#### 受け入れ条件

- [ ] 未ログインでは、起動対象の状態参照も起動の指示もできない。
- [ ] 本機能が割り当てられていないログイン中ユーザは、状態参照も起動の指示もできない。
- [ ] 論理削除済みのユーザまたは本機能では、状態参照も起動の指示もできない。
- [ ] 判定は他機能の API に依存しない。

### REQ-002

ログイン中の、本機能が割り当てられた利用者が本機能を使うとき、システムは起動対象が起動済みか未起動かを示すこと。判定は、起動対象の IP への ping の応答の有無とすること。待ち時間内に応答がなければ未起動とすること。

#### 受け入れ条件

- [ ] ping に応答があれば起動済みと示す。
- [ ] ping の待ち時間内に応答がなければ未起動と示す。
- [ ] ping の待ち時間は 2 秒である。
- [ ] 状態は、画面を開いたとき、および利用者が状態の確認を求めたときに更新できる。

### REQ-003

ログイン中の、本機能が割り当てられた利用者が起動を指示し、起動対象が未起動のとき、システムは起動処理を実行すること。

#### 受け入れ条件

- [ ] 未起動であれば、続行の確認なしに起動処理を実行する。
- [ ] 起動処理は本機能が保持するものを使う。他機能の処理は使わない。
- [ ] 起動対象は 1 台であり、指示のたびに対象を選ぶ必要はない。

### REQ-004

ログイン中の、本機能が割り当てられた利用者が起動を指示し、起動対象が起動済みのとき、システムは警告し、利用者の続行の確認を経たときだけ起動処理を実行すること。

#### 受け入れ条件

- [ ] 起動済みのときは、警告を示す。
- [ ] 利用者が続行しないときは、起動処理を実行しない。
- [ ] 利用者が続行したときは、起動処理を実行する。

### REQ-005

起動処理が正常に終わったとき、システムは起動の成功として扱うこと。起動処理が正常に終わらなかったとき、システムは失敗として扱い、利用者に分かるようにすること。

#### 受け入れ条件

- [ ] 起動処理が正常終了すれば、その時点の ping 結果にかかわらず成功とする。
- [ ] 起動処理が失敗すれば、成功としない。
- [ ] 失敗時に画面へ出す文言は、内部の詳細な理由を含まない。内部理由はログにだけ残す。

### REQ-006

起動処理の実行中に、同じ利用者が再度起動を指示したとき、システムは重ねて起動処理を始めないこと。

#### 受け入れ条件

- [ ] 実行中は、新たな起動処理を開始しない。
- [ ] 実行中であることは利用者に分かる。
- [ ] 実行が終わったあと、再度起動を指示できる。

### REQ-007

システムは、状態参照と起動の指示について、入力された内容、それを元にした判断結果、正常系ではない場合の理由をログに残すこと。

#### 受け入れ条件

- [ ] 状態参照の要求と、起動済み／未起動の判断がログに残る。
- [ ] 起動の指示、起動済みかどうか、続行の確認の結果、起動処理の成功／失敗がログに残る。
- [ ] 失敗のときは内部理由がログに残る。
- [ ] パスワードとセッション ID はログに出ない。

## 非機能要件

- 本機能の利用には認証を必須とする。利用可否は、ログイン中ユーザに本機能が割り当てられているかで判定する。他機能の API は使わない。
- 本機能は `portal` の Python を import しない。ログイン画面は本機能では提供しない（`portal` でログインする）。
- 起動対象への ping と起動処理は、本機能のバックエンドが動作する環境から到達できることを前提とする。
- ping 先、MAC、ping の待ち時間は設定として持ち、コードに埋め込まない。値は ping 先 `192.168.2.178`、MAC `D8:43:AE:82:D0:F1`、待ち時間 2 秒とする。
- 操作の記録は、入力された内容、それを元にした判断結果、正常系ではない場合の理由を契機として出力する。
- ログはファイルサイズでローテーションする。上限サイズと世代数は、機能の `.env` で指定する。コードに埋め込まない。
- パスワードとセッション ID はログに出さない。
- 失敗時に画面へ出す文言は、内部の詳細な理由を含まない。内部理由はログにだけ残す。

## 対象外

- ログイン画面、メニュー画面（`portal` が担う）
- 本機能の初期登録（機能マスタへの追加と、利用者への割当は運用またはユーザ管理で行う）
- 起動対象の追加、削除、画面からの切替
- 停止、再起動
- 実機が起動し終えたことの確認（成功判定には使わない）
- 複数台の同時管理
- 起動処理の内容を画面から編集すること
