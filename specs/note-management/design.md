> API の詳細（パス・要求・応答・エラー）は書かない → `api-design.md`

## 全体構成

本設計は `requirements.md` の REQ-001〜REQ-018 を満たす。

- フロントエンド: `src/features/note-management/frontend` の Vue（SPA）。Vite `base` は `/portal_note_management/`。nginx では dist をドキュメントルートの `features/note-management/` に置き、公開 URL `/portal_note_management/` へ対応付ける。
- バックエンド: `src/features/note-management/backend` の別プロセスの FastAPI（venv、uvicorn）。開発時のポートは 8009、フロントの開発ポートは 5183（既存機能と重複しない値）。
- API 基点: フロントの `VITE_API_NOTE_MANAGEMENT_URL`。
- DB: 業務テーブル（フォルダ・ファイル・パーツ・過去世代・チェックリスト・カテゴリ・項目）はスキーマ `note_management` に置く。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` を直接読む（複製しない）。
- 業務データは、すべて利用者ごとに持つ（`user_id`）。共通のデータはない。
- 論理削除: フォルダ・ファイル・パーツは削除フラグで論理削除する。チェックリストのカテゴリ・項目も、削除フラグで論理削除する（復元の操作はない）。
- 画像・バイナリの中身は、Base64 の文字列のまま、パーツの行に持つ（過去世代も同じ）。API の応答では、ファイルの取得に中身を含めず、パーツ・過去世代ごとの取得（バイナリの応答）で返す。
- チェックリストは、パーツに紐づく別のテーブル（チェックリスト・カテゴリ・項目）で持つ。
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない。
- 本機能の識別子: `note-management`（機能マスタの識別子。利用可否判定に用いる）。
- 移行プログラム: バックエンドの `scripts/` に、コマンドラインのスクリプトとして置く。移行元 DB と移行先 DB へ同時に接続する。API サーバとは独立に動く。

```
ブラウザ ── SPA(Vue) ──(Cookie)──▶ FastAPI ──▶ PostgreSQL（移行先: public / note_management）
                                                        ▲
移行プログラム(scripts/) ── 読み取り ──▶ 移行元 DB       │ 書き込み
                       └─────────────────────────────────┘
```

関連ドキュメント: `requirements.md` / `ui-design.md` / `db-design.md` / `api-design.md`

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- ツリー（展開状態を含む）、入力中の内容、PDF 出力の選択は画面内の状態とする。永続化しない。
- システム設定（ログイン画面 URL、メニュー画面 URL、共通アイコン）は API から取得して保持する。

### フロントの責務

- ツリー: ルートフォルダを取得して表示し、フォルダの展開のたびに、その直下（フォルダとファイル）を取得する。削除済みを表示する切り替えのオン・オフで、取得し直す。
- 画像・バイナリ: 登録・差し替えは、選んだファイルを Base64 にして送る。表示・ダウンロードは、バイナリの応答の取得先（画像は `<img>` の参照先、ダウンロードはリンク）を使う。10 MB を超えるファイルは、送る前に断る（サーバ側でも検証する）。
- Markdown: `markdown-it` で HTML 化する。本文中の生の HTML は許可せず、リンクは http / https のものだけを開けるリンクにする。TeX: `katex` で組版する。組版に失敗したときは、ソースを、そのまま表示する。
- 行動予定・画像のマーカー・倍率の入力は、送信前に、サーバ側と同じ規則で検証する。失敗時は、内部理由が分からない一文だけを示す。
- チェックリスト: 操作（項目の追加・チェック・並び替えなど）のたびに、サーバへ送り、応答の最新の状態で表示を置き換える。ドラッグ操作に加え、上下の移動ボタンでも並び替えられる。
- PDF 出力: 出力対象のファイルを取得し、印刷用のレイアウト（画面には出さない領域）に組み立てて、ブラウザの印刷機能（`window.print()`）を呼ぶ。印刷用のレイアウトは、ファイル（複数のときは選択した順）ごとに、フォルダ名・タイトル・削除されていないパーツを並べる。複数ファイルのときは、ファイルごとの改ページの指定に従う。画像は、印刷用の領域の読み込みの完了を待ってから印刷する。

### 業務ロジック

#### 共通

- すべての操作は、ログイン必須かつ、ログイン中ユーザに本機能が割り当てられていること。
- すべての操作は、常にログイン中ユーザ自身の `user_id` で絞り込む。他ユーザの行は存在しないものとして扱う（親フォルダ・移動先・入れ替え対象の指定も同じ）。
- 名前・タイトルの必須項目は、前後の空白を除いた結果が空のときは入力不正とする。
- 同じ親の中の並び順は、親ごとに一意にする。新規の項目・移動・削除解除の衝突は、同じ親の中の最大値 + 1 とする。並び順の採番と入れ替えは、親の行（ルートはユーザ）を、トランザクション内でロックして、同時の操作でも重ならないようにする。入れ替えは、2 件の値を、同じトランザクションの中で交換する。

#### ツリーの一覧

- 指定したフォルダ（ルートを含む）の、直下のフォルダとファイルを、並び順の昇順で返す。ルートの直下にはフォルダだけがある。
- 各項目に、削除済みか（自身が削除済み、または祖先のいずれかが削除済み）を含める。削除済みを含めない指定のときは、削除済みの項目（祖先が削除済みのものを含む）を返さない。

#### フォルダ・ファイル

- 作成: 親（フォルダ）が存在し、本人のものであることを確認する（ファイルは、必ずフォルダの中）。同じ親の中に、削除されていない同名があるときは、失敗にする（DB の一意制約で判定し、同時の作成でも二重に作らない）。並び順は末尾。
- 名前・タイトルの変更: 削除されていないものだけが対象。同じ親の中の、削除されていない同名との重複は、自身を除いて判定する。
- 移動: 削除されていないものだけが対象。移動元の親が、指定と一致することを確認する。移動先に、削除されていない同名があるときは、失敗にする。フォルダは、自分自身と子孫の中へは移動できない（移動先の祖先をたどって判定する）。移動先の末尾に並べる。
- 並び順の入れ替え: 同じ親の中の、削除されていない 2 件が対象。
- 削除: 削除されていないものを、削除フラグを立てて論理削除する。子孫の行は変更しない（一覧の削除済みの判定で、祖先をたどって反映する）。
- 削除解除: 削除済みのものだけが対象。同じ親の中に、削除されていない同名があるときは、失敗にする。並び順が、同じ親の中の他の項目と重なるときは、末尾に付け直す。子孫の行は変更しない。
- 削除済み（祖先が削除済みで表示されているだけのものを含む）のファイルの、パーツの取得はできる。削除済みのファイル・フォルダに対する、名前・移動・並び替え、および削除済みのファイルのパーツの追加・編集・削除・並び替えは、失敗にする。ファイルが、祖先の削除で削除済みとして扱われる場合も、同じとする。

#### パーツ

- 取得: ファイルの取得は、ファイル・所属フォルダ名と、パーツ（並び順の昇順）を返す。削除済みのパーツを含めるかは、指定による。パーツには、画像・バイナリの中身を含めず、大きさと過去世代の一覧（世代番号・ファイル名・種別・保管の日時）を含める。テキスト・Markdown・TeX・URL・行動予定の本文は、含める。チェックリストは、識別子を返し、内容は、チェックリストの取得で返す。
- 追加: ファイルが存在し、削除済みとして扱われないことを確認し、末尾に追加する。種別ごとの検証を行う（下記）。チェックリストのときは、チェックリストを同じトランザクションで作る。
- 種別ごとの検証:
  - テキスト・Markdown・TeX・URL: 本文は空でもよい。
  - 行動予定: 本文は JSON。地点・経由メモ・時刻の規則を検証し、正規化して保存する（末尾の空地点の除去、末尾空白の除去）。
  - 画像・バイナリ: 中身（Base64）とファイル名が必須。デコードした大きさが上限（`PART_MAX_BYTES`）以下であること。画像は、タイトル（任意）、倍率（0.25〜4.0）、マーカー（100 個まで、位置は 0〜1、家は番号なし、番号は 1 以上、識別子は重複しない）を持つ。JPEG は JPEG、PNG は PNG の形式であることを、先頭のバイト列で確認する。
  - チェックリスト: 本文を持たない。
- 編集: 種別・本文・ファイル名・タイトル・倍率・マーカーを更新する。省略した項目は、現在の値を維持する。種別を、チェックリストへ、またはチェックリストから変更することは、失敗にする。種別を画像以外にしたときは、タイトル・倍率・マーカーを、空・1.0・空にする。
- 画像・バイナリの差し替え: 中身・種別・ファイル名のいずれかが変わるとき、更新前の内容を、過去世代として、世代番号（そのパーツの最大 + 1）で保存する（同じトランザクション）。保管数が `PARTS_MAX_REVISIONS` を超えるときは、古い世代から削除する。画像の中身を差し替えたときは、マーカーを空にする。タイトル・倍率・マーカーだけの変更では、世代を増やさない。
- 削除・削除解除: 削除フラグの切り替え。削除解除で並び順が重なるときは、末尾に付け直す。
- 並び順の入れ替え: 同じファイルの中の、削除されていない 2 件が対象。
- 画像・バイナリの取得: パーツまたは過去世代の中身を、バイナリで返す（画像は種別に応じた形式、バイナリは添付ファイルとして）。本人のものだけが対象。

#### チェックリスト

- 取得: タイトルと、削除されていないカテゴリ（並び順の昇順）、各カテゴリの削除されていない項目（並び順の昇順）を返す。無名カテゴリは、名前が空のカテゴリとして、識別できるようにする。
- 変更の操作（タイトルの更新、カテゴリの追加・名前変更・削除・並び替え、項目の追加・更新・削除・移動・並び替え）は、すべて、変更後の最新の状態（取得と同じ形）を返す。
- カテゴリの名前は、削除されていないカテゴリの間で、同じ名前を許さない（無名カテゴリは 1 つまで。DB の一意制約で判定）。名前が空のカテゴリは、項目をカテゴリ指定なしで追加したときに、無ければ自動で作る。
- カテゴリの削除は、そのカテゴリの項目も、同じトランザクションで論理削除する。
- 項目の移動は、移動先のカテゴリと、その中の位置を指定して、移動先・移動元の並び順を、付け直す。カテゴリの並び替えは、削除されていないカテゴリの全件の順を指定する。
- 復元の操作は持たない。

#### ログ

- 操作が試みられたとき、次を契機としてログへ出す。
  - 入力された内容（対象の識別子、名前・タイトル、種別、画像・バイナリの大きさ、パーツの個数など。パーツの本文・画像・ファイルの中身は出さない）
  - それを元にした判断結果（成功、一覧の件数）
  - 正常系ではない場合の理由（重複、対象なし、入力不正、規則違反、未ログイン、権限なし）
- 1 行はタイムスタンプ、区分、メッセージの順。区分は INF / WRN / ERR / DBG。出力先は `log/`。ファイルサイズでローテーションし、上限は `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。
- セッション ID、パスワード、Cookie は出さない。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。DB の失敗は、原因の先頭の 1 行をログにだけ残す（パスワードは含まれない）。

### 移行プログラム

移行元（既存のノート管理サービスの DB。スキーマ `note`、利用者は `public.accounts`）から、移行先（本機能の DB）へ、両方に同時に接続して直接移行する。実行場所は、本機能のバックエンドの venv が使え、両方の DB に到達できる環境。

- 配置: `backend/scripts/migrate_from_note.py`、手順書 `backend/scripts/README.md`。
- 接続:
  - 移行元: 引数（`--host` `--port` `--dbname` `--user` `--password`）または環境変数（`NOTE_DB_HOST` / `NOTE_DB_PORT` / `NOTE_DB_NAME` / `NOTE_DB_USER` / `NOTE_DB_PASSWORD`）。パスワードは画面・ログに出さない。読み取り専用のセッションで接続する。
  - 移行先: `backend/.env`（または `NOTE_MANAGEMENT_ENV_FILE` で指定した設定ファイル）。
  - どちらかの接続に失敗したときは、どちらかがわかるメッセージを表示して終了する。
- 引数: `--username`（必須。移行元のアカウント名であり、移行先の利用者名）、`--dry-run`（書き込まない）。
- 処理の流れ:
  1. 両方の DB に接続し、`--username` のアカウントを移行元の `accounts` から、同名の利用者を移行先の `public.users` から探す（移行先は論理削除済みは不可）。どちらかが無いときは、何も移行せずに、その旨を表示して終了する。
  2. そのアカウントのフォルダを、上位から順に（親が先になるように）、移行する。削除済みのものも移行する（削除済みの状態のまま）。
  3. ファイルを、フォルダの順・並び順の昇順に、1 件ずつ移行する（下記）。
  4. 結果を報告する。
- フォルダの移行: 移行先の同じ親の中に、同じ名前で、同じ削除状態のものがあるとき、移行済みとしてスキップし、その識別子を、子・ファイルの移行先の親として使う。同じ親の中に、同じ名前の削除済みが複数あるときは、移行先にある同じ名前の削除済みの個数が、移行元の何番目にあたるか（並び順の昇順）を上回るかで判定する。無いときは、移行元の並び順をそのまま用いて作成する（並び順が、移行先の既存のものと重なるときは、末尾に付け直す）。
- ファイルの移行（1 件を **1 つのトランザクション**）:
  - 移行済みの判定: フォルダと同じ規則（同じ親の中の、同じタイトル・同じ削除状態）。
  - ファイル、その全パーツ（種別・本文・ファイル名・タイトル・マーカー・倍率・削除フラグ・並び順は移行元の値）、画像・バイナリの過去世代（世代番号・ファイル名・種別・中身・保管の日時は移行元の値）、チェックリスト（タイトル）とその削除されていないカテゴリ・項目（名前・タイトル・チェック状態・並び順は移行元の値）を作る。チェックリストは、パーツに新しい識別子で紐づける。
  - 表のパーツは、移行しない（対象外として、フォルダの経路・ファイルのタイトル・パーツの並び順を記録する）。表のパーツの並び順は、欠番のまま残る。
  - チェックリストの削除済みのカテゴリ・項目は、移行しない（対象外として、件数を記録する）。
  - 種別の値が、想定外のパーツがあるときは、そのファイルを、失敗として記録する。
  - 最後に、移行先のパーツ・過去世代・チェックリストのカテゴリ・項目の数と、画像・バイナリの中身の一致（大きさと MD5 の照合）を、移行元（対象外を除く）と照合し、すべて一致したときだけ確定する。一致しない、または途中で失敗したときは、ロールバックして、そのファイルを失敗として記録する。次のファイルへ進む。
  - 識別子は移行先で新しく採番する。
- ドライラン: 移行元と移行先の読み取りだけを行い、対象の件数、スキップ、対象外を報告して終了する。
- 進捗: ファイル 1 件ごとに「n / 全体件数、フォルダの経路とタイトル」を標準エラー出力へ出す。
- 結果の報告: 種別（フォルダ・ファイル・パーツ・過去世代・チェックリスト）ごとに、移行・スキップ・対象外・失敗の件数と内訳を標準エラー出力へ出す。失敗が 1 件でもあれば、終了コードを 0 以外にする（接続の失敗・利用者なしは、別の終了コード）。
- 移行元へは書き込まない。移行プログラムの操作記録（開始・終了・失敗の理由）は、本機能のログ方針に従い `log/` にも出す（パスワード・パーツの中身は出さない）。

## 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API は、ログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログイン、割当なしは権限なしとして扱う。フロントは、未ログインならログイン画面へ誘導する。
- 画像・バイナリの取得（`<img>`・ダウンロードのリンク）は、ブラウザが Cookie を自動で送るため、同じ認証で判定する。フロントと API は、Cookie が送られる関係（同一サイト）で配置する。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい（当該ユーザへの本機能の割当は判定する）。本番では空にする。
- 他機能の API を認証・利用可否判定に使わない。
- 移行プログラムは、画面のログインを介さない。移行先の利用者は、ユーザ名の指定で決める。

## 外部連携

- 移行元のノート管理サービスの DB（`sample/note` の実運用 DB）。移行プログラムからだけ、読み取りで接続する。本機能の API サーバは、移行元へ接続しない。
- 上記以外の他システム・外部 API との連携はなし。

## デプロイ上の考慮（nginx）

- 公開 URL とディスク配置は `rules/17-nginx-deploy.md` に従う（`/portal_note_management/`、`features/note-management/`）。配置例は `frontend/nginx.example.conf` に書く。
- API を nginx 経由で公開するときは、画像・バイナリのアップロード（Base64 で、最大 約 14 MB）のため、リクエスト本文の上限（`client_max_body_size`）を 16 MB 以上にし、画像・バイナリの応答は、バッファリングせずに流す設定にする。
