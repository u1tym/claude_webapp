# 設計: room（ROOM）

## 概要

本設計は `requirements.md` の REQ-001〜REQ-013 を満たす。自室の機器（電灯、間接照明、屋内スピーカー、枕元スピーカー、玄関ドア）の状態を 1 枚の部屋の図で表示し、パーツのクリックと一括切替ボタンで状態を変える。実際の機器操作は、バックエンドが SwitchBot の Web API を呼んで行う。定期実行（毎日・曜日・祝日と時刻）の定義は画面から登録し、実行は `mail-notice` と同じく「1 回判定して終了するコンソール処理」をタスクスケジューラが毎分起動して行う。画面・API・定期実行は、バックエンド内の同じサービス層を使う。ログインとメニューは `portal` が担い、本機能は `public` のユーザ・セッション・システム設定・機能マスタ・メニュー割当・API キーを参照して複製しない。

画面毎の部品配置と画面遷移は `ui-design.md`、API のパス・要求・応答は `api-design.md`、テーブル定義と ER 図は `db-design.md` に書く。

## 全体構成

```
[ブラウザ: Vue SPA] --Cookie--> [FastAPI: room backend] --HTTPS(署名)--> [SwitchBot クラウド] --> 各機器
[AI(MCP)]          --APIキー--> [FastAPI: room backend]
[タスクスケジューラ] --毎分起動--> [定期実行ジョブ(コンソール)] --(同じサービス層)--> [SwitchBot クラウド]
                                         |
                                  [PostgreSQL: スキーマ room]
```

- フロントエンド: `src/features/room/frontend` で Vue を起動。Vite `base` は `/portal_room/`。nginx では dist をドキュメントルートの `features/room/` に置き、公開 URL `/portal_room/` へ対応付ける
- バックエンド（API）: `src/features/room/backend` の venv で uvicorn を起動。ポートは `8011`
- 定期実行ジョブ: 同じ `backend`（同じ venv、同じ `.env`）から、別プロセスのコンソールとして `python -m app.jobs` で起動する。HTTP サーバは使わない。起動したら判定と実行を 1 回行い、終了する
- API 基点: フロントの `VITE_API_ROOM_URL`
- DB: 定期実行の定義と実行の記録はスキーマ `room`。ユーザ、セッション、システム設定、機能マスタ、メニュー割当、API キーはスキーマ `public` を直接読む。機能スキーマへ複製しない。DDL は本機能の `backend` が持つ。機器の状態は DB に持たず、都度 SwitchBot から取得する（REQ-012）。詳細は `db-design.md`
- ログ: バックエンドの `log/` へファイル出力する。API とジョブは同じフォルダへ出し、行の中で出力元を区別する。テーブルには残さない
- 本機能の識別子: `room`（機能マスタの識別子。利用可否判定に用いる）

関連ドキュメント:

- UI設計: `ui-design.md`
- DB設計: `db-design.md`
- API設計: `api-design.md`

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 機器の状態と取得日時は、API から取得して画面内の状態とする。永続化しない。
- 取得中・切替中は画面内の状態として持ち、その間は重ねて更新・切替をできなくする。
- 定期実行の一覧は API から取得して画面内の状態とする。

### バリデーション

- 定期実行の送信前に、実行条件があること、曜日の指定なら 1 つ以上の曜日が選ばれていること、時刻が `HH:MM` の形式であること、実行内容が選ばれていること（一括切替なら 5 種のいずれか、機器の個別切替なら、機器と目標の状態）を確認する。満たさなければ送信しない。祝日の扱いと実行日の取り方は、曜日の指定のときだけ送り、毎日のときは送らない（既定の値になる）。
- 失敗時は、内部理由が分からない一文のメッセージだけを示す。

### API クライアント

- 基点 URL: `import.meta.env.VITE_API_ROOM_URL`
- API ホストをコードに直書きしない
- 呼び出し時は Cookie を含める（credentials）
- エンドポイントの契約は `api-design.md`

### 業務ロジック

- 機器は 5 つで固定とする。機器と SwitchBot の対応は次のとおり。SwitchBot の認証情報と機器の識別子は `.env` にだけ置き、コード・画面・応答・ログに出さない（REQ-012）。

  | 機器 | 実体 | 取り得る状態 | 操作 |
  |------|------|--------------|------|
  | 電灯 | 赤外線ライト（未実装） | OFF 固定 | 何もしない |
  | 間接照明 | プラグ（SPB汎） | ON / OFF | ON / OFF の指示 |
  | 屋内スピーカー | プラグ（SBPアンプ） | ON / OFF | ON / OFF の指示 |
  | 枕元スピーカー | プラグ（SBP枕スピーカー） | ON / OFF | ON / OFF の指示 |
  | 玄関ドア | スマートロック（ロックPro） | 施錠中 / 開錠中、電池残量 | 施錠・開錠の指示（電池残量は表示のみ） |

- **状態の取得**: 取得は、要求のたびに SwitchBot へ問い合わせる。キャッシュしない。4 機器（電灯を除く）を並行して問い合わせ、取得日時は問い合わせを終えた時刻（日本標準時）とする。ある機器の取得に失敗しても、他の機器の取得は続け、失敗した機器には「取得できなかった」ことを示す。状態を推測した値は返さない（REQ-001、REQ-012）。電灯は SwitchBot へ問い合わせず、常に OFF を返す（REQ-006）。
- **個別切替**: 対象は間接照明、屋内スピーカー、枕元スピーカー、玄関ドア。目標の状態（ON / OFF、施錠 / 開錠）を受け取って、SwitchBot へ指示する。成功したら、その機器の状態を取得し直して返す。実機は、指示してから状態に反映されるまで少し時間がかかるため、指示の直後には取得せず、`ROOM_SETTLE_SECONDS`（既定 5 秒）を上限に、1.5 秒おきに、目標の状態になるまで取り直す。上限までに目標の状態にならなければ、最後に取得した値を返す。指示の成功と取得し直した値が食い違うときは、取得した値を返す。失敗したら、状態は変えず失敗を返す。他の機器は変えない（REQ-004、REQ-005）。電灯への切替要求は、機器へ何も指示せず、OFF の状態を返す（REQ-006、REQ-011）。
- **玄関ドアの確認**: 施錠・開錠の確認は画面（フロント）の責務とする。API は確認済みの要求として受ける。API 単独で呼ばれた場合も、要求に目標の状態を明示的に含めるものとし、「反転」の指示は受けない（誤って逆に切り替えないため）。
- **一括切替**: 5 種の定義は、対象機器と目標状態の組とする（要件の用語表のとおり）。実行は、対象機器へ個別の指示を並行して行い、機器ごとの成否を集めて返す。成功した機器は元に戻さない。電灯が対象の指示は、何もせず OFF のままとする（このため電灯選択では間接照明の OFF だけが実行される）。お出かけは玄関ドアを対象に含めない。実行後は、各機器の最新の状態を取得し直して返す（REQ-007）。個別切替と同じく、指示が成功した機器が目標の状態になるまで、1.5 秒おきに（上限は `ROOM_SETTLE_SECONDS`）全機器を取り直す。定期実行は、結果を画面に返さないため、取り直さない。
- **定期実行の定義**: 次を持つ（REQ-008）。
  - 実行条件: `daily`（毎日）、`weekdays`（曜日の指定）のいずれか。
  - 曜日の指定のとき: 曜日（月曜から日曜のうち 1 つ以上）、祝日の扱い `holiday_mode`（`none` = 指定した曜日のみ、`include` = 祝日も実行、`exclude` = 祝日は実行しない。既定 `none`）、実行日の取り方 `day_shift`（`same` = 当日、`before` = の前の日、`after` = の次の日。既定 `same`）。毎日のときは、`none` と `same` に固定する。
  - 時刻（時と分、日本標準時）。
  - 実行内容 `action_type`: `scene`（一括切替。5 種のいずれか）、`device`（機器 1 つの個別切替。機器 = 電灯・間接照明・屋内スピーカー・枕元スピーカーのいずれかと、目標の状態 `on` / `off`）のいずれか。玄関ドアの施錠・開錠は選べない。1 つの定期実行が持つ実行内容は 1 つ。
  - 有効／無効。
- **定期実行の判定**: `python -m app.jobs` は、日本標準時の現在を判定時刻とする。有効な定期実行のうち、次をすべて満たすものを実行する。
  1. 予定の日付（実行日）が、実行条件に合う。毎日なら、常に合う。曜日の指定なら、「基準日」の判定（下記）に合う。
  2. 指定時刻が、判定時刻から `ROOM_SCHEDULE_GRACE_MINUTES` 分前までの範囲にある（既定 5 分。タスクスケジューラの起動の遅れを吸収するため）。
  3. 当該定期実行の同じ日の実行記録が、まだ無い。
- **基準日の判定**（曜日の指定のとき。REQ-009）: 実行日 `r` に対して、基準日の候補 `b` を、実行日の取り方で決める。`same` なら `b = r`、`before` なら `b = r の翌日`（翌日が基準日である日に実行する）、`after` なら `b = r の前日`（前日が基準日である日に実行する）。`b` が基準日かは、祝日の扱いで決める。`none` なら、`b` の曜日が指定した曜日。`include` なら、`b` の曜日が指定した曜日、または `b` が祝日。`exclude` なら、`b` の曜日が指定した曜日で、かつ `b` が祝日でない。実行日 `r` 自体は、曜日や祝日で絞り込まない。
- **重複実行の防止**: 実行記録を、定期実行と実行日の組で一意とする。実行の直前に記録を追加し、既にあるときは実行しない。2 つのジョブが同時に動いても、記録の追加に成功した 1 つだけが実行する（REQ-009）。
- **実行内容の実行**: 実行内容が `scene` なら、一括切替を実行する（実行後の取り直しはしない）。`device` なら、指定した機器へ、目標の状態を 1 回だけ指示する（個別切替と同じ指示。取り直しはしない）。電灯の個別切替は、機器へ何も指示せず、成功として扱う（未実装。失敗にしない）。
- **定期実行の失敗**: ある定期実行の実行が失敗しても、他の定期実行の判定と実行は続ける。実行の結果と、失敗した機器を、最終実行として当該定期実行に残す（REQ-010）。結果は、一括切替では、成功・一部失敗・失敗。機器の個別切替では、成功・失敗のみ（失敗のとき、失敗した機器は、その 1 つ）。
- **祝日**: `holiday_service` が日本の国民の祝日（振替休日を含む）かを判定する。ユーザ休日は扱わない。基準日の判定では、基準日の候補 `b` の日付を渡す。
- **通信の制限**: SwitchBot の上限は 1 日 10,000 リクエスト。状態の取得は 1 回あたり最大 4 件、個別切替は 1 件の指示と最大 4 件の取得（反映待ちの取り直しを含む）、一括切替は最大 4 件の指示と 4 件の取得の最大 4 回分。通常の利用では上限に当たらない。SwitchBot への各呼び出しにはタイムアウトを設け、自動で再試行しない（二重の指示を避けるため）。
- **ログ**: 操作が試みられたとき、次を契機としてログへ出す。SwitchBot の認証情報、機器の識別子、セッション ID、API キーは出さない（REQ-013）。
  - 入力された内容（対象の機器の名称、目標の状態、一括切替の種類、実行した主体（画面の利用者／API の利用者／定期実行）、定期実行の識別、定期実行の実行内容の種類と、基準日の判定に使った実行日・基準日の候補）
  - それを元にした判断結果（成功または失敗、機器ごとの成否、定期実行を実行する／しない）
  - 正常系ではない場合の理由（入力不正、対象なし、SwitchBot に接続できない、SwitchBot のエラー、実行記録が既にある、条件に合わない、未ログイン、権限なし）
- ログの 1 行はタイムスタンプ、区分、メッセージの順とする。区分は INF、WRN、ERR、DBG（`rules/16-logging.md`）。出力先は作業ディレクトリの `log/`。ファイルサイズでローテーションし、上限サイズは `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`（`.env`）。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。
- システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）は `public` から読む。未ログインでもログイン画面 URL は取得できるようにする。

| `ROOM_SCHEDULE_GRACE_MINUTES` | 定期実行の起動遅れの猶予。未設定または空なら 5。正の整数でないときは 5 とし、その判断をログに残す |
| `SWITCHBOT_TIMEOUT_SECONDS` | SwitchBot への呼び出しのタイムアウト。未設定なら 10 |
| `ROOM_SETTLE_SECONDS` | 機器を切り替えたあと、実機の反映を待って状態を取り直す最大の時間（秒）。未設定または空なら 5。0 以上の数で、0 は待たない。不正なときは 5 とし、その判断をログに残す。切替の応答は、最大でこの時間だけ遅くなる |

## 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API はログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログインとして扱う。割当なしは権限なしとして扱う。フロントは未ログインならログイン画面へ誘導する。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい。本番では空にする。その場合も、当該ユーザに本機能が割り当てられていることを判定する。
- 他機能の API を認証・利用可否判定に使わない。
- 機器の状態と定期実行は、利用者ごとのデータではなく、1 つの部屋に対するものである。割当を受けた利用者はすべて同じ部屋を見る（利用者は 1 人を想定する。要件の「スコープ外」のとおり、複数の部屋は扱わない）。定期実行の定義には、作成した利用者の ID を残す。

API キーによる認証も受け付ける（他システム連携用。AI（MCP）が使う。`specs/api-key-management/design.md` の「対象機能の認証の変更」と同じ方式）。

- 要求に `Authorization` ヘッダ（Bearer 方式）があるときは、API キーで判定する。無いときは上記の Cookie（または `DEBUG_USER`）で判定する。API キーの判定に失敗したとき、Cookie・`DEBUG_USER` へは戻らない。
- キーの SHA-256 ハッシュで `public.api_keys` を検索する。該当なし・失効済み・有効期限切れ・持ち主が論理削除済みは未ログインとする。持ち主に本機能が割り当てられていない、または本機能が論理削除済みのときは権限なしとする。
- 許可したときは、持ち主をログイン中ユーザとして処理し、最終利用日時を更新する。セッションの期限は延ばさない。
- 判定の結果をログに出す。API キー全体とそのハッシュは出さない。識別するときは識別用の先頭部分だけを出す。
- `api-key-management` の Python は import しない。

定期実行ジョブは、利用者のログインを必要としない。ジョブは `.env` の接続情報で DB に接続し、SwitchBot の認証情報で機器を操作する。

## 外部連携

- **SwitchBot Web API v1.1**（`https://api.switch-bot.com/v1.1`）: 機器の状態取得（`GET /devices/{id}/status`）と操作（`POST /devices/{id}/commands`）。認証は、ヘッダにトークン、タイムスタンプ（ミリ秒）、UUID の nonce、署名（`Base64(HMAC-SHA256(secret, token + t + nonce))` の大文字）を付ける。リクエストごとに署名を作り直す。
- **日本の祝日**: ライブラリ `jpholiday` で判定する。外部の祝日 API は呼ばない。
- **MCP サーバ**: 本機能の API を呼ぶ。MCP 側のツール追加は、本機能の設計・実装が承認されたあとに、`mcp` 側の SPEC を改訂して扱う（要件のスコープ外）。

## ルールの改訂

本設計は、API キー認証の対象機能として `room` を加える。`specs/api-key-management/design.md` の「対象機能の認証の変更」は、対象機能を `goods-management`、`expense-management`、`knowhow-management`、`schedule` と列挙している。`room` の追加は、`api-key-management` の要件・設計の改訂と再承認を伴う。本設計の承認とあわせて、`api-key-management` の改訂を扱う。
