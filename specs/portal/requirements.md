# 機能: portal（ログインとメニュー）

## 目的

利用者がユーザ名とパスワードでログインし、自分に割り当てられた機能へ進めるようにする。運用者はコマンドでユーザと機能の登録・割当を管理できる。

## ユーザーストーリー

- 利用者として、ユーザ名とパスワードでログインしたい。なぜなら、許可された機能だけを使いたいから。
- 利用者として、自分に割り当てられた機能の一覧から目的の機能へ進みたい。なぜなら、使う機能を迷わず選べるようにしたいから。
- 運用者として、コマンドでユーザと機能を登録し、利用者ごとに使える機能を割り当てたい。なぜなら、画面を経由せずに利用可否を整えたいから。
- 運用者として、ログインの試行内容と判断結果を記録として残したい。なぜなら、失敗の理由を後から追えるようにしたいから。
- 各機能の開発者として、その機能の表示が許されているかを判定したい。なぜなら、割り当てられていない利用者に機能を使わせたくないから。

## 用語

| 用語 | 意味 |
|------|------|
| ユーザ | ユーザ名とパスワードで識別される利用者。 |
| 機能 | 本システムが提供する個々の業務機能。識別子、タイトル、遷移先を持つ。アイコンは任意。 |
| メニュー | ログイン中のユーザに、割り当てられた機能を表示順で示す一覧。 |
| 割当 | あるユーザのメニューに、ある機能を載せる関係。表示順を持つ。 |
| 論理削除 | データを残したまま、以降の認証・表示・割当の対象外とすること。 |
| システム設定 | ログイン画面の URL、メニュー画面の URL、システム共通アイコンなど、機能をまたいで参照する値。 |
| システム共通アイコン | システム全体を表すアイコン、設定アイコン、戻るアイコン。 |
| 運用コマンド | データベース上のユーザ・機能・割当を操作するコマンドラインの道具。 |
| ログ | ログイン処理の入力、判断結果、正常系ではない場合の理由を、タイムスタンプと区分付きで残す記録。画面へ出す文言とは別である。 |

## 要件

要件は EARS の意味を保ち、日本語の文で書く。画面部品、テーブル定義、API パス、HTTP ステータスなど設計は書かない。

### REQ-001

システムは、ユーザをユーザ名とパスワードで管理すること。

#### 受け入れ条件

- [ ] ユーザを追加できる。
- [ ] 同じユーザ名のユーザを複数登録できない。
- [ ] パスワードは平文のまま保持されない。

### REQ-002

ユーザを削除するとき、システムは当該ユーザを論理削除すること。

#### 受け入れ条件

- [ ] 削除したユーザはユーザ一覧の対象外になる。
- [ ] 削除したユーザはログインできない。
- [ ] 削除後もユーザのデータは残る。

### REQ-003

システムは、ログインした利用者を以降の要求で特定できる状態を保持すること。

#### 受け入れ条件

- [ ] 正しい認証のあと、ログイン状態になる。
- [ ] ログイン状態は、同一利用者の後続の操作で参照できる。

### REQ-004

システムは、次のシステム設定を保持すること。ログイン画面の URL、メニュー画面の URL、システム全体を表すアイコン、設定アイコン、戻るアイコン。

#### 受け入れ条件

- [ ] 初期状態で上記の設定が登録されている。
- [ ] ログイン画面の URL とメニュー画面の URL を取得できる。
- [ ] 3 種のシステム共通アイコンを取得できる。

### REQ-005

システムは、アイコンをディスク上のファイルとしては置かず、データとして保持すること。

#### 受け入れ条件

- [ ] 機能のアイコンはデータとして保持される。
- [ ] システム共通アイコンはデータとして保持される。
- [ ] アイコン用のファイルをディスク上に配置しなくても、画面にアイコンを示せる。

### REQ-006

未削除のユーザが正しいユーザ名とパスワードを提示したとき、システムはログイン状態にし、メニュー画面へ誘導すること。

#### 受け入れ条件

- [ ] 正しいユーザ名とパスワードでログインできる。
- [ ] ログイン成功後、メニュー画面へ進む。

### REQ-007

ユーザ名またはパスワードが正しくないとき、または対象ユーザが論理削除済みのとき、システムはログインを拒否すること。

#### 受け入れ条件

- [ ] 誤ったパスワードではログインできない。
- [ ] 存在しないユーザ名ではログインできない。
- [ ] 論理削除済みのユーザではログインできない。
- [ ] 失敗時に、ユーザ名の有無など詳細な理由は示さない。

### REQ-008

ログイン中の利用者がログアウトするとき、システムはログイン状態を終了し、ログイン画面へ誘導すること。

#### 受け入れ条件

- [ ] ログアウト後はログイン状態ではない。
- [ ] ログアウト後はログイン画面へ進む。

### REQ-009

ログインしていない利用者がメニューを要求したとき、システムはメニューを見せず、ログイン画面へ誘導すること。

#### 受け入れ条件

- [ ] 未ログインではメニューの内容を見られない。
- [ ] 未ログインでメニューを要求するとログイン画面へ進む。

### REQ-010

システムは、機能を一意の識別子、タイトル、遷移先 URL、任意のアイコンで管理し、論理削除できること。

#### 受け入れ条件

- [ ] 運用コマンドで識別子を指定して機能を追加できる。
- [ ] アイコンは省略できる。省略したときはアイコンなしで登録する。
- [ ] 機能のタイトル、遷移先 URL、アイコンを更新できる。
- [ ] 同じ識別子の機能を複数登録できない。
- [ ] 削除した機能はメニューに出ない。
- [ ] 削除後も機能のデータは残る。

### REQ-011

システムは、ユーザごとに、メニューへ載せる機能と表示順を割り当てられること。

#### 受け入れ条件

- [ ] あるユーザのメニューへ、未削除の機能を割り当てられる。
- [ ] 割当ごとに表示順を持てる。
- [ ] あるユーザのメニューから、割り当てた機能を外せる。

### REQ-012

ログイン中の利用者がメニューを開いたとき、システムは当該利用者へ割り当て済みかつ未削除の機能を、表示順に示すこと。

#### 受け入れ条件

- [ ] 自分に割り当てられた未削除の機能だけが見える。
- [ ] 他ユーザへ割り当てられた機能は見えない。
- [ ] 表示順どおりに並ぶ。
- [ ] 論理削除済みの機能は、割当が残っていても見えない。

### REQ-013

利用者がメニュー上の機能を選んだとき、システムはその機能の遷移先へ誘導すること。

#### 受け入れ条件

- [ ] 選んだ機能の遷移先へ進める。

### REQ-014

システムは、機能の一覧とユーザへの割当を、他機能からも参照できる共通データとして保持すること。他機能は、自機能の処理のなかで当該データを参照し、表示が許されているかを判定できること。

#### 受け入れ条件

- [ ] 指定したユーザに、指定した機能が割り当てられているかを判定できる。
- [ ] 論理削除済みのユーザまたは機能は、許可されない。
- [ ] 判定は他機能の API に依存しない。

### REQ-015

運用者は運用コマンドで、削除されていないユーザの一覧を表示できること。

#### 受け入れ条件

- [ ] ユーザ名が一覧に出る。
- [ ] 論理削除済みのユーザは出ない。

### REQ-016

運用者は運用コマンドで、ユーザを追加できること。

#### 受け入れ条件

- [ ] ユーザ名とパスワードを指定して追加できる。
- [ ] 追加したユーザでログインできる。

### REQ-017

運用者は運用コマンドで、ユーザを論理削除できること。

#### 受け入れ条件

- [ ] 指定したユーザを論理削除できる。
- [ ] 存在しないユーザ、または既に論理削除済みのユーザを指定したときは失敗する。

### REQ-018

運用者は運用コマンドで、機能を追加・更新・論理削除できること。

#### 受け入れ条件

- [ ] 識別子、タイトル、遷移先 URL を指定して追加できる。アイコンは省略できる。
- [ ] アイコンを指定して追加できる。
- [ ] 既存機能のタイトル、遷移先 URL、アイコンを更新できる。
- [ ] 指定した機能を論理削除できる。
- [ ] 存在しない機能、または既に論理削除済みの機能の更新・削除は失敗する。

### REQ-019

運用者は運用コマンドで、ユーザのメニューへ機能を割り当て、また外すことができること。

#### 受け入れ条件

- [ ] 未削除のユーザへ、未削除の機能を表示順付きで割り当てられる。
- [ ] 既に割り当て済みの組み合わせを再度割り当てたときは失敗する。
- [ ] 割り当て済みの機能を、そのユーザのメニューから外せる。
- [ ] 割り当てていない組み合わせを外そうとしたときは失敗する。

### REQ-020

ログインが試みられたとき、システムは当該試行の記録を log フォルダへ出力すること。

#### 受け入れ条件

- [ ] ログインの試行が log フォルダ配下のファイルに残る。
- [ ] 記録にはタイムスタンプが含まれる。
- [ ] 記録には区分（INF、WRN、ERR、DBG のいずれか）が含まれる。
- [ ] 記録には、入力のうちユーザ名が含まれる。パスワードは含まれない。
- [ ] 記録には判断結果（成功または失敗）が含まれる。
- [ ] 失敗のとき、画面へ出さない内部理由が記録に含まれる。
- [ ] ファイルはサイズが大きくなったら新しいファイルへ切り替わる。

## 非機能要件

- ログイン後のメニュー表示には認証を必須とする。
- パスワードはハッシュ化して保存する。平文では保存しない。
- あるユーザのメニューは、そのユーザ自身の割当だけを対象とする。
- 運用コマンドは Web 画面を介さず、データベースを直接操作する。
- 機能の利用可否データはシステム共通とし、各機能が同じデータ源を参照できるようにする。スキーマは `public` とする（現行ルールの「`public` はユーザ・セッション・システム設定のみ」を、本要件の承認後に機能マスタとメニュー割当も含めるよう改訂する）。
- ログイン処理の記録は、入力された内容、それを元にした判断結果、正常系ではない場合の理由を契機として出力する。
- ログはファイルサイズでローテーションする。上限サイズと世代数は、機能の `.env` で指定する。コードに埋め込まない。
- パスワードとセッション ID はログに出さない。
- 失敗時に画面へ出す文言は、従来どおり詳細な理由を含まない（REQ-007）。内部理由はログにだけ残す。

## 対象外

- Web 画面からのユーザ管理、機能管理、割当管理
- パスワードの変更、リセット、有効期限
- ロールや画面単位より細かい権限
- システム設定を運用コマンドで変更すること
- 設定画面そのもの（設定アイコンは保持するが、本機能では設定画面を提供しない）

## 未決事項

- ログインとメニューを 1 機能 `portal` にまとめた。別機能に分ける場合は承認前に指示すること。
- ログアウト（REQ-008）は依頼に無かったが、ログイン状態を終える操作として含めている。不要なら対象外にする。
