# 設計: portal（ログインとメニュー）

## 概要

本設計は `requirements.md` の REQ-001〜REQ-020 を満たす。利用者がユーザ名とパスワードでログインし、自分に割り当てられた機能のメニューから遷移できるようにする。ユーザ・機能・割当の登録は運用コマンドが行う。Web 画面からのユーザ/機能管理は対象外とし、後続の別機能が同じ共通データを利用する前提とする。ログインの試行は、入力・判断結果・失敗時の内部理由を `log` フォルダへ残す。

画面毎の部品配置と画面遷移は `ui-design.md`、API のパス・要求・応答は `api-design.md`、テーブル定義と ER 図は `db-design.md` に書く。

## 構成

- フロントエンド: `src/features/portal/frontend` で Vue を起動。Vite `base` は `/portal/`。nginx では dist をドキュメントルートの `portal/` に置く
- バックエンド: `src/features/portal/backend` の venv で uvicorn を起動
- 運用コマンド: 同バックエンドの Python モジュールを、venv 上でコマンドとして実行する
- API 基点: フロントの `VITE_API_PORTAL_URL`
- DB: 本機能の固有スキーマは作らない。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` に置く。DDL と初期データは本機能の `backend` が持つ。詳細は `db-design.md`
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない。

関連ドキュメント:

- UI設計: `ui-design.md`
- DB設計: `db-design.md`
- API設計: `api-design.md`

## フロントエンド設計

### 画面

画面の一覧のみ（画面名、パス、役割）。部品配置と遷移の詳細は `ui-design.md`。

| 画面 | パス | 説明 |
|------|------|------|
| ログイン | `/portal/login` | ユーザ名とパスワードを入力してログインする。 |
| メニュー | `/portal/menu` | ログイン中ユーザに割り当てられた機能を表示し、遷移先へ進む。ログアウトできる。 |

公開パスの基点は Vite `base`（`/portal/`）。Vue Router のルートは `/login` と `/menu`。システム設定に登録するログイン画面 URL・メニュー画面 URL は、上記パスに対応する URL とする。

### コンポーネント

構成上の単位（ページ、共有部品）の名前と役割のみ。配置の詳細は `ui-design.md`。

| 名前 | 役割 |
|------|------|
| ルータ | 画面の切り替え。ヘッダ / ナビの殻は持たない。 |
| ログインページ | ロゴ、ユーザ名、パスワード、ログインボタン。 |
| メニューページ | 割当機能の一覧表示、機能への誘導、ログアウト。 |

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- ログイン入力は当該画面内の状態とする。
- メニューに出す機能の一覧は、表示のために取得して画面内の状態とする。他ユーザ分は持たない。
- ログイン画面のロゴはフロントの静的ファイルとして置く。
- 機能のアイコンは API から得たデータとして画面で示す。無いときは画像を出さずタイトルだけを示す。機能アイコン用の配信用ファイルはフロントに置かない。

### バリデーション

- ログイン実行前に、ユーザ名とパスワードが空でないことを確認する。空なら送信しない。
- 認証失敗時は、ユーザ名の有無が分からない一文のメッセージだけを示す。

### API クライアント

- 基点 URL: `import.meta.env.VITE_API_PORTAL_URL`
- API ホストをコードに直書きしない
- 呼び出し時は Cookie を含める（credentials）
- エンドポイントの契約は `api-design.md`

## バックエンド設計

### 起動

- 作業ディレクトリ: `src/features/portal/backend`
- 仮想環境: `venv/`
- 起動: `uvicorn app.main:app --reload --port 8000`
- 運用コマンド: 同じ venv と作業ディレクトリで、CLI モジュールを実行する

### モジュール構成

| ファイル | 役割 |
|----------|------|
| `app/main.py` | FastAPI 生成、CORS 設定、ルータ登録、ログの初期化 |
| `app/config.py` | `.env` から接続情報、CORS、セッション有効期間、`DEBUG_USER`、ログのローテーション設定を読む |
| `app/logger.py` | ファイルログの初期化と出力。サイズによるローテーション |
| `app/db.py` | PostgreSQL への接続 |
| `app/security.py` | パスワードのハッシュ化と比較、セッション Cookie の扱い |
| `app/deps.py` | 要求からログイン中ユーザを特定する。未ログイン・期限切れは未ログインとして扱う |
| `app/routers/auth.py` | ログインとログアウト |
| `app/routers/menu.py` | ログイン中ユーザのメニュー取得 |
| `app/routers/settings.py` | システム設定（URL とシステム共通アイコン）の取得 |
| `app/services/auth_service.py` | 認証、セッションの作成と破棄、論理削除ユーザの除外 |
| `app/services/menu_service.py` | 自ユーザの割当機能の抽出（未削除のみ、表示順） |
| `app/services/access_service.py` | 指定ユーザに指定機能が割り当てられているかの判定（本機能のメニュー表示に用いる） |
| `app/cli.py` | 運用コマンド（ユーザ・機能・割当の操作） |
| `sql/` | `public` の DDL とシステム設定の初期データ |
| `log/` | ログファイルの出力先。リポジトリに含めない |

エンドポイントの契約は `api-design.md`。テーブルは `db-design.md`。

他機能は本機能の Python を import しない。利用可否の判定は、各機能が `public` を読んで自ら実装する。本機能は他機能向けの判定 API を提供しない。

### 業務ロジック

- ユーザ追加時、パスワードは一方向ハッシュにして保存する。平文は残さない。
- ログインは、未削除ユーザのユーザ名で引き、ハッシュを照合する。成功ならセッションを作成する。失敗（ユーザなし、論理削除、パスワード不一致）は同じ扱いとし、詳細を返さない。内部理由はログに残す。
- ログインが試みられたとき、次を契機としてログへ出す。パスワードとセッション ID は出さない。
  - 入力された内容（ユーザ名）
  - それを元にした判断結果（成功または失敗）
  - 正常系ではない場合の理由（ユーザなし、論理削除、パスワード不一致、入力不正）
- ログの 1 行はタイムスタンプ、区分、メッセージの順とする。区分は INF（要求受付・成功）、WRN（想定内の失敗）、ERR（想定外）、DBG（調査用）とする。
- ログの出力先は作業ディレクトリの `log/`。ファイルサイズでローテーションする。上限サイズは `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。いずれも `.env` から読む。開発用の初期値は 10485760（10MB）と 5 世代。
- セッションの有効期間は `SESSION_TIMEOUT_MINUTES` 分。期限切れは未ログインとする。
- ログアウトは当該セッションを無効にする。
- メニューは、ログイン中ユーザの割当のうち、機能が未削除のものだけを表示順で返す。他ユーザの割当は読まない。アイコンが無い機能はタイトルだけを示す。
- 機能識別子は運用者が指定する文字列とし、他機能が利用可否を判定するときのキーにする。
- ユーザ削除・機能削除は論理削除とする。割当行は残してよい。メニューと認証の対象からは外す。
- 運用コマンドは Web を介さず DB を直接更新する。ユーザ一覧は未削除のみ。ユーザ追加はユーザ名とパスワード。機能追加は識別子・タイトル・遷移先 URL。アイコンは任意。機能更新はタイトル・遷移先 URL・アイコン。割当は未削除のユーザと未削除の機能に対して行い、表示順を持つ。重複割当、存在しない対象、既に論理削除済みの対象への操作は失敗とする。
- 運用コマンドがアイコンを受け取るときは、実行環境上の入力からバイト列を読み、DB に格納する。省略したときはアイコンなしとする。リポジトリに配信用の画像ファイルは置かない。
- 初期状態で、ログイン画面 URL、メニュー画面 URL、システム共通アイコン 3 種をシステム設定として登録する。

### データアクセス

テーブル定義は `db-design.md`。ここにはアクセス関数の役割だけを書く。

| 対象 | 役割 |
|------|------|
| ユーザ | 追加、未削除の一覧、ユーザ名による取得、論理削除。パスワードハッシュの保存と比較。 |
| セッション | 作成、参照、無効化。期限切れの扱いは未ログイン。 |
| システム設定 | キーによる取得。初期データの投入。 |
| 機能マスタ | 識別子による追加・更新・取得、論理削除。アイコンのバイト列の保存と取得。 |
| メニュー割当 | ユーザと機能の割当追加、削除、あるユーザの割当一覧（表示順）。 |

### 認証 / 認可

Cookie ベースのセッション認証を用いる。

- ログインは未認証で受け付ける。成功時にセッションを作成し、セッション ID を Cookie に載せる。セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- メニュー取得とログアウトはログイン必須。未ログインまたはセッション期限切れは未ログインとして扱う。フロントはログイン画面へ誘導する。
- メニューの内容は、ログイン中ユーザ自身の割当だけを対象とする。
- `DEBUG_USER` があるときだけ、認証せずそのユーザ名として処理してよい。本番では空にする。
- 他機能の認証・利用可否判定に、本機能の API は使わない。

## 未決事項

- Web でのユーザ/機能/割当管理は、後続の別機能とする。本設計の対象外。
- メニューから機能へ進むとき、キャッシュ回避のため遷移先に `?a=<乱数>` を付ける。機能マスタの URL が末尾スラッシュなし（例: `/portal_schedule`）だと、nginx が `/portal_schedule/` へ 301 する際にクエリを引き継がず、ブラウザの最終 URL から `?a=` が消える。フロントは付与できている（ログの `destination` に残る）。対応は未決。候補は、(1) 機能マスタの URL を末尾 `/` 付きの公開 URL にする、(2) フロントでスラッシュを付けてから `?a=` を付ける、(3) nginx の 301 を `$is_args$args` 付きにする。確認: 2026-09-01、`id=schedule`。nginx 側の注記は `.cursor/rules/17-nginx-deploy.mdc`。
