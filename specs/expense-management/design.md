## 全体構成

フロントエンド（Vue.js の SPA）と、別プロセスで動くバックエンド（FastAPI）が疎通する構成とする。ログインは `portal` 機能が担うが、本機能のバックエンドは Cookie のセッション ID を用いて、共有スキーマ `public`（ユーザ・セッション・機能マスタ・メニュー割当）を自ら参照し、ログイン中ユーザの特定と機能利用可否の判定を行う。業務データ（予算期間・予算項目・支出方法・支出記録）はスキーマ `expense_management` に置く。

本機能の識別子: `expense-management`（機能マスタの識別子。利用可否判定に用いる）

## フロントエンド設計

### 画面

画面の一覧のみ（画面名、パス、役割）。部品配置と遷移の詳細は `ui-design.md`。ログイン画面とメニュー画面は持たない。ヘッダ / ナビの殻を使う。

| 画面 | パス | 役割 |
|------|------|------|
| 支出記録 | `/portal_expense_management/` | 支出記録の一覧表示、登録、編集、削除。 |
| 予算管理 | `/portal_expense_management/budgets` | 予算期間（タイトル・開始日・終了日）の一覧表示、新規作成、複製元を選べる複製作成、更新。予算項目（項目名・金額・表示順・メモ）の登録・編集・削除。 |
| 支出方法管理 | `/portal_expense_management/payment-methods` | 支出方法（名称・締め日・支払月オフセット・支払日・ずらし方向・除外条件・表示順）の一覧表示、登録、編集、削除。 |
| 集計 | `/portal_expense_management/reports` | 予算対実績の集計を、利用日基準・支払発生月基準を切り替えて表示。 |

公開パスの基点は Vite `base`（`/portal_expense_management/`）。nginx では dist をドキュメントルートの `features/expense-management/` に置き、公開 URL `/portal_expense_management/` へ対応付ける。Vue Router のルートは `/`・`/budgets`・`/payment-methods`・`/reports`。未ログインはシステム設定のログイン画面 URL へ誘導する。戻る先はシステム設定のメニュー画面 URL とする。

### モジュール構成

- 起動方法: `src/features/expense-management/frontend/` で `npm run dev`
- 構成:
  - 画面ごとの Vue ページ（支出記録 / 予算管理 / 支出方法管理 / 集計）
  - ヘッダ・ナビ（`rules/15-ui-style.md` の殻。本機能の `frontend/` 内に実装し、他機能から流用しない）
  - API クライアント（`VITE_API_EXPENSE_MANAGEMENT_URL` を基点に、Cookie を含めて通信）
  - 各画面内で完結する表示状態（読込中 / 空 / エラー）の管理

## バックエンド設計

- 起動方法: `src/features/expense-management/backend/` で venv を有効化し `uvicorn app.main:app` を起動
- モジュール構成:

| ファイル | 役割 |
|----------|------|
| `app/main.py` | FastAPI 生成、CORS 設定、ルータ登録、ログ初期化 |
| `app/config.py` | `.env` から DB 接続情報、CORS、`DEBUG_USER`、`SESSION_TIMEOUT_MINUTES`、ログのローテーション設定を読む |
| `app/logger.py` | ファイルログの初期化と出力（サイズローテーション） |
| `app/db.py` | PostgreSQL への接続（`public` と `expense_management` の両方を参照） |
| `app/deps.py` | Cookie のセッション ID から `public` を参照してログイン中ユーザを特定する。未ログイン・期限切れは未ログイン扱い。`DEBUG_USER` 指定時は認証をスキップする。`Authorization` ヘッダ（Bearer）があるときは、`public.api_keys` を参照して API キーで判定し、許可時に最終利用日時を更新する |
| `app/access.py` | `public` の機能マスタ・メニュー割当を参照し、ログイン中ユーザに本機能が割り当てられているかを判定する |
| `app/routers/budget_periods.py` | 予算期間の一覧・作成・複製作成・更新 |
| `app/routers/budget_items.py` | 予算項目の登録・編集・削除 |
| `app/routers/payment_methods.py` | 支出方法の一覧・登録・編集・削除 |
| `app/routers/expenses.py` | 支出記録の一覧・登録・編集・削除 |
| `app/routers/reports.py` | 予算対実績の集計（利用日基準・支払発生月基準） |
| `app/services/budget_service.py` | 予算期間・予算項目の登録・更新、複製元を選べる複製ロジック、予算期間一覧に付与する金額合計（削除されていない予算項目の金額合計）の算出 |
| `app/services/payment_method_service.py` | 支出方法の登録・更新。締め日 0 のときの支払月オフセット・支払日の固定値自動設定、除外条件・ずらし方向の保持 |
| `app/services/closing_date_service.py` | 利用日が属する締め対象月（利用日が締め日以前なら当月、締め日より後なら翌月）を決定したうえで、締め日・支払日それぞれの基準値・除外条件・ずらし方向から、対象月の実際の締め日・実際の支払日を算出する（共通ロジック）。祝日判定には `jpholiday` を使う |
| `app/services/expense_service.py` | 支出記録の登録・更新・論理削除（削除フラグ）。支払日の自動算出（利用日・実際の締め日・支払月オフセット・実際の支払日から算出）と、自動算出の有効・無効フラグの保持 |
| `app/services/report_service.py` | 予算項目ごとの集計（利用日基準は支出記録の利用日、支払発生月基準は支出記録の支払日を用いる） |
| `sql/` | スキーマ `expense_management` の DDL |
| `log/` | ログファイルの出力先（リポジトリに含めない） |

- 業務ロジック:
  - 支出方法登録・更新時、締め日に 0 が指定された場合は支払月オフセット・支払日を即時支払を表す固定値に自動設定し、締め日用・支払日用のずらし方向・除外条件は保持しない。締め日が 1 以上の場合は、締め日用・支払日用それぞれのずらし方向（過去/未来）と 0 件以上の除外条件（特定の曜日、当月に存在しない日、または祝日）をあわせて保持する。
  - 実際の締め日の算出は、まず利用日が属する締め対象月を決める（利用日が締め日（基準値。当月に存在しない日はその月の末日とみなす）以前なら利用日と同じ月、締め日より後なら翌月）。実際の締め日・実際の支払日の算出（`app/services/closing_date_service.py`）は、対象の基準値（締め日または支払日）を起点に、対応する除外条件のいずれかに一致する間、対応するずらし方向に従って 1 日ずつずらし、いずれにも一致しなくなった日を実際の日とする。同一ロジックを締め日・支払日の双方に適用する。締め日 0（即時支払）は算出対象外とする。「祝日」は日本の国民の祝日を指し、`jpholiday` ライブラリで日付から判定する（DB には保存しない）。
  - 支出記録登録・更新時、利用日と選択された支出方法から実際の締め日を算出し、支払月オフセットを加えた月と、実際の支払日を組み合わせて支払日を自動算出する。ユーザが上書きした値があればそれを優先する。支払日の自動算出の有効・無効は支出記録とともに保存し、編集時はその保存値を初期状態として使う。
  - 予算期間一覧の取得時、各予算期間に属する、削除されていない予算項目の金額を合計し、予算期間ごとの金額合計としてあわせて返す。予算項目一覧（画面の詳細表示）の金額合計は、取得済みの予算項目からフロントエンドで算出して表示する（バックエンドの応答形式は変えない）。
  - 予算期間の複製作成時、ユーザが選んだ複製元の予算期間に属する予算項目（項目名・金額・表示順）を複製して新しい予算期間へ登録する。新しい予算期間のタイトル・開始日・終了日はユーザが入力した値を用いる。
  - 予算期間は、同一ユーザ内で期間が重なる状態で複数作成できる（重複チェックは行わない）。
  - 予算期間の更新時、タイトル・開始日・終了日を変更する。終了日が開始日より前なら拒否する。更新後も既存の予算期間との重なりチェックは行わない。ログイン中ユーザ本人が所有する予算期間だけを更新できる。予算項目の対応関係（`budget_period_id`）は変えない。
  - 集計（利用日基準）は、指定された予算期間内に利用日を持つ、削除フラグが立っていない支出記録を予算項目ごとに合計し、予算項目の金額と比較する。
  - 集計（支払発生月基準）は、指定された年月と支出記録の支払日の年月が一致する、削除フラグが立っていない支出記録を予算項目ごとに合計する。
  - 支出記録の削除は削除フラグを立てる論理削除とする。一覧・集計は削除フラグが立っていない支出記録だけを対象とする。
  - 業務データへのアクセスは、常にログイン中ユーザ自身が登録した予算期間・予算項目・支出方法・支出記録に限定する。

## 認証 / 認可

Cookie ベースのセッション認証を用いる。

- ログイン画面・ログイン処理・セッションの発行は `portal` 機能が行う。本機能は自らログイン画面を持たない。
- 本機能のバックエンドは、要求に含まれる Cookie のセッション ID をもとに、共有スキーマ `public`（ユーザ・セッション）を自ら参照してログイン中ユーザを特定する。`portal` の API は呼び出さない。
- 本機能のバックエンドは、`public` の機能マスタ・メニュー割当を自ら参照し、ログイン中ユーザに本機能が割り当てられているかを判定する。論理削除済みのユーザまたは機能は許可しない。
- 未ログインには 401、権限なし（機能未割当）には 403 を返す。
- `DEBUG_USER` が設定されているときのみ、認証をスキップし指定ユーザとして処理する。本番では空にする。

API キーによる認証も受け付ける（他システム連携用。詳細は `specs/api-key-management/design.md` の「対象機能の認証の変更」）。

- 要求に `Authorization` ヘッダ（Bearer 方式）があるときは、API キーで判定する。無いときは上記の Cookie（または `DEBUG_USER`）で判定する。API キーの判定に失敗したとき、Cookie・`DEBUG_USER` へは戻らない。
- キーの SHA-256 ハッシュで `public.api_keys` を検索する。該当なし・失効済み・有効期限切れ・持ち主が論理削除済みは未ログインとする。持ち主に本機能が割り当てられていない、または本機能が論理削除済みのときは権限なしとする（Cookie と同じ割当判定）。
- 許可したときは、持ち主をログイン中ユーザとして処理し、`public.api_keys` の最終利用日時を更新する。セッションの期限は延ばさない。以降の `user_id` による絞り込みは変わらない。
- 判定の結果（許可・拒否と理由、ユーザ名、API キーの識別子と識別用の先頭部分）をログに出す。API キー全体とそのハッシュは出さない。
- `api-key-management` の Python は import しない。
