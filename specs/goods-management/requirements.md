# 機能: goods-management（グッズ管理）

## 目的

ログイン中の利用者が、自分が応援する人物・アーティストに関連する商品（グッズ）を、人物・アーティスト・媒体で分類しながら登録・閲覧・編集・削除できるようにする。商品には画像を添付でき、所持済みかどうかも記録できる。

## 背景

別サーバで稼働している既存のグッズ管理サービス（`sample/goods` 配下にソースコードを保管）と同等の機能を、本プロジェクトの機能の一つとして実装する。渡されたソースコードおよび仕様書には、次の点で本プロジェクトの方針と差異があり、本要件で扱いを定め直す。

- 元アプリには認証・利用者の区別が一切なく、人物・アーティスト・媒体・商品はすべての利用者で共有されるデータだった。本機能では、`rules/14-security.md` の方針に従い、ログイン中ユーザごとにデータを分離する（利用者Aが登録した人物・アーティスト・媒体・商品は、利用者Bからは参照できない）。
- 元アプリには人物・アーティスト・媒体・商品のいずれにも削除機能がなかった。本機能ではすべてに論理削除を追加する。他のデータから参照されている間は削除できないようにする。
- 元アプリは商品につき画像1枚のみの実装だったが、データベースの設計は複数枚を想定していた。本機能ではこれを活かし、商品に複数枚の画像を登録できるようにする。
- 元アプリのフロントエンドには、人物・アーティスト・媒体それぞれの専用一覧画面のソースファイルが存在したが、実際の画面（ルーティング）からは使われていなかった。本機能では、実際に使われていた「人物→アーティスト→媒体の順に絞り込んで商品を一覧する画面」と「商品の追加・編集画面」を踏襲する。

既存サービスのデータは、別途作成する移行スクリプトで本機能のデータベースへ取り込む。

## ユーザーストーリー

- 利用者として、応援する人物・アーティスト・媒体で商品を分類して管理したい。なぜなら、収集した商品を整理して把握したいから。
- 利用者として、人物を選び、次にアーティスト、次に媒体と絞り込んで商品を探したい。なぜなら、件数が増えても目的の商品を見つけやすくしたいから。
- 利用者として、絞り込んだ商品一覧をさらにタイトルで検索したい。なぜなら、同じ媒体に多数の商品があっても素早く探したいから。
- 利用者として、商品に複数枚の写真を添付したい。なぜなら、パッケージと中身など複数の見た目を記録したいから。
- 利用者として、商品を所持済みかどうか記録したい。なぜなら、収集状況を把握したいから。
- 利用者として、不要になった人物・アーティスト・媒体・商品を削除したい。なぜなら、整理を保ちたいから。
- 利用者として、自分が登録した人物・アーティスト・媒体・商品だけを扱いたい。なぜなら、他人のデータを見せたくないから。

## 用語

| 用語 | 意味 |
|------|------|
| 人物 | 応援する対象となる個人。名称を持つ。商品一覧の絞り込みの起点になる。 |
| アーティスト | 人物が所属するグループ・ユニットなど。名称と、所属する人物（複数可）を持つ。 |
| 媒体 | 商品が属するシリーズ・作品・レーベルなどの分類。名称を持つ。 |
| 商品 | 収集対象のグッズ本体。媒体・アーティストへの紐付け、タイトル、リリース日、メモ、所持フラグ、品番、画像（複数可）を持つ。 |
| 商品画像 | 商品に添付する画像。1件の商品に複数登録できる。 |

## 要件

要件は EARS の意味を保ち、日本語の文で書く。画面部品、テーブル定義、API パス、HTTP ステータスなど設計は書かない。

### REQ-001

本機能を利用するとき、システムはログインを必須とし、ログイン中ユーザに本機能が割り当てられているときだけ利用を許可すること。ただし、有効な API キーを添えた要求は、その API キーの持ち主がログインしているものとして扱うこと（API キーの発行・失効は `api-key-management` が担う）。

#### 受け入れ条件

- [ ] 未ログインでは、人物・アーティスト・媒体・商品の参照も操作もできない。
- [ ] 本機能が割り当てられていないログイン中ユーザは、参照も操作もできない。
- [ ] 論理削除済みのユーザまたは本機能では、参照も操作もできない。
- [ ] 判定は他機能の API に依存しない。
- [ ] 有効な API キーを添えた要求は、ログインしなくても、その持ち主として参照・操作できる。扱えるのは持ち主本人のデータだけである。
- [ ] 無効な API キー（存在しない、失効済み、有効期限切れ、持ち主が論理削除済み）を添えた要求は、未ログインとして扱う。
- [ ] API キーの持ち主に本機能が割り当てられていないときは、参照も操作もできない。

### REQ-002

システムは常に、ログイン中ユーザ本人が登録した人物・アーティスト・媒体・商品だけを参照・操作の対象とすること。他の利用者が登録したものは、参照も操作もできないこと。

#### 受け入れ条件

- [ ] 一覧・詳細取得・登録・変更・削除は、操作しているユーザ本人が登録したものだけを対象にする。
- [ ] 他ユーザが登録した人物・アーティスト・媒体・商品の ID を直接指定しても、参照・操作できない。

### REQ-003

ログイン中の利用者が人物を登録するとき、システムは名称を受け付けること。

#### 受け入れ条件

- [ ] 名称を入力して人物を登録できる。
- [ ] 名称は、空文字・空白のみは登録できない。

### REQ-004

システムは常に、ログイン中ユーザ本人が登録した、削除されていない人物を一覧表示すること。

#### 受け入れ条件

- [ ] 未削除の人物が一覧表示できる。
- [ ] 削除済みの人物は一覧に出ない。

### REQ-005

#### 受け入れ条件

- [ ] 人物の名称を変更できる。
- [ ] 存在しない、または既に論理削除済みの人物の変更は失敗する。

### REQ-006

ログイン中の利用者が登録済みの人物を削除するとき、システムは論理削除すること。ただし、その人物がいずれかのアーティストに紐付いている場合は削除できないこと。

#### 受け入れ条件

- [ ] どのアーティストにも紐付いていない人物は削除できる。削除後は一覧に出ない。
- [ ] 削除しても記録は残り、削除フラグが立った状態になる。
- [ ] いずれかの未削除のアーティストに紐付いている人物の削除は失敗する。
- [ ] 存在しない、または既に論理削除済みの人物の削除は失敗する。

### REQ-007

- [ ] 名称は、空文字・空白のみは登録できない。
- [ ] 登録時に、所属する人物を0件以上指定できる。
- [ ] 指定した人物が、存在しない、削除済み、または他ユーザのものであるときは登録に失敗する。

### REQ-010

- [ ] 追加しようとする人物が、存在しない、削除済み、または他ユーザのものであるときは変更に失敗する。
- [ ] 存在しない、または既に論理削除済みのアーティストの変更は失敗する。

### REQ-011

ログイン中の利用者が登録済みのアーティストを削除するとき、システムは論理削除すること。ただし、そのアーティストを参照する商品が存在する場合は削除できないこと。

#### 受け入れ条件

- [ ] どの商品からも参照されていないアーティストは削除できる。削除後は一覧に出ない。
- [ ] 削除しても記録は残り、削除フラグが立った状態になる。
- [ ] いずれかの未削除の商品から参照されているアーティストの削除は失敗する。
- [ ] 削除しても、そのアーティストと人物との関連付け自体は保持される（参照制約の判定にのみ影響する）。
- [ ] 存在しない、または既に論理削除済みのアーティストの削除は失敗する。

### REQ-016

ログイン中の利用者が人物を1件選んだとき、システムはその人物が紐付くアーティスト、およびそれらのアーティストの商品が属する媒体を、それぞれ一覧表示すること。

#### 受け入れ条件

- [ ] 指定した人物に紐付く未削除のアーティストを一覧表示できる。
- [ ] 指定した人物に紐付くアーティストの、削除されていない商品が属する媒体を、重複なく一覧表示できる。
- [ ] 指定した人物が存在しない、削除済み、または他ユーザのものであるときは失敗する。

### REQ-017

ログイン中の利用者が人物を選んだ上で、アーティスト（すべて、または1件）と媒体（すべて、または1件）を選んだとき、システムは条件に合致する削除されていない商品を一覧表示すること。

#### 受け入れ条件

- [ ] 人物のみを条件にすると、その人物に紐付く全アーティストの商品のうち、選んだ媒体条件に合う商品が一覧表示される。
- [ ] アーティストを1件に絞ると、その人物かつそのアーティストの商品に絞り込まれる。
- [ ] 媒体を1件に絞ると、その媒体の商品に絞り込まれる。
- [ ] 一覧には、商品のタイトル・アーティスト名・媒体名・リリース日・所持フラグ・代表画像を含む。
- [ ] 削除済みの商品は一覧に出ない。
- [ ] 条件に指定した人物・アーティスト・媒体が、存在しない、削除済み、または他ユーザのものであるときは失敗する。

- [ ] 大文字小文字を区別しない。

### REQ-020

ログイン中の利用者が商品を登録するとき、システムは媒体・アーティスト・タイトルを必須で受け付け、リリース日・メモ・所持フラグ・品番・画像（0枚以上）を任意で受け付けること。

#### 受け入れ条件

- [ ] 媒体・アーティスト・タイトルを指定して商品を登録できる。
- [ ] タイトルは、空文字・空白のみは登録できない。
- [ ] 指定した媒体またはアーティストが、存在しない、削除済み、または他ユーザのものであるときは登録に失敗する。
- [ ] リリース日を指定しない場合は、登録日を設定する。
- [ ] 所持フラグを指定しない場合は「未所持」として登録する。
- [ ] 登録時に画像を0枚以上添付できる。

- [ ] タイトルの必須・空文字の扱いは登録時と同じ。
- [ ] 変更先の媒体またはアーティストが、存在しない、削除済み、または他ユーザのものであるときは変更に失敗する。
- [ ] 存在しない、または既に論理削除済みの商品の編集は失敗する。

### REQ-022

ログイン中の利用者が登録済みの商品に画像を追加するとき、システムは既存の画像を残したまま新しい画像を追加できること。また、登録済みの画像を個別に削除できること。

#### 受け入れ条件

- [ ] 商品に画像を追加できる。上限枚数は設けない。
- [ ] 商品に登録済みの画像を1枚選んで削除できる。
- [ ] 存在しない、または既に論理削除済みの商品、および存在しない画像への操作は失敗する。

### REQ-023

ログイン中の利用者が登録済みの商品を削除するとき、システムは論理削除すること。

#### 受け入れ条件

- [ ] 商品を削除できる。削除後は一覧・詳細取得の対象外になる。
- [ ] 削除しても記録は残り、削除フラグが立った状態になる。
- [ ] 商品を削除しても、添付されていた画像の記録は保持される。
- [ ] 存在しない、または既に論理削除済みの商品の削除は失敗する。

### REQ-024

システムは、人物・アーティスト・媒体・商品の登録・変更・削除・参照の試行について、入力された内容、それを元にした判断結果、正常系ではない場合の理由をログに残すこと。

#### 受け入れ条件

- [ ] 登録・変更・削除・一覧取得・詳細取得の試行と成否がログに残る。
- [ ] 失敗のときは内部理由がログに残る。
- [ ] セッション ID はログに出ない。
- [ ] 画像データそのもの（バイナリ・Base64文字列）はログに出ない。

## 非機能要件

- 本機能の利用には認証を必須とする。利用可否は、ログイン中ユーザに本機能が割り当てられているかで判定する。他機能の API は使わない。他システム連携のため、`api-key-management` が発行した API キーによる認証も受け付ける。その場合の利用可否は、API キーの持ち主に本機能が割り当てられているかで判定する。
- 人物・アーティスト・媒体・商品は、ログイン中ユーザ本人が登録したものだけを扱う。他ユーザのデータは参照させない。
- 本機能は `portal` の Python を import しない。ログイン画面は本機能では提供しない（`portal` でログインする）。
- 操作の記録は、入力された内容、それを元にした判断結果、正常系ではない場合の理由を契機として出力する。
- ログはファイルサイズでローテーションする。上限サイズと世代数は、機能の `.env` で指定する。コードに埋め込まない。
- 失敗時に画面へ出す文言は、内部の詳細な理由を含まない。内部理由はログにだけ残す。

## 対象外

- ログイン画面、メニュー画面（`portal` が担う）
- 人物・アーティスト・媒体・商品の共有（他利用者への公開・閲覧許可）
- 変更履歴・バージョン管理
- 商品画像同士の表示順の入れ替え（登録順の表示のみとし、並び替えは対象外とする）
- 人物・アーティスト・媒体の名称の重複可否の制御（元アプリに重複禁止の仕組みがなく、本要件でも設けない）
- 本機能の初期登録（機能マスタへの追加と、利用者への割当はユーザ管理で行う）
- 別サーバ版からのデータ移行そのもの（移行スクリプトは本要件定義の対象外とし、別途作成する）
