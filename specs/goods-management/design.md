# 設計: goods-management（グッズ管理）

## 概要

本設計は `requirements.md` の REQ-001〜REQ-024 を満たす。ログイン中の、本機能が割り当てられた利用者が、自分専用の人物・アーティスト・媒体・商品を登録・変更・削除・一覧・詳細表示できるようにする。ログインとメニューは `portal` が担う。本機能は `public` のユーザ・セッション・システム設定・機能マスタ・メニュー割当を参照し、複製しない。業務テーブル（人物・アーティスト・媒体・商品・商品画像・アーティストと人物の関連）はスキーマ `goods_management` に置く。操作の試行は、入力・判断結果・失敗時の内部理由を `log` フォルダへ残す。

画面毎の部品配置と画面遷移は `ui-design.md`、API のパス・要求・応答は `api-design.md`、テーブル定義と ER 図は `db-design.md` に書く。

## 構成

- フロントエンド: `src/features/goods-management/frontend` で Vue を起動。Vite `base` は `/portal_goods_management/`。nginx では dist をドキュメントルートの `features/goods-management/` に置き、公開 URL `/portal_goods_management/` へ対応付ける
- バックエンド: `src/features/goods-management/backend` の venv で uvicorn を起動
- API 基点: フロントの `VITE_API_GOODS_MANAGEMENT_URL`
- DB: 業務テーブル（人物・アーティスト・媒体・商品・商品画像・アーティストと人物の関連）はスキーマ `goods_management` に置く。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` を直接読む
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない
- 本機能の識別子: `goods-management`（機能マスタの識別子。利用可否判定に用いる）

関連ドキュメント:

- UI設計: `ui-design.md`
- DB設計: `db-design.md`
- API設計: `api-design.md`

## フロントエンド設計

画面の一覧のみ（画面名、パス、役割）。部品配置と遷移の詳細は `ui-design.md`。ログイン画面とメニュー画面は持たない。ヘッダ / ナビの殻を使う。

| 画面 | パス | 説明 |

公開パスの基点は Vite `base`（`/portal_goods_management/`）。Vue Router のルートは `/`、`/goods/new`、`/goods/:id/edit`。未ログインはシステム設定のログイン画面 URL へ誘導する。戻る先はシステム設定のメニュー画面 URL とする。

### コンポーネント

構成上の単位（ページ、共有部品）の名前と役割のみ。配置の詳細は `ui-design.md`。

| 名前 | 役割 |
|------|------|
| ルータ | 商品一覧画面と商品登録・編集画面の切り替え。 |
| 殻 | ヘッダとナビ。他機能の部品は import しない。ナビは「グッズ管理」のみ。 |
| 商品一覧ページ | 人物・アーティスト・媒体の選択、商品一覧・タイトル絞り込み、人物・アーティスト・媒体の登録／改名／削除の管理画面を持つ。 |
| 商品登録・編集ページ | 媒体・アーティスト・タイトルなどの入力、画像の追加・削除、保存・削除操作を持つ。 |

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 人物一覧・選択中の人物に紐づくアーティスト一覧・媒体一覧・商品一覧・選択中の人物/アーティスト/媒体・タイトル絞り込み文字列の状態は画面内の状態とする。永続化しない。
- システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）は API から取得して画面内の状態とする。
- 開いた直後に人物一覧を取得する。人物を選ぶと、紐づくアーティスト一覧・媒体一覧を取得する。アーティストまたは媒体の選択（「すべて」を含む）が変わるたびに商品一覧を再取得する。タイトル絞り込みは取得済みの一覧に対する画面内の絞り込みとし、再取得はしない。

### バリデーション

- 人物・アーティスト・媒体の名称、商品のタイトルは、空文字・空白のみを送信しない。
- 商品の登録・編集では、媒体・アーティスト・タイトルを必須とする。
- 画像はブラウザで Base64 に変換して送信する。
- 失敗時は、内部理由が分からない一文のメッセージだけを示す。

### API クライアント

- 基点 URL: `import.meta.env.VITE_API_GOODS_MANAGEMENT_URL`
- API ホストをコードに直書きしない
- 呼び出し時は Cookie を含める（credentials）
- エンドポイントの契約は `api-design.md`

### 業務ロジック

- すべての操作はログイン必須かつ、ログイン中ユーザに識別子 `goods-management` の機能が割り当てられていること。論理削除済みのユーザまたは本機能は許可しない。
- 一覧・詳細取得・登録・変更・削除は、常にログイン中ユーザ自身の `user_id` で絞り込む。他ユーザの行は対象にしない（存在しないものとして扱う）。
- 人物の削除は、その人物を参照する未削除の `artist_persons` 行（いずれかの未削除アーティストとの関連）が1件以上あるとき失敗する。
- アーティストの削除は、そのアーティストを参照する未削除の商品が1件以上あるとき失敗する。削除できた場合も、`artist_persons` の関連行はそのまま残す（人物との関連の記録自体は削除しない）。
- 媒体の削除は、その媒体を参照する未削除の商品が1件以上あるとき失敗する。
- アーティストの変更で所属人物を入れ替えるとき、追加しようとする人物が操作者本人の未削除の人物であることを確認する。指定されなかった既存の関連は削除する。
- 商品の登録・変更では、指定した媒体・アーティストが操作者本人の未削除の行であることを確認する。
- 商品の登録でリリース日を指定しないときは、登録日時点の日付を設定する。編集でリリース日を指定しないときは、既存の値を保持する。
- 商品の画像は、追加のたびに表示順（登録順）を自動採番して追加する。個別の画像は商品と画像の両方が操作者本人の行であることを確認したうえで削除する。商品自体を削除しても、画像の行は削除しない（論理削除された商品に属したまま残る）。
- 人物を指定したときの関連アーティスト一覧・関連媒体一覧は、その人物に `artist_persons` で紐づく未削除のアーティストと、それらのアーティストが登録した未削除の商品が属する媒体（重複除去）を返す。
- 商品一覧は、人物必須、アーティスト（1件または「すべて」）、媒体（1件または「すべて」）の条件で、操作者本人の未削除の商品を対象に返す。タイトルによる絞り込みはフロントエンドで行い、API には持たせない。
- 操作が試みられたとき、次を契機としてログへ出す。
  - 入力された内容（人物名・アーティスト名・媒体名・商品タイトルなど。画像データそのものはログに出さない）
  - それを元にした判断結果（登録・変更・削除の成功、一覧・詳細取得の件数）
  - 正常系ではない場合の理由（参照制約違反、対象なし、入力不正、未ログイン、権限なし）
- ログの1行はタイムスタンプ、区分、メッセージの順とする。区分は INF（要求受付・成功）、WRN（想定内の失敗）、ERR（想定外）、DBG（調査用）とする。
- ログの出力先は作業ディレクトリの `log/`。ファイルサイズでローテーションする。上限サイズは `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。いずれも `.env` から読む。
- セッションの有効期間は `SESSION_TIMEOUT_MINUTES` 分。期限切れは未ログインとする。セッションの作成と破棄は本機能では行わない。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。
- システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）は `public` から読む。未ログインでもログイン画面 URL は取得できるようにする（未ログイン時の誘導に使う）。

### 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API はログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログインとして扱う。割当なしは権限なしとして扱う。フロントは未ログインならログイン画面へ誘導する。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい。本番では空にする。その場合も、当該ユーザに本機能が割り当てられていることを判定する。
- 他機能の API を認証・利用可否判定に使わない。

API キーによる認証も受け付ける（他システム連携用。詳細は `specs/api-key-management/design.md` の「対象機能の認証の変更」）。

- 要求に `Authorization` ヘッダ（Bearer 方式）があるときは、API キーで判定する。無いときは上記の Cookie（または `DEBUG_USER`）で判定する。API キーの判定に失敗したとき、Cookie・`DEBUG_USER` へは戻らない。
- キーの SHA-256 ハッシュで `public.api_keys` を検索する。該当なし・失効済み・有効期限切れ・持ち主が論理削除済みは未ログインとする。持ち主に本機能が割り当てられていない、または本機能が論理削除済みのときは権限なしとする（Cookie と同じ割当判定）。
- 許可したときは、持ち主をログイン中ユーザとして処理し、`public.api_keys` の最終利用日時を更新する。セッションの期限は延ばさない。以降の `user_id` による絞り込みは変わらない。
- 判定の結果（許可・拒否と理由、ユーザ名、API キーの識別子と識別用の先頭部分）をログに出す。API キー全体とそのハッシュは出さない。
- `api-key-management` の Python は import しない。
