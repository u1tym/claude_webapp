# 設計: schedule（スケジュール管理）

## 概要

本設計は `requirements.md` の REQ-001〜REQ-040 を満たす。利用者が自分の予定と TODO を月カレンダーで登録・確認・更新する。カテゴリ（名称・色）、ユーザ休日（年月日・名称）、ルーチン（毎月のひな型と指定年月への適用）、表示設定（カテゴリの表示／非表示、削除済みカテゴリの表示、週の開始曜日）も本人ごとに持つ。スケジュールとルーチンは通知要不要（要または不要）を持つ。通知の送信は行わない。ログインとメニューは `portal` が担う。本機能は `public` のユーザ・セッション・システム設定・機能マスタ・メニュー割当を参照し、複製しない。業務データは機能スキーマに置く。操作の試行は、入力・判断結果・失敗時の内部理由を `log` フォルダへ残す。

画面毎の部品配置と画面遷移は `ui-design.md`、API のパス・要求・応答は `api-design.md`、テーブル定義と ER 図は `db-design.md` に書く。

## 構成

- フロントエンド: `src/features/schedule/frontend` で Vue を起動。Vite `base` は `/portal_schedule/`。nginx では dist をドキュメントルートの `features/schedule/` に置き、公開 URL `/portal_schedule/` へ対応付ける
- バックエンド: `src/features/schedule/backend` の venv で uvicorn を起動
- API 基点: フロントの `VITE_API_SCHEDULE_URL`
- DB: 業務データはスキーマ `schedule`。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` を直接読む。機能スキーマへ複製しない。DDL は本機能の `backend` が持つ。詳細は `db-design.md`
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない
- 本機能の識別子: `schedule`（機能マスタの識別子。利用可否判定に用いる）

関連ドキュメント:

- UI設計: `ui-design.md`
- DB設計: `db-design.md`
- API設計: `api-design.md`

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 表示対象月は画面内の状態とする。永続化しない。開いた直後は操作している日の年月。
- スマートフォンで選んでいる日付は画面内の状態とする。永続化しない。
- カテゴリ、ユーザ休日、ルーチン、表示対象範囲のスケジュール、日本の祝日、表示設定は API から取得して画面内の状態とする。他ユーザ分は持たない。
- 日セルに出しきれない件数の算出と、残件の参照はフロントが表示時に行う。
- 適用の年月は画面内の状態とする。永続化しない。適用の操作を始めたときの初期値は表示対象月。設定ダイアログの一覧には置かない。

### バリデーション

- スケジュールの送信前に、タイトルが空でないこと、カテゴリが選ばれていること、開始と終了があること、終了が開始より前でないこと、通知要不要が要または不要であること、を確認する。満たさなければ送信しない。
- 日単位のとき、開始・終了は年月日だけを送る。時間単位のとき、年月日時分を送る。秒は送らない。
- カテゴリの送信前に、名称が空でないこと、色が選ばれていることを確認する。満たさなければ送信しない。
- ユーザ休日の送信前に、年月日があること、名称が空でないことを確認する。満たさなければ送信しない。
- ルーチンの送信前に、タイトルが空でないこと、カテゴリが選ばれていること、種別と適用日タイプがあること、通知要不要が要または不要であること、反映月が 1 つ以上あること、日付指定なら月末日か毎月 X 日（1〜31）があること、曜日指定なら N（1〜5）と曜日と N 番目／最終から N 番目があること、除外調整日が有なら除外対象が 1 つ以上かつずらしかたがあることを確認する。満たさなければ送信しない。
- 適用の送信前に、年月があることを確認する。満たさなければ送信しない。
- 失敗時は、内部理由が分からない一文のメッセージだけを示す。

### 業務ロジック

- すべての操作 API はログイン必須かつ、ログイン中ユーザに識別子 `schedule` の機能が割り当てられていること。論理削除済みのユーザまたは本機能は許可しない。
- スケジュール・カテゴリ・ユーザ休日・ルーチン・表示設定は、操作しているユーザの ID を付けて保持する。一覧・更新・削除は本人かつ対象が本人のものだけを扱う。他ユーザの ID を指定しての参照・更新はしない。
- スケジュールの種別は予定または TODO。TODO のみ実施状態（実施済み／未実施）を持つ。予定として保存するときは実施状態を持たない。予定から TODO に変えるときは未実施にする。TODO から予定に変えるときは実施状態を捨てる。
- タイトル、開始、終了、カテゴリは必須。場所と詳細は空を許す。通知要不要は要または不要。空は拒否。追加時の初期値は不要。カテゴリは本人の未削除カテゴリだけを指定できる。削除済みカテゴリが付いた既存スケジュールは参照できるが、更新時にカテゴリを指定するときは未削除のものを指定する。ルーチン識別は無くてよい。画面からの手入力追加ではルーチン識別を付けない。更新ではルーチン識別を変えない。
- 日単位の開始・終了は年月日のみ。時間単位の開始・終了は年月日時分まで（秒は持たない）。日時の基準は日本標準時。
- 終了が開始より前なら失敗する。同じなら受け付ける。
- 追加した TODO の実施状態は未実施。実施状態の単独変更は TODO のみ。予定に対する実施状態変更は失敗する。
- スケジュールの削除は論理削除。存在しない、既に論理削除済み、または他ユーザのものは失敗する。物理削除はしない。
- 範囲取得は、指定した開始日と終了日に重なる、本人の未削除スケジュールを返す。開始から終了までに含まれる各日に載せる対象である。並びは日単位、時間単位の順、同じ粒度の中では開始の昇順、開始が同じときは終了の昇順、終了も同じときはタイトルの昇順。
- 表示対象の判定（カテゴリ非表示、削除済みカテゴリを出さない）は、フロントがカテゴリと表示設定を見て行う。バックエンドの範囲取得は、本人の未削除スケジュールをカテゴリ非表示では落とさない（削除済みカテゴリ付きも含めて返す）。
- カテゴリ追加は名称と色。名称は空を拒否。同一ユーザの未削除カテゴリと名称が同じなら失敗。他ユーザや論理削除済みと同じ名称は許す。
- カテゴリ更新は未削除かつ本人の名称と色。名称の空は拒否。変更後の名称が同一ユーザの別の未削除カテゴリと同じなら失敗。名称を変えずに色だけ変えるのは成功。存在しない、論理削除済み、他ユーザは失敗。
- カテゴリ削除は論理削除。紐づくスケジュールは残し、カテゴリとの対応は維持する。物理削除はしない。
- 表示設定はユーザごとに 1 組。未登録のときの初期値は、週の開始曜日が日曜始まり、削除済みカテゴリは出さない、未削除カテゴリはすべて表示。カテゴリごとの非表示は、非表示にするカテゴリの識別を保持する。
- 祝日は、指定期間の日本の国民の祝日と振替休日を、名称付きで返す。外部の祝日 API は呼ばない。本機能のバックエンドで算出する。
- ユーザ休日の追加は年月日と名称。名称は空を拒否。同一ユーザの未削除ユーザ休日と年月日が同じなら失敗。他ユーザや論理削除済みと同じ年月日は許す。日本の祝日と同じ年月日も許す。
- ユーザ休日の更新は未削除かつ本人の年月日と名称。名称の空は拒否。変更後の年月日が同一ユーザの別の未削除ユーザ休日と同じなら失敗。年月日を変えずに名称だけ変えるのは成功。存在しない、論理削除済み、他ユーザは失敗。
- ユーザ休日の削除は論理削除。物理削除はしない。一覧は未削除のみ、年月日の昇順。
- ルーチンは本人ごとに持つ。一覧は未削除のみ。項目はタイトル、カテゴリ、種別、適用日タイプ、反映月、除外調整日の有無、詳細メモ、通知要不要、および適用日タイプに応じた日の決め方、除外調整日が有のときの除外対象とずらしかた。識別は追加時に付与する。利用者は識別を入力しない。通知要不要は要または不要。空は拒否。追加時の初期値は不要。
- ルーチン追加は必須項目の欠落を拒否する。タイトル空、カテゴリ未指定、反映月 0 件、日付指定なのに日の決め方が無い、曜日指定なのに曜日の決め方が無い、除外調整日が有なのに除外対象 0 件またはずらしかたが無い、通知要不要が要でも不要でもないときは失敗。カテゴリは本人の未削除のみ。毎月 X 日の X は 1〜31。N は 1〜5。反映月は 1〜12 から 1 つ以上。詳細メモは空を許す。
- ルーチン削除は論理削除。紐づくスケジュールは残し、ルーチン識別との対応は維持する。存在しない、既に論理削除済み、または他ユーザのものは失敗。物理削除はしない。
- ルーチン更新は未削除かつ本人。項目は追加と同じ規則。紐づくスケジュールは変えず、ルーチン識別との対応は維持する。反映月と除外対象は置き換える。存在しない、論理削除済み、他ユーザは失敗。
- 適用は指定年月に対して行う。1 件適用は未削除かつ本人のルーチン 1 件。一括適用は本人の未削除ルーチンすべて。ある件が登録しない条件に当たっても、一括では他件を続ける。
- 適用の基準日は指定年月と適用日タイプから決める。指定年月の月が反映月に含まれないときは登録しない。日付指定かつ月末日はその月の最終日。日付指定かつ毎月 X 日は、その月に X 日があればその日、無ければ基準日なし。曜日指定かつ N 番目の X 曜日は、その月の N 番目の当該曜日。無ければ基準日なし。曜日指定かつ最終から N 番目は、その月の最後から N 番目の当該曜日。無ければ基準日なし。基準日なしは登録しない。
- 除外調整日が無、または基準日が除外対象でなければ、適用日は基準日。除外調整日が有で基準日が除外対象なら、ずらしかたに従い 1 日ずつ前後し、除外対象でない日を適用日とする。ずらした結果が指定年月の外でもその年月日を適用日とする。31 日ずらしても除外のままなら適用日なし（登録しない）。祝日除外は日本の祝日（振替休日を含む）。ユーザ休日は含めない。除外対象かどうかの判定は `holiday_service` を使う。
- 指定年月に、同一ユーザの未削除スケジュールで当該ルーチン識別が付き、開始日の年月が指定年月と一致するものがあるときは登録しない。失敗にはしない。
- 適用で作るスケジュールは日単位。開始と終了は適用日。タイトル・カテゴリ・種別・通知要不要はルーチンの値。詳細は詳細メモ。場所は空。TODO なら未実施。ルーチン識別を付ける。カテゴリが論理削除済み、または本人のものでないときは登録しない。
- 日付の文字色（土曜日は青、日曜日と休日は赤、休日が土曜に重なるときは赤）はフロントが表示時に付ける。
- 操作が試みられたとき、次を契機としてログへ出す。パスワードとセッション ID は出さない。
  - 入力された内容（種別、粒度、開始、終了、カテゴリ、タイトル、通知要不要、実施状態、表示設定、ユーザ休日の年月日と名称、ルーチンの適用日タイプ・反映月・指定年月など。詳細の全文は出してよいが、セッション ID は出さない）
  - それを元にした判断結果（成功または失敗。適用で登録しなかったときはその理由も）
  - 正常系ではない場合の理由（入力不正、対象なし、論理削除済み、他ユーザ、名称重複、年月日重複、終了が開始より前、予定への実施状態変更、未ログイン、権限なし、反映月外、基準日なし、適用日なし、同一ルーチン識別が指定年月に既にある）
- ログの 1 行はタイムスタンプ、区分、メッセージの順とする。区分は INF（要求受付・成功）、WRN（想定内の失敗）、ERR（想定外）、DBG（調査用）とする。
- ログの出力先は作業ディレクトリの `log/`。ファイルサイズでローテーションする。上限サイズは `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。いずれも `.env` から読む。開発用の初期値は 10485760（10MB）と 5 世代。
- セッションの有効期間は `SESSION_TIMEOUT_MINUTES` 分。期限切れは未ログインとする。セッションの作成と破棄は本機能では行わない。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。
- システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）は `public` から読む。未ログインでもログイン画面 URL は取得できるようにする（未ログイン時の誘導に使う）。

### データアクセス

テーブル定義は `db-design.md`。ここにはアクセス関数の役割だけを書く。

| 対象 | 役割 |
|------|------|
| スケジュール | 本人・未削除の期間重なり取得、ID による本人分の取得、追加、更新、実施状態の更新、論理削除。指定年月かつ指定ルーチン識別の未削除有無の確認 |
| カテゴリ | 本人の一覧（削除済みを含む／含まない）、ID による本人分の取得、追加、名称・色の更新、論理削除、同一ユーザの未削除名称の重複確認 |
| ユーザ休日 | 本人の未削除一覧（期間または全件）、ID による本人分の取得、追加、年月日・名称の更新、論理削除、同一ユーザの未削除年月日の重複確認 |
| ルーチン | 本人の未削除一覧、ID による本人分の取得、追加、更新、論理削除 |
| 表示設定 | 本人分の取得、無いときの初期値での扱い、更新 |
| ユーザ | ID / ユーザ名による取得（認証・認可）。業務データとしては更新しない |
| セッション | 参照。作成と破棄はしない。期限切れの扱いは未ログイン |
| システム設定 | キーによる取得 |
| 機能マスタ | 識別子による取得（本機能の利用可否）。更新しない |
| メニュー割当 | 指定ユーザに指定機能があるかの確認 |

### 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API はログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログインとして扱う。割当なしは権限なしとして扱う。フロントは未ログインならログイン画面へ誘導する。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい。本番では空にする。その場合も、当該ユーザに本機能が割り当てられていることを判定する。
- 他機能の API を認証・利用可否判定に使わない。
