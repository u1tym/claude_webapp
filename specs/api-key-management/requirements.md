# api-key-management（APIキー管理）要件定義

## 概要

ログイン中の利用者が、他システムとの連携に使う自分専用の API キーを発行・確認・失効できる機能である。他システムは、発行された API キーを添えることで、画面からログインせずに、その利用者として対象機能の API を利用できる。

API キーで利用できる範囲は、キーの持ち主であるユーザに割り当てられた機能と同じとする。API キーでの利用に対応させる機能（対象機能）は、まず `goods-management`、`expense-management`、`knowhow-management`、`schedule` の 4 機能とし、その他の機能は後で広げる。

## 用語

| 用語 | 説明 |
|------|------|
| API キー | 他システムが、ある利用者として対象機能の API を利用するための秘密の文字列。1 人の利用者が複数持てる。 |
| 持ち主 | その API キーを発行したユーザ。API キーによる利用は、持ち主による利用として扱う。 |
| 名前 | API キーの用途を利用者が見分けるための表示名（例:「家計簿連携」）。 |
| 有効期限 | その日時を過ぎると API キーが使えなくなる日時。発行時に任意で指定する。指定しなければ無期限。 |
| 失効 | API キーを以後使えなくすること。元に戻せない。 |
| 有効な API キー | 失効しておらず、有効期限を過ぎておらず、持ち主が論理削除されていない API キー。 |
| 識別用の先頭部分 | 一覧で API キーを見分けるために示す、キーの先頭の数文字。キー全体ではない。 |
| 対象機能 | API キーでの利用に対応させる機能。本要件では `goods-management`、`expense-management`、`knowhow-management`、`schedule`。 |
| 本機能 | この API キー管理機能そのもの。メニューへ載せる機能の一つである。 |

## 要件一覧

### REQ-001: 利用可否の判定

本機能を利用するとき、システムはログインを必須とし、ログイン中ユーザに本機能が割り当てられているときだけ利用を許可すること。

**受け入れ条件**

- 未ログインでは、API キーの発行・一覧・失効ができない。
- 本機能が割り当てられていないログイン中ユーザは、発行・一覧・失効ができない。
- 論理削除済みのユーザまたは本機能では、発行・一覧・失効ができない。
- API キーを使って本機能を利用すること（API キーで API キーを発行・一覧・失効すること）はできない。
- 判定は他機能の API に依存しない。

### REQ-002: 本人の API キーだけを扱う

システムは常に、ログイン中ユーザ本人が持ち主である API キーだけを、一覧・失効の対象とすること。

**受け入れ条件**

- 一覧には、本人が持ち主の API キーだけが出る。
- 他ユーザの API キーの識別子を直接指定しても、失効できない（存在しないものとして扱う）。

### REQ-003: API キーの発行

ログイン中の利用者が名前と、任意で有効期限を指定して API キーの発行を要求したとき、システムは本人を持ち主とする新しい API キーを発行し、そのキー全体を発行の直後に一度だけ示すこと。

**受け入れ条件**

- 名前を指定して発行できる。名前が空のときは発行できない。
- 有効期限を指定して発行できる。指定しないときは無期限になる。
- 過去の日時を有効期限に指定したときは発行できない。
- 発行したキー全体は、発行直後の応答でだけ示され、その後の一覧や再表示では二度と示されない。
- キー全体は、平文のまま保持されない。
- 発行されるキーは推測困難であり、他のキーと重複しない。
- 1 人の利用者が複数の API キーを持てる。

### REQ-004: API キーの一覧

ログイン中の利用者が API キーの一覧を要求したとき、システムは本人の API キーを示すこと。

**受け入れ条件**

- 名前、識別用の先頭部分、発行日時、有効期限（無期限ならその旨）、最終利用日時（未使用ならその旨）が一覧に出る。
- 有効、期限切れ、失効済みのいずれの状態かが分かる。
- キー全体は一覧に出ない。
- 失効済みの API キーも一覧に出る。

### REQ-005: API キーの失効

ログイン中の利用者が自分の API キーの失効を要求したとき、システムは当該 API キーを失効させること。

**受け入れ条件**

- 失効させた API キーは、その直後から対象機能の API に使えなくなる。
- 失効は取り消せない。
- 失効後も、当該 API キーの記録（名前、発行日時、最終利用日時など）は一覧に残る。
- 存在しない API キー、または既に失効済みの API キーの失効は失敗する。

### REQ-006: 対象機能の API キーによる利用

他システムが有効な API キーを添えて対象機能の API を要求したとき、対象機能は、ログインを介さずに、その API キーの持ち主がログインしているのと同じ扱いで要求を処理すること。

**受け入れ条件**

- 有効な API キーを添えれば、画面からログインしなくても、対象機能の API を利用できる。
- API キーによる要求で参照・操作できるデータは、持ち主本人のデータだけである（ログインして利用するときと同じ）。
- 持ち主に当該機能が割り当てられていない、または当該機能が論理削除済みのときは、API キーを添えても利用できない。
- 存在しない、失効済み、有効期限切れ、または持ち主が論理削除済みの API キーでは、未ログインとして扱い、利用できない。
- 持ち主のパスワードを変更しても、API キーはそのまま使える。
- API キーを添えない要求は、従来どおりログイン状態で判定し、画面からの利用に変化はない。
- 判定は他機能の API に依存しない。
- 対象機能以外の機能は、API キーを添えても利用できない（従来どおりログインが必要）。

### REQ-007: 最終利用日時の記録

対象機能が API キーによる要求を受け付けたとき、システムは当該 API キーの最終利用日時を更新すること。

**受け入れ条件**

- API キーで対象機能を利用すると、一覧の最終利用日時がその利用の日時に変わる。
- 利用を拒否した要求（割当なしなど）では、最終利用日時は変わらない。

### REQ-008: 操作の記録（ログ）

API キーの発行・失効が試みられたとき、および対象機能が API キーによる要求を判定したとき、システムは当該試行の記録を、それぞれの機能の log フォルダへ出力すること。

**受け入れ条件**

- 発行・失効の試行が、本機能の log フォルダ配下のファイルに残る。
- 対象機能で API キーによる要求を許可・拒否した記録が、その対象機能の log フォルダ配下のファイルに残る。
- 記録にはタイムスタンプと区分（INF、WRN、ERR、DBG のいずれか）が含まれる。
- 記録には、判断に使う値（ユーザ名、API キーの名前、識別用の先頭部分など）と判断結果が含まれる。
- API キー全体は、記録に含まれない。
- 失敗・拒否のとき、画面や応答へ出さない内部理由が記録に含まれる。
- ファイルはサイズが大きくなったら新しいファイルへ切り替わる。

## 認証の要否

本機能の画面と操作（API キーの発行・一覧・失効）は、すべてログインによる認証を必須とし、API キーによる利用は認めない。利用可否は、ログイン中ユーザに本機能が割り当てられているかで判定する（REQ-001）。ログイン画面とメニュー画面は本機能では提供しない（`portal` が担う）。

対象機能の API は、従来のログインに加えて、有効な API キーによる利用を認める。利用可否は、API キーの持ち主にその機能が割り当てられているかで判定する（REQ-006）。

## スコープ外

- ログイン画面、メニュー画面（`portal` が担う）
- 本機能の初期登録（機能マスタへの追加と、利用者への割当はユーザ管理で行う）
- 運用者による、他ユーザの API キーの発行・一覧・失効
- API キーごとに利用できる機能や操作（参照のみ等）を限定すること
- 対象機能以外（`note-management`、`recipe-management`、`movie-management`、`password-management`、`user-management` など）の API キー対応
- 発行済み API キーの名前・有効期限の変更、失効の取り消し、キー全体の再表示
- API キーによる利用の回数制限・流量制限
- 発行できる API キーの個数の上限
- 失効済み・期限切れの API キーの記録の削除
