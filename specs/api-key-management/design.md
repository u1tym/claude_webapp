# api-key-management（APIキー管理）全体設計

> UI の詳細（画面毎の部品配置・画面遷移）は書かない → `ui-design.md`
> API の詳細（パス・要求・応答・エラー）は書かない → `api-design.md`
> テーブル定義と ER 図は書かない → `db-design.md`

## 全体構成

本設計は `requirements.md` の REQ-001〜REQ-008 を満たす。本設計は、本機能そのもの（API キーの発行・一覧・失効）と、対象機能（`goods-management`、`expense-management`、`knowhow-management`、`schedule`）の認証部分の変更の 2 つからなる。

- フロントエンド: `src/features/api-key-management/frontend` の Vue（SPA）。Vite `base` は `/portal_api_key_management/`。nginx では dist をドキュメントルートの `features/api-key-management/` に置き、公開 URL `/portal_api_key_management/` へ対応付ける。
- バックエンド: `src/features/api-key-management/backend` の別プロセスの FastAPI（venv、uvicorn）。開発時のポートは 8010、フロントの開発ポートは 5184（既存機能と重複しない値）。
- API 基点: フロントの `VITE_API_API_KEY_MANAGEMENT_URL`。
- DB: API キーの表は、スキーマ `public` に置く（`public.api_keys`）。本機能が書き込み、対象機能がそれぞれ直接読んで判定するため、機能スキーマではなく共通のスキーマに置く。本機能の固有スキーマ（`api_key_management`）は作らない。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` を直接読む（複製しない）。
- API キーの表の DDL は、本機能の `backend/sql/` が持つ（`portal` の DDL には足さない）。
- ログ: 本機能・対象機能とも、それぞれのバックエンドの `log/` へファイル出力する。テーブルには残さない。
- 本機能の識別子: `api-key-management`（機能マスタの識別子。利用可否判定に用いる）。

```
ブラウザ ── SPA(Vue) ──(Cookie)──▶ api-key-management(FastAPI) ──▶ public.api_keys（発行・一覧・失効）
                                                                       ▲ 読み取り・最終利用日時の更新
他システム ──(API キー)──▶ 対象機能(FastAPI: goods / expense / knowhow / schedule) ─┘
ブラウザ ── 対象機能の SPA ──(Cookie)──▶ 対象機能(FastAPI)   ※従来どおり
```

関連ドキュメント: `requirements.md` / `ui-design.md` / `db-design.md` / `api-design.md`

## フロントエンド設計

### 画面

画面の一覧のみ。部品配置と遷移の詳細は `ui-design.md`。ログイン画面とメニュー画面は持たない。ヘッダ / ナビの殻を使う（`rules/15-ui-style.md`）。パスは Vue Router のルート（公開パスの基点は Vite `base`）。

| 画面 | パス | 役割 |
|------|------|------|
| API キー一覧 | `/` | 本人の API キーの一覧（名前、識別用の先頭部分、発行日時、有効期限、最終利用日時、状態）。発行（名前・有効期限の入力と、発行したキー全体の一度だけの表示）と、失効の入口。 |

未ログインはシステム設定のログイン画面 URL へ誘導する。戻る先はシステム設定のメニュー画面 URL とする。`createWebHistory(import.meta.env.BASE_URL)` を用いる。

### 起動方法・モジュール構成

- 起動方法: `src/features/api-key-management/frontend/` で `npm run dev`
- 技術: Vue 3、TypeScript、Vue Router、Vite。他機能の Vue・CSS・コンポーネントは import しない。

| 場所 | 役割 |
|------|------|
| `src/router.ts` | ルート定義（上記の画面）。 |
| `src/api/` | API 基点 URL の解決、Cookie を含めた呼び出し、認証失敗（未ログイン・権限なし）の共通処理、各 API の呼び出しと型。 |
| `src/views/` | 画面ごとのページコンポーネント。 |
| `src/components/` | 殻（ヘッダ・ナビ）、`Icon.vue`、確認ダイアログ、発行ダイアログ、発行結果のダイアログ。 |
| `src/styles.css` | `rules/15-ui-style.md` のトークンとスタイル。 |

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 発行したキー全体は、発行結果のダイアログを閉じるまでの画面内の状態とし、閉じたら破棄する。`localStorage`・URL・ログには置かない。
- システム設定（ログイン画面 URL、メニュー画面 URL、共通アイコン）は API から取得して保持する。

### フロントの責務

- 一覧: 本人の API キーを取得して表示する。状態（有効・期限切れ・失効済み）はサーバが判定した値を表示する。
- 発行: 名前（必須）と有効期限（任意）を入力して送る。送信前に、名前が空でないこと、有効期限が過去でないことを検証する（サーバ側でも検証する）。成功したら、発行結果のダイアログでキー全体を示し、クリップボードへのコピーを提供する。「この画面を閉じると二度と表示できない」旨を示す。閉じたら一覧を取得し直す。
- 失効: 確認ダイアログを経て送る。成功したら一覧を取得し直す。
- 失敗時は、内部理由が分からない一文だけを示す。

### 業務ロジック

#### 共通

- すべての操作は、ログイン必須かつ、ログイン中ユーザに本機能が割り当てられていること（REQ-001）。
- すべての操作は、常にログイン中ユーザ自身の `user_id` で絞り込む。他ユーザの API キーは存在しないものとして扱う（REQ-002）。

#### API キーの形式と保存

- キー全体は、固定の接頭辞（`wak_`）と、暗号論的に安全な乱数（`secrets`、32 バイト）を URL 安全な Base64 にした文字列を連結したものとする。推測困難であり、重複は事実上起きない。重複時の保険として、ハッシュの一意制約で検出し、生成し直す。
- 保存するのは、キー全体の SHA-256 ハッシュと、識別用の先頭部分（接頭辞を含む先頭 12 文字）だけとする。キー全体は保存しない。
  - パスワードと異なり、キーは十分に長い乱数であるため、ソルト付きの低速なハッシュ（bcrypt 等）は用いない。ハッシュの完全一致で検索できるようにするため。
- 状態は、保存した値からその都度判定する。失効日時があれば「失効済み」、有効期限を過ぎていれば「期限切れ」、それ以外は「有効」。

#### 発行（REQ-003）

- 名前は、前後の空白を除いた結果が空のときは入力不正とする。
- 有効期限は任意。指定されたときは、現在より後であることを確認する（過去・現在は入力不正）。
- キー全体を生成し、ハッシュと識別用の先頭部分を、本人の `user_id`・名前・有効期限・発行日時とともに保存する。
- 応答にだけキー全体を含める。一覧・その他の応答には含めない。

#### 一覧（REQ-004）

- 本人の API キーを、失効済みを含めてすべて返す。発行日時の新しい順。
- 各行に、名前、識別用の先頭部分、発行日時、有効期限（無期限は空）、最終利用日時（未使用は空）、失効日時、状態を含める。

#### 失効（REQ-005）

- 本人の、未失効の API キーだけが対象。存在しない・他人の・既に失効済みのものは失敗とする。
- 失効日時を記録する。行は削除しない。失効を取り消す操作は持たない。
- 期限切れの API キーの失効は、成功として扱う（失効日時を記録する）。

### 対象機能の認証の変更（REQ-006、REQ-007）

対象機能（`goods-management`、`expense-management`、`knowhow-management`、`schedule`）それぞれの `app/deps.py` の、ログイン中ユーザを特定する処理を、次のように変える。本機能の Python は import せず、各対象機能が `public.api_keys` を直接読む。

1. 要求に API キー（`Authorization` ヘッダの Bearer 方式）が添えられているときは、API キーで判定する。添えられていないときは、従来どおり（`DEBUG_USER`、Cookie のセッション）で判定する。API キーの判定に失敗したときに、Cookie や `DEBUG_USER` へは戻らない。
2. API キーの判定:
   - 添えられたキーの SHA-256 ハッシュで `public.api_keys` を検索する。
   - 行が無い、失効済み、有効期限を過ぎている、持ち主が論理削除済みのいずれかのときは、未ログインとする。
   - 持ち主に当該機能が割り当てられていない、または当該機能が論理削除済みのときは、権限なしとする（従来の割当判定と同じ処理を使う）。
   - 許可したときは、最終利用日時を現在に更新し、持ち主をログイン中ユーザとして扱う。拒否したときは更新しない。
   - セッションの有効期限の延長はしない（セッションを使わないため）。
3. 以降の処理（本人のデータだけを扱う絞り込みなど）は、従来のログイン中ユーザと同じ `user_id` を使うため、変更しない。
4. 各対象機能の `repos` に、API キーの検索と最終利用日時の更新を足す。`security.py` に、キーのハッシュ化（本機能と同じ方式。コードは各機能に置く）を足す。
5. 対象機能のすべての API（システム設定の取得、業務の API、画像等の取得を含む）が、同じ判定を通る。
6. CORS の設定は変えない。他システムからの要求はブラウザを介さない想定のため。

対象機能以外は変更しない。対象機能以外に API キーを添えても、従来どおり Cookie で判定するため、ログインしていなければ未ログインになる。

対象機能の既存 SPEC（`design.md` の認証 / 認可、`db-design.md` の参照する表、`api-design.md` の共通の認証とエラー、`tasks.md`）は、本機能の `api-design.md` の承認後に改訂し、再承認を得る。

#### ログ（REQ-008）

- 本機能: 発行・一覧・失効の試行ごとに、入力（ユーザ名、名前、有効期限、対象の API キーの識別子と識別用の先頭部分）、判断結果、失敗の理由（入力不正、対象なし、失効済み、未ログイン、権限なし）を出す。
- 対象機能: API キーによる要求ごとに、判定の結果を出す。許可は INF（ユーザ名、API キーの識別子、識別用の先頭部分）、拒否は WRN（理由: 該当なし、失効済み、期限切れ、ユーザ削除済み、権限なし）。該当なしのときは、識別用の先頭部分に相当する、添えられた値の先頭 12 文字だけを出す。
- API キー全体、そのハッシュ、セッション ID、パスワード、Cookie は出さない。
- 1 行はタイムスタンプ、区分、メッセージの順。区分は INF / WRN / ERR / DBG。出力先は `log/`。ファイルサイズでローテーションし、上限は `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。
- 画面・応答へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。

### テスト

- `src/features/api-key-management/tests/` に、本機能のバックエンドの API テスト（pytest）を置く。
- 各対象機能の `tests/` に、API キーによる認証のテスト（許可、未ログインの各理由、権限なし、最終利用日時の更新、Cookie による従来の利用が変わらないこと）を足す（詳細は `tasks.md`）。

## 認証 / 認可

### 本機能

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API は、ログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログイン、割当なしは権限なしとして扱う。フロントは、未ログインならログイン画面へ誘導する。
- API キーによる認証は受け付けない（API キーが添えられていても無視し、Cookie で判定する）。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい（当該ユーザへの本機能の割当は判定する）。本番では空にする。
- 他機能の API を認証・利用可否判定に使わない。

### 対象機能

従来の Cookie ベースのセッション認証に加えて、API キーによる認証を受け付ける（前節「対象機能の認証の変更」）。

- API キーは `Authorization` ヘッダの Bearer 方式で受け取る。URL（クエリ）では受け取らない。
- API キーの判定の結果は、未ログイン・権限なしの扱いを Cookie と同じにする。
- 本番では https を用いるため、API キーは通信路で保護される。

## デプロイ上の考慮（nginx）
