# 設計: user-management（ユーザ管理）

## 概要

本設計は `requirements.md` の REQ-001〜REQ-013 を満たす。運用者が Web 画面から、ユーザ・機能・割当を追加・更新・削除できるようにする。ユーザはメールアドレスを持つ。ログインには使わない。ログインとメニューは `portal` が担う。本機能は `portal` と同じ `public` のユーザ・機能・割当を更新し、複製しない。操作の試行は、入力・判断結果・失敗時の内部理由を `log` フォルダへ残す。

画面毎の部品配置と画面遷移は `ui-design.md`、API のパス・要求・応答は `api-design.md`、テーブル定義と ER 図は `db-design.md` に書く。

## 構成

- フロントエンド: `src/features/user-management/frontend` で Vue を起動。Vite `base` は `/portal_user_management/`。nginx では dist をドキュメントルートの `features/user-management/` に置き、公開 URL `/portal_user_management/` へ対応付ける
- バックエンド: `src/features/user-management/backend` の venv で uvicorn を起動
- API 基点: フロントの `VITE_API_USER_MANAGEMENT_URL`
- DB: 本機能の固有スキーマは作らない。ユーザ、セッション、システム設定、機能マスタ、メニュー割当はスキーマ `public` を直接読む・更新する。機能スキーマへ複製しない。DDL は持たない（表は `portal` が用意する。メールアドレス列も `portal` の DDL で `public.users` に足す）。詳細は `db-design.md`
- ログ: バックエンドの `log/` へファイル出力する。テーブルには残さない
- 本機能の識別子: `user-management`（機能マスタの識別子。利用可否判定と、本機能自身の削除禁止に用いる）

関連ドキュメント:

- UI設計: `ui-design.md`
- DB設計: `db-design.md`
- API設計: `api-design.md`

## フロントエンド設計

### 画面

画面の一覧のみ（画面名、パス、役割）。部品配置と遷移の詳細は `ui-design.md`。ログイン画面とメニュー画面は持たない。ヘッダ / ナビの殻を使う。

| 画面 | パス | 説明 |
|------|------|------|
| ユーザ | `/portal_user_management/users` | ユーザの一覧、追加、更新、削除。メールアドレスを含む。 |
| 機能 | `/portal_user_management/features` | 機能の一覧、追加、更新、削除。 |
| 割当 | `/portal_user_management/assignments` | 割当の一覧、追加、解除。 |

公開パスの基点は Vite `base`（`/portal_user_management/`）。Vue Router のルートは `/users`、`/features`、`/assignments`。`/portal_user_management/` はユーザ画面へ進む。未ログインはシステム設定のログイン画面 URL へ誘導する。戻る先はシステム設定のメニュー画面 URL とする。

### コンポーネント

構成上の単位（ページ、共有部品）の名前と役割のみ。配置の詳細は `ui-design.md`。

| 名前 | 役割 |
|------|------|
| ルータ | 画面の切り替え。 |
| 殻 | ヘッダとナビ。他機能の部品は import しない。 |
| ユーザページ | ユーザの一覧と、追加・更新・削除。メールアドレスの表示と入力。 |
| 機能ページ | 機能の一覧と、追加・更新・削除。 |
| 割当ページ | 割当の一覧と、追加・解除。 |

### 状態管理

- セッション ID はフロントに保持しない。Cookie で送受信する。
- 一覧は表示のために取得して、当該画面内の状態とする。
- アイコンは API から得たデータ、または利用者が選んだデータとして扱う。配信用の画像ファイルはフロントに置かない。

### バリデーション

- ユーザ追加の前に、ユーザ名、パスワード、メールアドレスが空でないこと、メールアドレスに `@` がありその前後に文字があることを確認する。満たさなければ送信しない。
- ユーザ更新の前に、ユーザ名とメールアドレスが空でないこと、メールアドレスに `@` がありその前後に文字があることを確認する。パスワードが空ならパスワードは変えない。
- 機能追加の前に、識別子、タイトル、遷移先、アイコンが揃っていることを確認する。空なら送信しない。
- 機能更新の前に、タイトルと遷移先が空でないことを確認する。アイコンを選んでいないときは、既存のアイコンを維持する。
- 割当追加の前に、ユーザ、機能、表示順が揃っていることを確認する。空なら送信しない。
- 失敗時は、内部理由が分からない一文のメッセージだけを示す。

### API クライアント

- 基点 URL: `import.meta.env.VITE_API_USER_MANAGEMENT_URL`
- API ホストをコードに直書きしない
- 呼び出し時は Cookie を含める（credentials）
- エンドポイントの契約は `api-design.md`

## バックエンド設計

### 起動

- 作業ディレクトリ: `src/features/user-management/backend`
- 仮想環境: `venv/`
- 起動: `uvicorn app.main:app --reload --port 8001`

### モジュール構成

| ファイル | 役割 |
|----------|------|
| `app/main.py` | FastAPI 生成、CORS 設定、ルータ登録、ログの初期化 |
| `app/config.py` | `.env` から接続情報、CORS、セッション有効期間、`DEBUG_USER`、ログのローテーション設定を読む |
| `app/logger.py` | ファイルログの初期化と出力。サイズによるローテーション |
| `app/db.py` | PostgreSQL への接続 |
| `app/security.py` | パスワードのハッシュ化、セッション Cookie の参照 |
| `app/deps.py` | 要求からログイン中ユーザを特定し、本機能の割当を判定する。未ログイン・期限切れは未ログイン。割当なしは権限なし |
| `app/routers/users.py` | ユーザの一覧、追加、更新、論理削除 |
| `app/routers/features.py` | 機能の一覧、追加、更新、論理削除 |
| `app/routers/assignments.py` | 割当の一覧、追加、解除 |
| `app/routers/settings.py` | システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）の取得。`public` を直接読む |
| `app/services/user_service.py` | ユーザの追加・更新・論理削除。自己削除の禁止。パスワードのハッシュ化。メールアドレスの検証 |
| `app/services/feature_service.py` | 機能の追加・更新・論理削除。本機能自身の削除禁止。識別子は更新しない |
| `app/services/assignment_service.py` | 割当の追加・解除。自分自身からの本機能の割当解除の禁止 |
| `app/services/access_service.py` | 指定ユーザに指定機能が割り当てられているかの判定（本機能内） |
| `log/` | ログファイルの出力先。リポジトリに含めない |

エンドポイントの契約は `api-design.md`。テーブルは `db-design.md`。

`portal` の Python を import しない。ログイン・ログアウトの API は持たない。利用可否は `public` の機能マスタとメニュー割当を本機能が読んで判定する。

### 業務ロジック

- すべての操作 API はログイン必須かつ、ログイン中ユーザに識別子 `user-management` の機能が割り当てられていること。論理削除済みのユーザまたは本機能は許可しない。
- ユーザ追加時、パスワードは一方向ハッシュにして保存する。平文は残さない。同じユーザ名は登録できない。メールアドレスは必須。空、または `@` の前後に文字が無い形式は拒否する。メールアドレスではログインしない。
- ユーザ更新は、未削除ユーザのユーザ名とメールアドレス、任意でパスワードを変える。パスワードが空なら変えない。指定があればハッシュして保存する。ユーザ名またはメールアドレスが空なら失敗する。メールアドレスの形式が不正なら失敗する。変更後のユーザ名が既にあれば失敗する。
- ユーザ削除は論理削除とする。自分自身の削除は失敗する。存在しない、または既に論理削除済みは失敗する。
- 機能追加は識別子・タイトル・遷移先・アイコン（バイト列とメディアタイプ）を保存する。同じ識別子は登録できない。配信用の画像ファイルは置かない。
- 機能更新は未削除機能のタイトル・遷移先・アイコンを変える。識別子は変えない。アイコンが来なければ既存を維持する。本機能（識別子 `user-management`）の削除は失敗する。存在しない、または既に論理削除済みの更新・削除は失敗する。
- 機能削除は論理削除とする。割当行は残してよい。一覧とメニューの対象からは外す。
- 割当追加は、未削除のユーザと未削除の機能に表示順を付けて行う。重複は失敗する。存在しない、または論理削除済みの対象は失敗する。
- 割当解除は、割り当て済みの組み合わせだけを外す。未割当は失敗する。操作している本人から本機能（識別子 `user-management`）を外すことは失敗する。
- 一覧は未削除のユーザ・機能、および未削除同士の割当だけを返す。パスワードハッシュは返さない。ユーザ一覧はメールアドレスを含む。
- 操作が試みられたとき、次を契機としてログへ出す。パスワードとセッション ID は出さない。
  - 入力された内容（ユーザ名、メールアドレス、機能識別子、表示順など。パスワードは出さない）
  - それを元にした判断結果（成功または失敗）
  - 正常系ではない場合の理由（重複、対象なし、論理削除済み、自己削除、本機能の削除、自己からの本機能割当解除、入力不正、メールアドレス形式不正、未ログイン、権限なし）
- ログの 1 行はタイムスタンプ、区分、メッセージの順とする。区分は INF（要求受付・成功）、WRN（想定内の失敗）、ERR（想定外）、DBG（調査用）とする。
- ログの出力先は作業ディレクトリの `log/`。ファイルサイズでローテーションする。上限サイズは `LOG_MAX_BYTES`、世代数は `LOG_BACKUP_COUNT`。いずれも `.env` から読む。開発用の初期値は 10485760（10MB）と 5 世代。
- セッションの有効期間は `SESSION_TIMEOUT_MINUTES` 分。期限切れは未ログインとする。セッションの作成と破棄は本機能では行わない。
- 画面へ返す失敗は、内部理由を含まない一文とする。内部理由はログにだけ残す。
- システム設定（ログイン画面 URL、メニュー画面 URL、システム共通アイコン）は `public` から読む。未ログインでもログイン画面 URL は取得できるようにする（未ログイン時の誘導に使う）。

### データアクセス

テーブル定義は `db-design.md`。ここにはアクセス関数の役割だけを書く。

| 対象 | 役割 |
|------|------|
| ユーザ | 未削除の一覧、ID / ユーザ名による取得、追加、ユーザ名とメールアドレスの更新、パスワードハッシュの更新、論理削除。パスワードハッシュは一覧では返さない。メールアドレスは返す |
| セッション | 参照。作成と破棄はしない。期限切れの扱いは未ログイン |
| システム設定 | キーによる取得 |
| 機能マスタ | 未削除の一覧、識別子による追加・更新・取得、論理削除。アイコンのバイト列の保存と取得 |
| メニュー割当 | 未削除ユーザ・未削除機能の割当一覧、追加、削除、存在確認 |

### 認証 / 認可

Cookie ベースのセッション認証を用いる。ログイン API は持たない。`portal` が発行したセッション Cookie を検証する。

- 操作 API はログイン必須かつ本機能の割当必須。未ログインまたはセッション期限切れは未ログインとして扱う。割当なしは権限なしとして扱う。フロントは未ログインならログイン画面へ誘導する。
- セッション ID は URL、レスポンス本文、`localStorage` に置かない。
- `DEBUG_USER` があるときだけ、Cookie がなくてもそのユーザ名として処理してよい。本番では空にする。その場合も、当該ユーザに本機能が割り当てられていることを判定する。
- 他機能の API を認証・利用可否判定に使わない。
