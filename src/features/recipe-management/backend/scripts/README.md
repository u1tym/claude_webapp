# 別サーバ版（recipe）からのデータ移行

`sample/recipe` で稼働している別サーバ版のレシピ管理サービスから、本機能（recipe-management）へデータを移行する手順。

移行元 DB と移行先 DB の **両方へ同時に接続** し、移行元から読んだデータを直接、移行先へ書き込む。エクスポート用のファイルは作らない。

移行元へは **読み取りしか行わない**（読み取り専用のセッションで接続する）。移行元のデータは変更・削除されない。

## 利用者について

移行元（`sample/recipe`）は利用者を持たない（全員が同じレシピ・材料・分量名称を共有している）。本機能はレシピを利用者ごとに持つため、**移行するデータは、すべて、`--username` で指定した 1 人の利用者のものとして移行する**。

- 移行先に、その利用者名の利用者が無い、または論理削除済みのときは、何も移行せずに終了する（終了コード `2`）。利用者は、事前にユーザ管理で作っておくこと。
- 本機能の利用の割当（機能マスタ・メニュー割当）は、移行には不要（画面を使う段階で必要）。

## 移行するもの

| 移行元 | 移行先 | 備考 |
|--------|--------|------|
| メニュー（`recipe.menu`）と工程（`recipe.menu_step`）、工程ごとの材料（`recipe.menu_step_ingredient`） | レシピ・工程・材料の行 | **削除済み（`is_deleted = true`）のメニューは移行せず**、対象外として一覧表示する |
| 材料（`recipe.ingredient`） | 材料 | 下記の対応付けをする |
| 分量名称（`recipe.measurements`） | 分量名称 | 下記の対応付けをする |

- 工程番号・工程内の材料の並び（移行元の識別子の順）・工程の説明・数量は、移行元の値をそのまま使う。
- 識別子は、移行先で新しく採番する。

### 材料・分量名称の対応付け

移行先には、全利用者共通の材料 12 件・分量名称 4 件が、初期データとして入っている。移行元の材料・分量名称は、次の順で対応付ける。

1. 移行先の **共通** のものと同じもの（材料は名前が同じ、分量名称は接頭語と接尾語の組が同じ）があれば、それに対応付ける（新しく作らない）。
2. 無ければ、`--username` の利用者の **独自** のものに同じものがあれば、それに対応付ける。
3. それも無ければ、その利用者の独自として **追加** する。

対応付けた既存のものと、数量の要否（数量が必要か）が違うときは、既存のものを **変更せず**、違いを結果の一覧に表示する。

## 前提

- 移行先の DDL を適用済みであること。

  ```bash
  cd src/features/recipe-management/backend
  python sql/apply.py
  ```

- `backend` の venv が使え、`backend/.env` が移行先（本プロジェクトの DB）を指していること。別の DB を移行先にするときは、環境変数 `RECIPE_MANAGEMENT_ENV_FILE` に、その接続情報を書いた設定ファイルのパスを指定する（`backend/.env` は変更しない）。
- 移行を実行する環境から、移行元 DB と移行先 DB の両方に到達できること。
- 移行元の DB ユーザには、`recipe` スキーマの読み取り権限があること。

## 手順

### 1. ドライラン（書き込まずに確認する）

```bash
cd src/features/recipe-management/backend
python scripts/migrate_from_recipe.py --dry-run --username <移行先の利用者名> \
  --host <移行元のホスト> --port 5432 --dbname <移行元のDB名> \
  --user <移行元のユーザ> --password <移行元のパスワード>
```

移行元の接続情報は、環境変数（`RECIPE_DB_HOST` / `RECIPE_DB_PORT` / `RECIPE_DB_NAME` / `RECIPE_DB_USER` / `RECIPE_DB_PASSWORD`）でも指定できる（引数が優先）。パスワードをコマンド履歴に残したくないときは、環境変数を使う。

何も書き込まず、移行の対象・スキップ・対象外・失敗の見込みを、標準エラー出力に表示する。

### 2. 実行

```bash
python scripts/migrate_from_recipe.py --username <移行先の利用者名> \
  --host <移行元のホスト> --port 5432 --dbname <移行元のDB名> \
  --user <移行元のユーザ> --password <移行元のパスワード>
```

実行中は、レシピ 1 件ごとに進捗（`[n/全体件数] メニュー名`）を表示する。レシピは **1 件ずつ、1 つのトランザクション** で移行する。途中で失敗したレシピは、移行先へ何も残らない（ロールバックされる）。1 件の失敗は、ほかのレシピの移行を止めない。

### 3. 結果を確認する

終了時に、種別ごとの件数と内訳が表示される。

```
===== 結果 =====
レシピ: 移行 12 / スキップ 0 / 対象外 2 / 失敗 0
    [対象外] レシピ「天下一品」(移行元ID=10) 削除済み
工程: 移行 47 / スキップ 0 / 対象外 0 / 失敗 0
材料の行: 移行 139 / スキップ 0 / 対象外 0 / 失敗 0
材料: 移行 39 / スキップ 12 / 対象外 0 / 失敗 0
分量名称: 移行 11 / スキップ 4 / 対象外 0 / 失敗 0
```

| 区分 | 意味 |
|------|------|
| 移行 | 移行先へ書き込んだ（ドライランでは「移行予定」） |
| スキップ | 既にあるため書き込まなかった（材料・分量名称は、共通・独自の既存のものに対応付けたもの。レシピは、移行済みのもの） |
| 対象外 | 移行の対象ではない（削除済みのレシピ、移行元に存在しない材料・分量名称を指すため取り除いた材料の行） |
| 失敗 | 移行しようとしたが失敗した。理由が併記される |

- 終了コードは、正常が `0`、失敗が 1 件でもあると `1`、接続できない・利用者が無いときは `2`。
- 操作の記録（開始・レシピごとの成否・終了）は、`backend/log/` にも残る。パスワードは出力しない。
- 移行したレシピは、移行先で、工程数と材料の行の数が、移行元と一致することを確認したうえで確定している。

### 4. 再実行

途中で止まった場合や、失敗の原因（移行元のデータなど）を直した後は、**同じコマンドをもう一度実行すればよい**。

- 移行済みのレシピは、指定した利用者の、削除されていないレシピに、**同じメニュー名** があるかで判定し、スキップする。
- 材料・分量名称は、既存のものに対応付けるため、二重に作られない。
- 移行後に、移行先でメニュー名を変更した、または削除したレシピは、再実行すると、移行済みと判定されず、もう一度移行される。再実行するときは、そのようなレシピがないかを、ドライランで確認する。

### 5. 後片付け

- 移行の確認が済んだら、コマンド履歴や環境変数に残した移行元のパスワードを消す。
- 移行元のデータは、この手順では削除しない。旧サービスの停止・削除は、別途判断する。

## 移行元の構造に関する注意

移行元は、`sample/recipe/backend/db/db.sql` の構造（スキーマ `recipe`）を前提にしている。テーブルや列の構成が異なる場合は、実行時にエラーになる。エラーの内容から、どのテーブル・列が異なるかを確認すること。

## テスト

`src/features/recipe-management/tests/test_migration.py`。移行元の構造を再現した一時的な DB（`tests/fixtures/source_recipe.sql`）を、管理者（既定は `postgres` / `postgres`。`PG_ADMIN_USER` / `PG_ADMIN_PASSWORD` で変更可）で作り、移行先（開発用 DB）へ移行して検証する。テスト後に一時的な DB は削除する。
