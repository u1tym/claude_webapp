# 別サーバ版（note）からのデータ移行

`sample/note` で稼働している別サーバ版のノート管理サービスから、本機能（note-management）へデータを移行する手順。

移行元 DB と移行先 DB の **両方へ同時に接続** し、移行元から読んだデータを直接、移行先へ書き込む。エクスポート用のファイルは作らない。

移行元へは **読み取りしか行わない**（読み取り専用のセッションで接続する）。移行元のデータは変更・削除されない。

## 利用者について

移行元のアカウント（`public.accounts`）のうち、`--username` で指定したものを、移行先の **同じユーザ名の利用者** のデータとして移行する。

- 移行元に、そのアカウントが無いときは、何も移行せずに終了する（終了コード `2`）。
- 移行先に、その利用者が無い、または論理削除済みのときも、何も移行せずに終了する（終了コード `2`）。利用者は、事前にユーザ管理で作っておくこと。
- 移行元の、ほかのアカウントのデータは移行しない。
- 本機能の利用の割当（機能マスタ・メニュー割当）は、移行には不要（画面を使う段階で必要）。

## 移行するもの

| 移行元 | 移行先 | 備考 |
|--------|--------|------|
| フォルダ（`note.folder`） | フォルダ | 階層・名前・並び順を、そのまま移行する |
| ファイル（`note.file`） | ファイル | タイトル・並び順を、そのまま移行する |
| パーツ（`note.parts`） | パーツ | 種別・本文・ファイル名・タイトル・マーカー・倍率・並び順を、そのまま移行する |
| 過去世代（`note.parts_revision`） | 過去世代 | 世代番号・ファイル名・種別・中身・保管の日時を、そのまま移行する |
| チェックリスト（`note.checklist` と、そのカテゴリ・項目） | チェックリスト・カテゴリ・項目 | パーツの本文にあった識別子は、移行先の新しい識別子に付け替える |

- **削除済みのフォルダ・ファイル・パーツも移行する**（削除済みの状態のまま）。移行元の「削除番号」が 0 でないものは、移行先では「削除済み」になる。移行後に、画面から削除解除できる。
- 識別子は、移行先で新しく採番する。
- 画像・バイナリの中身は、移行元と同じく Base64 の文字列のまま移行する。移行後に、大きさと MD5 が移行元と一致することを確認する。

### 移行しないもの

| 対象 | 扱い |
|------|------|
| **表のパーツ**（と、その表・セル・列幅） | 本機能は表を提供しないため、移行しない。結果の一覧に、フォルダの経路・ファイルのタイトル・並び順を出す。パーツの並び順は欠番のまま残る |
| チェックリストの **削除済みのカテゴリ・項目**（削除済みのカテゴリの中の項目を含む） | 移行元でも元に戻す操作がないため、移行しない。結果の一覧に、件数を出す |

## 前提

- 移行先の DDL を適用済みであること。

  ```bash
  cd src/features/note-management/backend
  python sql/apply.py
  ```

- `backend` の venv が使え、`backend/.env` が移行先（本プロジェクトの DB）を指していること。別の DB を移行先にするときは、環境変数 `NOTE_MANAGEMENT_ENV_FILE` に、その接続情報を書いた設定ファイルのパスを指定する（`backend/.env` は変更しない）。
- 移行を実行する環境から、移行元 DB と移行先 DB の両方に到達できること。
- 移行元の DB ユーザには、`note` スキーマと `public.accounts` の読み取り権限があること。

## 手順

### 1. ドライラン（書き込まずに確認する）

```bash
cd src/features/note-management/backend
python scripts/migrate_from_note.py --dry-run --username <利用者名> \
  --host <移行元のホスト> --port 5432 --dbname <移行元のDB名> \
  --user <移行元のユーザ> --password <移行元のパスワード>
```

移行元の接続情報は、環境変数（`NOTE_DB_HOST` / `NOTE_DB_PORT` / `NOTE_DB_NAME` / `NOTE_DB_USER` / `NOTE_DB_PASSWORD`）でも指定できる（引数が優先）。パスワードをコマンド履歴に残したくないときは、環境変数を使う。

何も書き込まず、移行の対象・スキップ・対象外・失敗の見込みを、標準エラー出力に表示する。

### 2. 実行

```bash
python scripts/migrate_from_note.py --username <利用者名> \
  --host <移行元のホスト> --port 5432 --dbname <移行元のDB名> \
  --user <移行元のユーザ> --password <移行元のパスワード>
```

フォルダを、親が先になる順に移行したあと、ファイルを **1 件ずつ、1 つのトランザクション** で移行する（ファイル本体・全パーツ・過去世代・チェックリストを、まとめて確定する）。実行中は、ファイル 1 件ごとに進捗（`[n/全体件数] フォルダの経路/タイトル`）を表示する。途中で失敗したファイルは、移行先へ何も残らない（ロールバックされる）。1 件の失敗は、ほかのファイルの移行を止めない。

### 3. 結果を確認する

終了時に、種別ごとの件数と内訳が表示される。

```
===== 結果 =====
フォルダ: 移行 24 / スキップ 0 / 対象外 0 / 失敗 0
ファイル: 移行 71 / スキップ 0 / 対象外 0 / 失敗 0
パーツ: 移行 148 / スキップ 0 / 対象外 5 / 失敗 0
    [対象外] ファイル「備忘録/会社/休憩時間」(移行元ID=27) 並び順2: 表のパーツ（移行しません）
過去世代: 移行 4 / スキップ 0 / 対象外 0 / 失敗 0
チェックリスト: 移行 2 / スキップ 0 / 対象外 0 / 失敗 0
チェックリストのカテゴリ: 移行 7 / スキップ 0 / 対象外 0 / 失敗 0
チェック項目: 移行 45 / スキップ 0 / 対象外 0 / 失敗 0
```

| 区分 | 意味 |
|------|------|
| 移行 | 移行先へ書き込んだ（ドライランでは「移行予定」） |
| スキップ | 既にあるため書き込まなかった（移行済みのフォルダ・ファイル） |
| 対象外 | 移行の対象ではない（表のパーツ、チェックリストの削除済みのカテゴリ・項目） |
| 失敗 | 移行しようとしたが失敗した。理由が併記される |

- 終了コードは、正常が `0`、失敗が 1 件でもあると `1`、接続できない・利用者が無いときは `2`。
- 操作の記録（開始・ファイルごとの成否・終了）は、`backend/log/` にも残る。パスワードと、パーツの中身は出力しない。
- 移行したファイルは、移行先で、パーツ・過去世代・カテゴリ・項目の件数と、パーツの中身（大きさと MD5）が、移行元と一致することを確認したうえで確定している。

### 4. 再実行

途中で止まった場合や、失敗の原因（移行元のデータなど）を直した後は、**同じコマンドをもう一度実行すればよい**。

- 移行済みかどうかは、移行先の、**同じ親（フォルダ）の中に、同じ名前（ファイルは同じタイトル）で、同じ削除状態のものがあるか** で判定し、あればスキップする（スキップしたフォルダの中のファイルは、続きから移行する）。同じ名前の削除済みが複数あるときは、個数で判定する。
- 移行後に、移行先でフォルダ名・ファイルのタイトルを変えた、または削除・削除解除したものは、移行済みと判定されず、もう一度移行される。再実行するときは、そのようなものがないかを、ドライランで確認する。

### 5. 後片付け

- 移行の確認が済んだら、コマンド履歴や環境変数に残した移行元のパスワードを消す。
- 移行元のデータは、この手順では削除しない。旧サービスの停止・削除は、別途判断する。

## 移行元の構造に関する注意

移行元は、`sample/note/DB_NOTE_SPEC.md` の構造（スキーマ `note`、アカウントは `public.accounts`）を前提にしている。テーブルや列の構成が異なる場合は、実行時にエラーになる。エラーの内容から、どのテーブル・列が異なるかを確認すること。

## テスト

`src/features/note-management/tests/test_migration.py`。移行元の構造を再現した一時的な DB（`tests/fixtures/source_note.sql`）を、管理者（既定は `postgres` / `postgres`。`PG_ADMIN_USER` / `PG_ADMIN_PASSWORD` で変更可）で作り、移行先（開発用 DB）へ移行して検証する。テスト後に一時的な DB は削除する。
