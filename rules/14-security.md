# セキュリティ方式

> 元Cursorルールでの適用範囲: 常時適用

## 利用技術

- 開発環境では、httpを用いる。
- 本番環境では、httpsを用いる。
- 認証を用いる場合は、 **Cookie ベースのセッション認証** を用いる。

## ユーザ管理

- スキーマ `public` にユーザを置く（ユーザID、ユーザ名、パスワード、論理削除）。
- パスワードはハッシュ化して保存する。平文で保存しない。
- 機能スキーマにユーザ表を複製しない。

## 機能マスタとメニュー割当

- スキーマ `public` に機能マスタとメニュー割当を置く。
- 機能マスタは、機能の識別子、タイトル、遷移先 URL、アイコン、論理削除を持つ。
- メニュー割当は、ユーザと機能の対応と表示順を持つ。
- 機能スキーマにこれらを複製しない。
- 認証が必要な機能は、自機能の FastAPI で、ログイン中ユーザにその機能が割り当てられているかを判定する。論理削除済みのユーザまたは機能は許可しない。

## 認証方式

- ユーザ名とパスワードで認証する。
- 認証成功時、バックエンドがセッションを作成し、スキーマ `public` に保存した後、セッション ID を **Cookie** に載せる。
- 以降の要求は、Cookie のセッション ID でユーザを特定する。
- セッション ID を URL、レスポンス本文、`localStorage` に置かない。
- Cookie は HttpOnly とする。SameSite は Lax。本番では Secure を付ける。
- フロントから API を呼ぶときは Cookie を送る（credentials を含める）。
- CORS は許可オリジンを具体指定し、資格情報付きを許可する。`*` は使わない。
- セッションの有効期間は、分単位の `SESSION_TIMEOUT_MINUTES`。各機能の `backend/.env` に同じ名前で持ち、値はシステムで揃える。期限切れは未ログインとして扱う。
- 未ログインには HTTP 401、権限なしには 403 を返す。

### 開発時の例外

- `DEBUG_USER` があるときだけ、認証せずそのユーザ名として処理してよい。
- 本番では `DEBUG_USER` を空にする。

## 機能ごとの実装

- 認証が必要な機能は、自機能の FastAPI で上記を実装する。
- 他機能の API を認証に使わない。他機能の Python を import しない。
- 共通なのは `public` のユーザ・セッション・システム設定・機能マスタ・メニュー割当と、設定名 `SESSION_TIMEOUT_MINUTES` だけである。
- 機能の利用可否は、各機能が `public` の機能マスタとメニュー割当を直接参照して判定する。他機能の API は使わない。

## データへのアクセス

- DBに業務データを格納する場合は、項目としてユーザIDを設け、他ユーザのデータを参照させない。
